# Git 提交规范

## 触发时机

仅在执行 `git commit` 前读取本文件；其他时候不加载。

本文件同时约束**提交落在哪条线**（需求分支）与**合并方式**（PR squash）。派发消息会给出分支名；**未给出时先问 PM，禁止自行提交到 main**。完整流水线见 @.agents/skills/github-flow.md。

## 流程

1. 确认当前分支是需求分支 `feat/<issue-id>-<slug>`（降级 `nao/<批次-slug>`，**不是 main**）
2. `git diff --cached` 与 `git diff --cached --stat` 查看暂存变更
3. `git log --oneline -10` 参考近期提交风格
4. 按格式编写提交消息，执行 `git commit -m "消息"`

## 提交时机与分支（需求分支制）

**main 只收 squash 合并后的 1 条提交；过程中的提交一律落在需求分支。**

- **需求分支**：派发消息给出 `feat/<issue-id>-<slug>`（无 Issue 时 `nao/<批次-slug>`）。分支不存在时由**首个被派发的 RD** 从 main 拉出并在回执中注明；之后所有 worker 都在该分支提交。
- **过程提交（检查点）**：每完成一段可自测的逻辑就提交一次，前缀 `wip(<编号>): <可读短语>`。这类提交**可以多、可以小**，只作检查点/归因/回退用，**永不上 main**（合并时被 squash 吸收）。
- **暂存纪律**：只 `git add <自己负责的路径>`；**禁 `git add -A` / `git add .` / `git commit -a`**——同一工作区有多个会话并行，全量暂存会把别人未完成的改动一起卷进提交。
- **禁止直推 main / 绕过 PR 合并**：feature 分支允许 `--force-with-lease`（改基 / 压缩历史时），main 永远禁止 force push。
- **回执必带**：`commit=<短 hash>`，便于 PM 核对归因。

## 合并（squash，由 RD 在 PM 验收通过后执行）

- **闸门**：PM 验收通过 = 授权合并；**PM 不亲自合并、不 push main**。未过验收一律不得合并。
- 正常（有远端 + `gh`）：`gh pr merge <n> --squash --delete-branch`；提交信息取 PR 标题 + 正文，因此**可读性硬性落在 PR 标题**。
- 降级（无远端 / 无 `gh`）：`git checkout main && git merge --squash feat/… && git commit` + 删分支。
- 合并后：main 上本需求**恰好 1 条提交**，且不含任何 `wip()` 提交；不符则回退重做。
- 合并前清理：工作区干净、无游离文件、分支已 push 到最新。

## 特殊情况白名单（封闭列举，其余一律走需求分支 + PR）

只有以下情况可**直接提交并推送目标分支**（不经 PR 流程）；均须在 `docs/tasks-state.md` 标注原因：

1. 线上 Hotfix（走 `hotfix/<issue-id>` 分支 + PR 快速合并，事后补 Release 与变更单）；
2. 前后端分离且后端契约需先提交/推送，前端才能消费；
3. 依赖/构建/CI 变更需被其他会话或流水线立刻消费；
4. 用户显式要求提交。

「其他特殊情况」须由**用户确认**；PM 不得自行开口子。

## 消息格式

```text
<type>(<scope>): 简短描述（≤50字符）

变更点：

- 具体变更1
- 具体变更2

其他（可选）：

- 依赖/配置/构建等非功能变更
```

**可读性（硬性）**：提交信息是给**用户/未来的自己**看的，不是给编译器看的。

- 标题与变更点写「**用户能得到什么 / 行为怎么变**」，如「支持按当前筛选条件导出 CSV（含表头与中文编码）」。
- **禁止**只写编号、类名、函数名、文件路径、字段名、包路径（如 `实现 exportCsvHandler 与 ExportService`、`完成 AC1`、`改 packages/domain-task`）。
- 任务编号只作追溯用，放标题**尾部** `[T1]` 或关联 Issue `(#123)`，不替代描述。
- **main 上的可读性由 PR 标题承担**（squash 合并取 PR 标题）；PR 标题同样禁纯编号/类名/路径。
- `scope` 用可读的模块/功能名（`导出`、`日历`），不用包路径。

## 类型（可扩展）

- feat   新增功能
- fix    修复缺陷
- chore  构建/依赖/配置等杂项
- change 其他（重构、性能等）
- 扩展：refactor（重构）、docs（文档）、test（测试）、style（样式）等

## 规则

- **先写用户可见的行为变化**，再补技术细节；纯技术变更（如依赖升级）也写清「会带来什么」
- 变更点列出主要逻辑或用户可见变动，描述具体
- 其他仅放配置文件、依赖版本（注明旧→新版本号）等
- 避免重复，已列变更点的不再写其他
- 版本示例：`升级 dayjs 从 1.10.7 到 1.11.5`

## 示例

```text
feat(日历): 日期时间选择器显示当前选中值 [T3]

变更点：

- 时间面板不再显示 NaN
- 日期面板显示当前选中日期
- 日期时间面板显示当前选中日期时间

其他：

- 升级 dayjs 从 1.10.7 到 1.11.5
```

反例（不可读，禁止）：

```text
feat(T1): 实现 exportCsvHandler
变更点：
- 新增 ExportService 与 CsvWriter
- 调整 packages/domain-task 接口
```

## 注意事项

- 工作期暂存只用**路径级** `git add <路径>`；降级本地 squash 合并时才允许 `git add -A`
- 工作期提交可小而多（检查点）；**main 上每个需求恰好 1 条提交**（PR squash 产生），不在分支上拆分主线提交
- 使用中文，简洁准确
- 禁止提交未测试或含调试代码的变更
