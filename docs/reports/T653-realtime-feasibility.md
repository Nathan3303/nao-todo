## 0. 结论（先行，四问各一句）

1. **事件从哪来**：存在一个极低成本的落点 —— **粗粒度「用户数据变了」信号**，只需 **2 处**冒烟点（`/sync/push` 出口 + REST 写路由中间件）。这是「3 人天档」与「10 人天档」的**唯一分水岭**：一旦要求「精确到行」或走 binlog CDC，成本跳到 8–15 人天，而按「事件只当信号」的硬约束，精确粒度**买不到任何东西**。
2. **部署形态**：服务端**当前是单实例**（单 `app` 容器、进程内 cron、进程内 SSE Hub）；Redis 是**既定组件**（会话 / 限流 / cache-aside），但**无 pub/sub 使用**。多实例时缺 fanout 的后果只是「实时性退化到兜底轮询间隔」，**B 不因此变成必须 sticky**。
3. **桌面端建连**：**技术上现在就能建连**（CSP `connect-src` 已放行 API 源、单实例锁已在），历史 `VITE_DISABLE_SSE=true` 的真实原因是「桌面当时已本地扫描提醒、SSE 会双弹」，**不是平台限制**。但发现一条**硬前置缺陷**：生产 HTTPS `WriteTimeout = 15s`（`cmd/main.go:61`）⇒ 任何 SSE 流约 15 秒被服务端切断；叠加旧客户端 `error` 即 `close()` 不重连、无心跳 ⇒ 这正是 ADR 记录的「SSE 断线即静默漏提醒」的机制来源。**B 不改这条就必然重蹈覆辙。**
4. **工期分档**：C′ 1–1.5 · A′ 2–3 · B′ **7.5–12 人天**（服务端 3–5 / 客户端打底 2–3 + SSE 增量 1.5–2.5 / 联调门禁 1–1.5）⇒ **B 在 A′ 之上的增量 = 5.5–9 人天**。B′ 相对 A′ 的**增量价值**只在「两端同时开着」这个前提成立时才兑现 —— 该前提未证实。

**建议**：以 **A′ 打底（30s 起步，非 15s，见 §7-1 限流预算）+ B 分两步**；B 立项前先做一次 30 分钟的 `WriteTimeout` 复现实验（§3.3），把最大的未知先关掉。PM 的「A′ 打底 + SSE 加速」立场，本评估**独立复核后同意**，理由见 §5 的对照表。

## 1. Q1 变更事件从哪来

### 1.1 三个落点的量化对照

| 落点                             | 改口数量                                                                                                                           | 抓得到什么                           | 可靠性                                                                               | 成本                                         |
| :------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------- | :----------------------------------------------------------------------------------- | :------------------------------------------- |
| **(a) 写路径主动发（粗粒度）**   | **2 处**：`/sync/push` 出口（`interfaces/controllers/sync.go:252`，已握 `userId`）+ 一条 REST 写路由中间件（覆盖 32 条数据写路由） | 用户级「变了」（可选 `tables` 位图） | 进程内 best-effort，**提交后发布**；崩溃/重启窗口丢事件 ⇒ 由兜底轮询收敛（设计允许） | **1–1.5 人天**（含测试）                     |
| **(b) 逐行 / 仓储层埋点**        | **50 个仓储写方法**（`infrastructure/persistence/**` 全量写方法计数）+ 派生/级联点                                                 | `(table, id, updated_at)`            | 同 (a)                                                                               | **4–6 人天**；且需处理 userId 提取与事务边界 |
| **(c) 数据库位点（binlog CDC）** | 新组件（canal / Maxwell / `go-mysql`）+ MySQL binlog 配置 + 位点与回放运维                                                         | 一切写入（含未来非本服务写入者）     | 最强（至少一次）                                                                     | **5–8 人天 + 新部署单元**                    |

### 1.2 为什么选 (a)

- **与硬约束自洽**：事件只当信号、数据仍走 `pull` ⇒ 事件携带行内容/版本**毫无用处**（客户端拿到也不会用，用了就是第二条裁决路径）。行级精度只增加成本与出错面。
- **现成可复用的两块底座**：① 请求级 `derived.Recorder` 已在 `/sync/push` 收集「本次请求中被推进版本的行」（`infrastructure/derived/recorder.go`），虽只覆盖派生写，但**请求级收集器 + 事务后合并**的范式已验证；② `sse.Hub.PublishJSON` 已存在且**当前 0 调用者**（`infrastructure/sse/hub.go:50`），是现成的事件出口。
- **未覆盖的一处**：偏好/设置面走**另一条链路**（`preference-sync.ts` 的 `/user/config`，对应审计 `F-05`，不在 7 表内）⇒ 若 B 要连「改了设置另一端立刻变」，需在 `userRouter` 的 `/config` 写路径另加一处事件（+0.25–0.5 人天）。本评估按「7 表业务数据」计价，偏好面单列。
- **不可用的候选**：既有 `events.InMemoryBus` 只承载**计数事件**（18 个调用点，`domain/types/count_events.go`）；字段更新（改名/优先级/标签/排序）**不发布** ⇒ 直接复用覆盖不足，只能作为 (a) 的载体之一。
- **写路径清点**（(a) 的覆盖面依据）：服务端数据写入口 = `/sync/push`（1）+ REST 写路由 **32** 条（task 6 / project 8 / tag 5 / pomodoro 6 / comment 3 / event 4，`interfaces/routers/*.go`）。`/sync/push` 是 web/desktop 的**唯一**写通道（本地优先 ⇒ 写本地 → 队列 → 批量 push）；移动端（Lynx）走 REST ⇒ 中间件那一处正好补上。
- **cron 不是写者**：提醒 cron 的字段改写**默认停用**（`conf.reminder.cronFieldWriteBack` 零值 false，`infrastructure/initialize.go:181`）；会话清理/注销用户清理不碰用户任务数据 ⇒ 无遗漏写口（唯一残留：若有人把 `cronFieldWriteBack` 打开做回滚，需同步埋点 —— 登记为实现约束）。

### 1.3 可靠性差异（必须说清的边界）

- 事件是**通知**不是**日志**：无 outbox、无 at-least-once、无 replay。写入成功但事件丢失 ⇒ 该客户端**直到下一次兜底轮询**才知道。这是可接受的，前提是**兜底轮询常开**（§6.4）。
- 事件**必须在事务提交之后**发布。在提交前发布 ⇒ 客户端下拉读到旧值，且此后再无事件 ⇒ 永久落后于「兜底轮询间隔」（这是最隐蔽的一类错，务必写进实现约束）。
- 发布路径必须 **异步 + 有缓冲 + 满了就丢**，任何 panic/阻塞都不得影响写响应（老客户端零影响的一部分，§6.2）。

## 2. Q2 部署形态与 fanout

### 2.1 当前是单实例（证据）

- `docker-compose.yml` 只有**一个** `app` 服务（`container_name: naotodo-server`，固定端口 `3302`，`mem_limit: 512m` / `cpus: 0.75`），无 replicas / 无编排扩缩。
- 进程内 cron（`infrastructure.LoadCron`）与进程内 SSE Hub（`sync.Once` 单例 map）都**预设单写者**：多实例会重复跑 cron、事件也只会到「连在同一实例」的客户端 —— 这本身就是「当前单实例」的反证。
- MySQL 8.4（`mem_limit 768m`）+ Redis 8.8（`mem_limit 128m`，`allkeys-lru`）。

### 2.2 Redis 是既定组件，但不是 pub/sub

- 已在用：会话缓存 `cache:session:<uid>:<token>`（TTL 5 分钟，`sessionRepoImpl.IsSessionValid`）、限流（Lua 原子固定窗口 60s）、cache-aside（profile / config / project list / tag list），并带**进程内兜底**（Redis 不可用时降级，fail-open + 结构化日志）。
- **未用**：任何 **Redis pub/sub**（全仓无 `*redis.PubSub` / `Publish` 调用点；进程内 `events.InMemoryBus.Subscribe` 是计数事件总线，不是跨进程通道）。⇒ 加一路 fanout = 新增 1 个 channel + 1 个订阅循环 + 失败降级，**0.5–1 人天**，无新组件、无新运维面。

### 2.3 多实例时会不会「必须 sticky」

**不会。** 因为事件只当信号：

- 缺 fanout 的最坏结果 = 客户端的「即时性」退化为兜底轮询间隔（60–120s），**不是数据错误**（数据永远走 `/sync/pull`，且 keyset 游标与服务端实例无关）。
- 因此正确性不依赖 sticky；sticky 反而更差（连接分布不均、实例重启即全断、LB 需 `ip_hash` 且 NAT 下退化）。
- **但**若将来真扩容，仍建议 pub/sub 而不是 sticky（0.5–1 人天，一次性）：否则「同时开两端」的用户会随机拿到「秒级/分钟级」两种体验，且无法解释。
- 附带：SSE 长连接是**有状态资源**。单实例 `mem_limit 512m` 下必须设**每用户连接上限**（建议 ≤2）与**总连接上限**，否则一次重连风暴就能顶到内存墙。

## 3. Q3 桌面端建连是否可行

### 3.1 先把历史事实纠正

- `VITE_DISABLE_SSE=true` 的**原始理由写在代码注释里**：`# 桌面版禁用远程 SSE 提醒（本地定时扫描替代）`（`apps/desktop/.env.development`，见 `4798920e`/`44ad5756` 与其后 `2b478e0e` 的删除）· 接线处 `index-view.ts:143-148`（历史版本 `2b478e0e^`）「桌面版通过 VITE_DISABLE_SSE=true 禁用（本地定时扫描替代）」。
  ⇒ **原因 = 避免与桌面本地提醒扫描双弹，不是 Electron 不能建连。**
- `VITE_DISABLE_SSE` 与**整个 SSE 客户端已在 `v1.12.15` 全部下线**（`docs/releases/v1.12.15.md`、AC10 用例 `packages/shared/reminder/__tests__/t525-ac10-single-implementation.test.ts`）⇒ 今天**客户端侧没有任何 SSE 代码**，是全新的接线（不是「重新打开开关」）。

### 3.2 两条真实的坑（已定位到代码，不是猜测）

1. **服务端 15 秒切断**：生产 HTTPS `http.Server{ReadTimeout: 15s, WriteTimeout: 15s, IdleTimeout: 60s}`（`cmd/main.go:60-62`）。Go 的 `WriteTimeout` 是**整个响应写**的截止时间（不是每次 write 重置）⇒ 任何 SSE 流约 **15s** 后写失败、连接被关。该设置来自 2026-06-24 移除 Nginx 时的一次性改动（`abdb2b1`），**早于**提醒 SSE 的上线 ⇒ 提醒 SSE 在生产**始终**是 15s 断。
2. **旧客户端无重连、无心跳**：`shared/hooks/use-sse.ts`（已删除，见 `2b478e0e^`）在 `error` 时 `close()` 且**不重连**；`reminder-sse.ts` 同样「`error` ⇒ `close`」；无心跳、无看门狗、无 `Last-Event-ID`。
   ⇒ 两条叠加 = 「**断线即静默**」，与 PRD `2026-10-23-reminder-local-polling.md:14`「SSE 断线即静默漏提醒」的表述完全吻合。**这是机制级证据链，但未做生产抓包复现**（建议 30 分钟实验证伪，见 §3.3）。

### 3.3 现在建连需要论证什么（B 的必证清单）

| #   | 必须论证            | 判定口径                                                                                                                                                                                                                            |
| :-- | :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `WriteTimeout` 处置 | 用 `http.ResponseController.SetWriteDeadline` 在 SSE 路由内续期（Go 1.25 可用），或长连接独立 server/路由；**其它路由保持 15s 不变**。30 分钟实验：本机 HTTPS + `/api/sse/reminders` 观察是否 ~15s 断（现状应断）→ 改后 ≥5 分钟不断 |
| 2   | 心跳                | 服务端每 15–25s 写 `:\n\n`（或 `event: ping` + 递增 seq）；客户端看门狗「2× 心跳周期内零字节 ⇒ 判假活」                                                                                                                             |
| 3   | 重连                | 指数退避 + 抖动，上限 ≤60s；`online` / `visibilitychange→visible` / 系统唤醒立即重连（Electron 休眠会断，与 Web 同）                                                                                                                |
| 4   | 不影响本地优先      | 事件只当信号 ⇒ 断线只影响「更新延迟」，**不得**改变本地可读可写、不得触发「离线/只读」判定（沿用 `DEF-33` 口径：SSE `error` 只关连接，认证清理仍由 `requester` 的 `10041` 单源兜底）                                                |
| 5   | 兜底轮询**常开**    | 不采用「断开时才轮询」：假活（连着但收不到）无法检测，只能靠常开兜底。间隔 60–120s（可见时）                                                                                                                                        |
| 6   | 不复用做提醒        | 提醒判定已本机化（ADR `2026-10-23`）；SSE 若再承载提醒 = 双弹 + 漏弹，**禁止**                                                                                                                                                      |
| 7   | 单主                | Web 多标签 / 桌面单实例（`C-57` 已存在）⇒ 每 origin **1 条连接**，非主标签经 `BroadcastChannel` 收「数据已变」                                                                                                                      |

**会不会重蹈覆辙**：只有把 SSE 当「准时/可靠的唯一通道」时会。本条设计把它**降级为加速信号**（丢失可容忍、兜底轮询保证收敛、数据永不走事件）⇒ 不会。上一代之所以翻车，正是因为它被当成了**唯一通道**且没有兜底（提醒场景不容忍漏，所以必须换）。

## 6. 硬约束逐条结论

### 6.1 「事件只当信号、不得新增第二条数据裁决路径」→ 成立，且是唯一合理形态

- 事件载荷建议只有 `{ type, at, tables? }`（**无行数据、无版本号、无 `serverCurrent`**）；客户端收到后唯一动作 = `syncService.pullAll()`（经既有 `enqueue` 串行门）。
- 验收判据（可自动化）：把事件载荷中所有数据字段删除后，客户端行为与断言**全部不变**。
- OCC / `baseUpdatedAt` / 冲突落账 / `pull-local-wins` 语义**零改动**；B 的改动面 = 「何时调 pull」，不是「pull 怎么裁决」。

### 6.2 「服务端改动对老客户端零影响」→ 成立，但有 4 个必须满足的条件

| 条件                                                             | 理由                                                          |
| :--------------------------------------------------------------- | :------------------------------------------------------------ |
| 新端点走**新路径**（如 `/api/sse/events`），老客户端从不建连     | 不建连 = 零行为差异（含老客户端不认识的字段/路由）            |
| 事件发布**在事务提交后、异步、有界缓冲、满了即丢**，并 `recover` | 发布不得改变写响应的状态码/体积/耗时（含 panic 不外溢）       |
| 不改 `/sync/pull`、`/sync/push` 的请求/响应契约                  | `R-D` 红线（老客户端不带 base 的推送/删除逐字不变）           |
| `WriteTimeout` 只对 SSE 路由放宽；新路由用**独立限流 tag**       | 放宽全局超时 = 全站语义变更；共享 `sync` 桶会挤占老客户端配额 |

**唯一残留的间接影响** = 资源：长连接占用内存/goroutine、事件发布 CPU。给出上限（每用户 ≤2 连接 + 总连接上限），并单独埋点（连接数、发布丢弃计数），不与现有健康检查混在一起。

### 6.3 轮询 ↔「本地未推改动」的边界：**不会判成假冲突**，但有 3 条规则 + 1 个副作用

**结论依据（读码）**：`/sync/pull` 遇到「本地有未推修改（`syncQueue` 有项）」时按 LWW 分三支（`sync-service.ts:1039-1101`）：

- 远端更新 ⇒ 远端胜：覆盖本地 + **出队** + 记 `remote-wins`（`kind: 'remote-wins'`，`:1048` / 墓碑分支 `:1074`）；
- 本地更新 ⇒ 本地胜：记账 `pull-local-wins`（`:695`）+ **把 base 收敛到远端 `updatedAt`**（`:1099`）+ **保留队列项**；
- 远端是墓碑 ⇒ 强制远端胜（否则下一步 push 会**确定性复活**墓碑）。

因为本地胜分支已把 base 推到「库中当前版本」，下一次 push 的 `baseUpdatedAt` 恰等库中值 ⇒ 服务端判 `applied`（**不是 `stale`**）。⇒ **假冲突不成立。**

**客户端必须遵守的规则**（A′/B′ 都要写进实现约束）：

- **R-1** pull 与 push 必须始终经同一串行队列（现状 `enqueue`）。事件回调**不得**直接调内部 `pullAllInner` / 绕过锁。
- **R-2** 本地写必须「业务行 + 队列」**同一 Dexie 事务**（现状 `putWithSyncBaseAndEnqueue`，`persistence-local/repos/put-with-sync-base.ts:56-72`）。高频 pull 会反复踩「行已写、队列未入」的窗口，这是唯一会制造「无记账静默覆盖」的路径。
- **R-3** 墓碑强制远端胜的特判**不得**因「pull 更频繁」而放宽（放宽 = 复活墓碑）。

**必须承认的副作用（产品面，不是正确性）**：拉取频率上升会**放大真实裁决的发生次数** —— 尤其 `pull-local-wins` 记账（它在冲突面板里就是一条「云端版本被你的版本覆盖」）。这不是假冲突，但**用户会感到「冲突变多了」**。建议 A′/B′ 同批降噪：同实体合并为一条 / 仅在随后的 push 确实 `applied` 时保留。另：`remote-wins` 命中「本地刚编辑 2s 内还没推」窗口的概率会随频率上升（用户感知为「刚打字就被回滚」）⇒ 这正是 PM 提的「脏数据暂停」要解决的问题：**队列非空时降频/暂停周期拉取**（`online`/可见/手动仍可拉，避免永久饿死）。

### 6.4 失败模式：独立活性判定（假活怎么发现、回落到什么）

| 失败模式                              | 是否可检测                                                                                                            | 处置                                                                            |
| :------------------------------------ | :-------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------ |
| 服务端 15s `WriteTimeout` 切断        | 可（客户端 `error`/`close`）                                                                                          | §3.3-1 修正；修正前不得上线                                                     |
| 中间层空闲断开（反代/CDN/运营商 NAT） | 可（`error` + 看门狗）                                                                                                | 心跳 + 看门狗（2× 周期无字节）+ 退避重连                                        |
| **假活**（TCP 在、事件永远不来）      | **不可由连接状态检测**                                                                                                | ① 心跳 seq 不递增 ⇒ 判假活并重建；② **常开兜底轮询**（唯一独立于 SSE 的活性源） |
| 事件被丢弃（Hub 满）                  | **不可检测**：`publishRaw` 在缓冲(10)满时 `select default` **静默丢弃**（`infrastructure/sse/hub.go:74-77`）          | 同上：兜底轮询；并把「发布丢弃计数」做成服务端指标                              |
| 发布先于提交 / 提交失败               | 不可检测                                                                                                              | 实现约束：提交后发布（§1.3）                                                    |
| 会话失效但连接仍在                    | 可（发布时 `SessionValidator`；缓存 5 分钟）                                                                          | 沿用；错误分类走 `10041` 单源，**SSE 层不清认证**                               |
| 多标签抢锁导致「非主标签永不刷新」    | 可（现状会**整轮跳过**：`withPullLock` 用 `navigator.locks` `ifAvailable`，未取锁 ⇒ skip，`sync-service.ts:828-848`） | **单主 + `BroadcastChannel` 通知必须成对**；只做单主 ⇒ 非主标签 UI 永久陈旧     |

> 「数据是否新鲜」的判据**不得**用连接状态，必须用现有的 `syncStatus.mirrorPulledAt`（`persistMirrorStatus` 落 IndexedDB，冷启动可读）与 `lastSyncAt`。

## 7. 跨仓与运维面（B 的额外成本来源，PM 易漏）

1. **限流预算（A′ 也会踩）**：`/api/sync/push` 与 `/api/sync/pull` **共享**同一个 `sync` tag 桶，**24 次/分钟/IP**（`interfaces/routers/syncRouter.go` + `middlewares/rateLimit.go:50` + 60s 固定窗口）。key 是 **IP**，不是 userId。
    - 15s 轮询 = 4 次/分/端 ⇒ 同一 NAT 下 **6 端即打满**；30s 轮询 = 2 次/分 ⇒ 12 端。
    - 更要紧的是：push 侧 2s 防抖下**连续编辑**理论峰值 30 次/分，**今天就可能触顶**（既有隐患，非本次引入）。⇒ **建议 A′ 用 30s 起步**；若要 15s 或要根治，需把 sync 限流改 userId 维度（服务端 0.5 人天，但属安全面改动，需单独评审）。
2. **反代 / CDN**：生产是否在 Go 之外还有一层代理，**仓库无法确认**（TLS 证书直接挂给 Go，`cmd/main.go` 自起 HTTPS）。若有 CDN，需确认「不缓冲 `text/event-stream`、空闲超时 ≥ 心跳周期」；`X-Accel-Buffering: no` 已在控制器里设（`interfaces/controllers/sse.go`），只对 Nginx 系有效。
3. **鉴权形态**：`EventSource` 不能带自定义头 ⇒ 只能 `?token=`（`/api/sse/` 前缀是 SEC-06 的允许清单位，`middlewares/jwtValidator.go:19-21`）。代价：**7 天会话 token 会落进反代/网关日志与 URL**。B 若要更干净，需一次性 ticket（`POST /sse/ticket` 换 30s 短票，+0.5 人天）—— 建议同批做，否则是在既有安全收口上开一个口子。
4. **连接资源**：`mem_limit 512m`；每连接 = goroutine + 10 槽缓冲 + 发布期 `SessionValidator`（Redis 命中，5 分钟缓存）。需设每用户/总连接上限与指标。

## 9. 需 PM / 用户拍板的决策点

- **D1 实时性的目标口径**：接受「30s 内一致」= A′ 即可收工；必须「秒级」才需要 B。**（决定是否花那 5.5–9 人天增量）**
- **D2 B 的价值前提**：是否经常两端同时开着（PM 已提，用户未答）。若不常开 ⇒ **建议止于 A′**。
- **D3 `WriteTimeout` 松动授权**：B 的硬前置；改动面覆盖服务端超时语义（须服务端先发、可回滚）。
- **D4 可靠性口径**：接受「事件可能丢、靠兜底轮询收敛」这一 NFR（不是 exactly-once）；据此定「兜底轮询间隔」进 AC。
- **D5 部署拓扑事实**（§8-①）与是否允许新增一次性 ticket 端点（§7-3）。
- **D6 限流是否改为 userId 维度**（跨仓 + 安全面，建议单独立项，A′ 先按 30s 规避）。
- **D7 `pull-local-wins` 降噪是否与本批同做**（否则「冲突变多」会成为新的用户抱怨）。

> 本评估**不替 PM 拍板**；D1–D7 的取舍属 trade-off，需 PM/用户裁定。
