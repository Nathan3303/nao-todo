## 二、根因

1. **设计派单缺锚点**：v3 被否定真因不是审美，而是我派单只写"参考项目风格"，没给既有类名与取值来源 ⇒ 设计自造了第三套盒子（1px 边框 + 卡内定高 + 自定义标签），与项目"有底色行 / 悬停描边"的语言冲突。
2. **探针与测试的边界靠自觉**：项目早已写明"探针放 `/tmp`、跑完删"，但没有机械闸；一个 worker 把它写成"测试"就绕过了纪律，且后果是**无关文件**报错，定位成本高。
3. **判据采样不足**：我用「单跑 5 次全绿」下了"负载相关 flake"的结论，qa 用 ×20 直接推翻（红在 12–14 次，连续三次）；真实根因是模块级定时器跨用例残留。
4. **派单措辞不精确**：`分支/工作区：main` 这类缩写对"该写在哪个分支"是歧义的，直接导致本地 main 被污染。
5. **子代理不稳定**：qa 三次 `ECONNREFUSED`（另有 2 次 30 分钟超时）⇒ 复签中断，末次机械复核由 PM 代做。

## 三、改了什么机制（可验证防线）

1. **设计派单模板**（我方）：必须写「既有先例：<文件名 + 类名>」+「取值来源：<token / 组件档位>」；无锚点的设计稿一律打回。验证：本批 v4 起稿件逐条引用既有类名，重写一次通过。
2. **探针进仓的机械闸（待落地）**：`apps/web` 与 `packages/shared` 的测试禁止 `from 'node:`（白名单外），违者红。本批的 `vp check` 事故就该被它提前拦住。
3. **flake 判定口径**：5 次采样不足以结论；**≥20 次连跑，或 ≥10 次 + 负载矩阵**；且必须记录「红在第几次、是否连续」。
4. **派单措辞**：固定写「分支 `<branch>`」+「⛔ 文档提交不得落本地 `main`，随任务 PR」；移除"分支/工作区"这类缩略写法。
5. **子代理中断留痕**：网络中断/超时一律在台账与报告写「qa 未复签，PM 代验 + 判据与数字」，不得写成"qa 已复验"。
