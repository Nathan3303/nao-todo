## 三、重大发现：一次约 4.5–5 分钟的「全请求 10041」窗口（疑似 DB 故障被折叠为凭证失效）

### 3.1 现象（原始证据）

`⑤` 的第 23–32 轮（**05:15:43.537Z → 05:20:22.661Z**，10 轮 / **60 次请求**）：3 个 token 的 **pull 与 push 全部 `10041`**，原始响应体：

```text
{"code":10041,"message":"用户凭证验证失败"}   （HTTP 200）
```

随后**未做任何重新登录**，第 33 轮（**05:20:52.737Z**）起自动恢复 `90020` / `90010`。

完整 40 轮逐 cycle 表（时间戳 / 3 个 token 的 pull、push 响应码 / 是否恢复）见 **§七**——该表是 `DEF-143` 的原始证据，可逐行复核。

### 3.2 为什么排除「我的 token 失效」

| 反证              | 证据                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------- |
| 不是单 token 问题 | 3 个**不同时刻签发**的独立 token（05:02 / 05:04）**同时**失效、**同时**恢复           |
| 不是被登出        | 窗口期间**没有任何 `signin`/`signout` 调用**；恢复时用的仍是同一批 token 文件         |
| 不是 JWT 过期     | JWT payload 实测 `exp=1794114146`（= 48h 后）、`iat=1793941346`；窗口内时间远未到     |
| 不是限流          | 限流超限是 `10051`，观察到的全是 `10041`；且 60s 窗口内只有 6 次 pull（配额 12）      |
| 不是账号被软删    | 窗口前后同一 token 正常工作；且软删路径会在 `signin` 返回 `pendingDeletion`（未出现） |
| 不是会话行被删    | 会话行若能「自己回来」不成立；且恢复后 `auth.Validate` 命中同一 token                 |

### 3.3 代码路径（部署提交 `049068a1` 已核对）

```text
JWTValidator        interfaces/middlewares/jwtValidator.go:68-76   （auth.Validate 任何 err ⇒ 10041）
  └ authApp.Validate  application/auth/appImpl.go:222-245
      ├ ParseJWT / IsJWTExpired                    （窗口内 exp 未到 ⇒ 不是这里）
      └ FindSessionByUserIdAndToken
          └ sessionRepoImpl.FindByUserIdAndToken   infrastructure/persistence/identity/sessionRepoImpl.go:345-370
```

关键在最后一步：该方法**只把 DB 错误打成一行 `Warnf`，然后返回零值实体**（注释自己写明「否则会被上层统一折叠成『用户凭证验证失败（10041）』」）：

```go
if err := sr.db.WithContext(ctx).Model(&models.UserSession{}).Where(findCond).First(&session).Error;
    err != nil && !errors.Is(err, gorm.ErrRecordNotFound) {
    logging.Warnf("会话查询失败（按 user_id + token）: user_id=%d token_len=%d err=%v", ...)
}
return SessionModel2Entity(session)   // ← 零值 ⇒ IsValid()==false ⇒ ErrTokenExpired ⇒ 10041
```

⇒ 结论（推断，需生产日志确认）：**该窗口内「按 user_id + token 查会话」这一步整体失败（MySQL 瞬时不可用 / 连接失败 / 查询超时）**，而失败被折叠成「凭证失效」，对外表现与「所有人都过期了」完全一致。

### 3.4 影响面与建议

- **客户端语义**：客户端把 `10041` 当「会话失效 ⇒ 清认证回登录页」⇒ 该窗口内**所有在线用户会被踢回登录**；而服务端**没有 5xx、没有错误率指标**，只留一行 Warn（`ratelimit` 之外的可用性问题不会被常规监控抓到）。
- **本次可证范围**：只证到「QA 账号在该窗口被拒」+「机制上对所有用户同构」（同一 repo 方法、无按账号分支）。真实用户是否同样被踢，需查生产日志关键字 **`会话查询失败（按 user_id + token）`** 与 MySQL 侧（重启 / OOM / `max_connections` / 网络抖动）。
- **建议（既有缺陷，非本单引入）**：DB 类错误**不得**折叠为 `10041`，应回 5xx 或专用业务码（客户端不清认证、走退避），并加计数指标。
- **处置**：已按「异常先报」纪律即时上报 PM；PM 已立 **`DEF-143`（P1）**（登记在 `docs/reports/defect-pool.md`），修法方向：① DB/连接类错误不得映射 `10041`（改 5xx 或专用 `9002x`）② 客户端 `10041` 加二次确认（连续两次 / 健康探测通过再清认证）③ `Warn` 计数进指标告警。**归 rd-be / rd-fe，走独立单，不在本单范围。**
