### 1.3 Q1 确认：是不是「整行 LWW」？逐表谁被丢？

**是。** 服务端 `DecideUpsert` 只在**整行版本**层面判定（`base == 库中 updated_at` ⇒ 覆盖，否则 `stale`；base 缺失 ⇒ 旧 LWW），而覆盖动作是 `UpdateColumns(整行 map)`（`task/repoImpl.go:137-145`、`project/repoImpl.go:96-102`、`tag/repoImpl.go:126-130`、`pomodoro/*RepoImpl.go`）。客户端 `entityToPush` 把该表**全部白名单字段**一次性发出（`sync-service.ts:96-260`）。⇒ **没有任何字段级 base 或字段级合并**。

**举例（A 端改 `name`、B 端改 `priority`）**：

| 时序                                                                                           | 结果                                                                                      | 是否留证据                                  |
| :--------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------- | :------------------------------------------ |
| A 先推成功；B 后推（B 的 base 仍是旧版本）                                                     | 服务端判 `stale` → 不写入，回库中当前版本 ⇒ **B 的 `priority` 丢失**，本地行仍是 B 的版本 | ✅ journal `stale`（含 B 的整行快照）+ 计数 |
| A 先推成功；B 先 **拉**（B 的队列项更旧）→ B 后推                                              | 拉取走「远端胜」⇒ **B 的 `priority` 丢失**，本地被 A 的整行覆盖                           | ✅ journal `remote-wins`（含 B 的整行快照） |
| A 先推成功；B 先 **拉**（B 的本地编辑时间更晚或同毫秒）→ B 后推                                | 「本地胜」分支**只把 base 收敛到 A 的版本**，随后 B 整行覆盖 ⇒ **A 的 `name` 丢失**       | ❌ **无 journal、无日志、无提示**（F-01）   |
| A、B 各自拉取后同时编辑并推送（base 均为同一旧版本），且首次写入落在**与该旧版本相同的毫秒**内 | 第二次推送的 `base.Equal(existingUpdated)` 仍成立 ⇒ 整行覆盖，无 stale                    | ❌ 无 journal（F-07，既有 `R-14`）          |

**`outcome = conflict` 之后客户端怎么处置（完整链路）**：

1. 服务端：`createdAt` 与库中相差 > 1min ⇒ `ErrIDConflict` ⇒ `outcome=conflict`，**不写入**（`domain/types/upsert.go:42-45`、`interfaces/controllers/sync.go:79-84`）。
2. 客户端：`kind='conflict'` 入 journal，但 `withSnapshot=false` ⇒ **`loser` 落成 `{}`**（`sync-service.ts:1317-1334`）；`SNAPSHOT_KINDS` 不含 `conflict` ⇒ UI 列表里 `loser=null`（`conflict-journal.ts:168-172, 229`）。
3. **不写回 base**（只有 `applied/noop/stale` 写回，`sync-service.ts:1337-1341`）。
4. 出队（revision 未变，`sync-service.ts:1344-1347`）⇒ 本地行原样保留、base 仍旧。
5. 下一次 pull：本地无队列项 ⇒ **无条件整行覆盖**（`sync-service.ts:985-1005`）⇒ 本地内容被服务端那条「ID 碰撞的另一实体」替换。
6. 结论：**本地内容永久丢失，只留下一个「冲突 N」计数**，用户即使打开面板也无内容可比对、无法恢复（F-03）。

> 重试？覆盖？丢弃？用户可选？—— `error`/未回执会重试；`conflict/skipped` **直接丢弃**；`noop/stale/remote-wins` 丢弃但留快照，用户可在面板选「保留服务端」或「以我的版本重试」；`applied` 视为成功。**唯独「本地胜」分支既不是丢弃也不是保留，而是悄悄把对方的改动合并掉（方向相反）。**

## 3. 量化：能估吗？

### 3.1 结论：**真实发生频率不可估计**（不是「没时间算」，是**没有观测面**）

三条硬约束：

1. **最严重的 F-01 根本不进任何日志** —— 现有冲突日志只覆盖 `remote-wins / push-noop / stale`（+ 无快照的 `conflict/skipped`），而 F-01 走的是「本地胜」分支，**代码里没有任何写点**（`sync-service.ts:967-981`）。⇒ 任何基于 journal 的统计都会**系统性低估**，且低估的正是最该量化的那一类。
2. **客户端日志从不上报** —— `structured-log` 只有 `console` + 200 条内存缓冲（`observability/structured-log.ts:1-40`），无远端 sink；`meta` 里的 journal 只在本机 IndexedDB（库名 `nao-todo-desktop`），**无导出、无遥测**。
3. **服务端只有访问日志** —— `RequestLogger` 只记 `method/path/status/duration/ip/user_id/...`（`interfaces/middlewares/requestLogger.go:26-58`），**没有 body、没有逐条 `outcome`**；`/sync/push` 无论内部多少条 `stale` 都是 HTTP 200。⇒ **服务端无法与客户端对账**，也无法反推覆盖次数。

### 3.2 本机可提取的统计（若允许人工导出，**不改代码**：DevTools → IndexedDB → `nao-todo-desktop` → `meta` → `${userId}:conflict-journal`）

| 统计                                       | 口径                                                                                          | 能回答什么                                                         | 局限                                       |
| :----------------------------------------- | :-------------------------------------------------------------------------------------------- | :----------------------------------------------------------------- | :----------------------------------------- |
| 按 `kind` 计数                             | `remote-wins / push-noop / stale / conflict / skipped`                                        | 冲突主要来自「拉取覆盖」还是「OCC 拒写」                           | 不含 F-01；`conflict/skipped` 无内容       |
| 按 `table` 分布                            | `tasks` vs 子实体 vs 容器                                                                     | 哪类实体最易冲突                                                   | 小样本、单设备                             |
| distinct `table:entityId`                  | 与状态面 `conflictObjectCount` 同源（`conflict-journal.ts:110-113`）                          | 受影响的**对象数**（非事件数）                                     | 「同一对象反复冲突」会被折叠               |
| `at` 时间分布                              | 客户端时钟（`appendConflict` 用 `new Date()`，`conflict-journal.ts:140`，**未经服务端校准**） | 冲突是否集中在「启动后首轮」「批量编辑后」                         | 客户端时钟偏斜会污染分桶                   |
| `winnerUpdatedAt − loserUpdatedAt`         | 两端时间戳差（ms）                                                                            | **竞态窗口估计**：差值 < 数秒 ⇒ 真并发；差值很大 ⇒ 时钟偏斜/长离线 | 一边是服务端时间、一边是客户端时间，含偏斜 |
| 快照体积（`JSON.stringify(loser).length`） | 单条败方内容大小                                                                              | 估算「若全量事件化」的存储放大倍数                                 | 只对留快照的 kind 有效                     |
| `conflictJournalEvictedCount`              | 累加淘汰数（`conflict-journal.ts:143-148`）                                                   | 事件总数的**下界**（≥ 200 + evicted）                              | 清库即归零                                 |

### 3.3 建议的度量路径（如需「真数字」，三选一，按成本升序）

1. **一次性人工抽样**（0 人天）：找 3–5 台真实在用的设备，按上述口径导出 journal，得到「量级」而非「比例」；
2. **埋点（推荐，1–2 人天）**：给 F-01 补 journal 写点后，把 `appendConflict` 的 `kind/table/deltaMs` 打到**已有的** `structured-log` 事件里，并由用户自愿导出日志（不新增上报通道，符合隐私最小面）；
3. **服务端审计（3–5 人天）**：`/sync/push` 增加逐条 `outcome` 的**计数型**结构化日志（不记 body、不记内容），可算「每千次推送的 stale/conflict 率」，但仍**无法**覆盖 F-01。

### 4.3 op-log 能解决什么、不能解决什么（直答 Q4）

**真能解决**

- **字段级意图表达**：`set(priority, 3)` 比「整行快照」信息量大，天然支持「不同字段各自合并」——但**前提是**同时引入**字段级 base / 因果序**，日志本身不产生合并能力。
- **审计与追责**：op 带 `deviceId + seq + at`，可回答「谁改的」；这是当前架构**完全没有**的能力（服务端无业务日志、客户端 journal 无设备标识）。
- **断点续传 / 幂等重放**：序号化后「客户端只发 `seq > serverAck`」，比现在的「整批重发 + base 判定」更干净（当前重试会产生伪 stale，见 F-09）。
- **可恢复**：保留 op 即可点对点回滚/重放，不依赖 200 条 journal 上限。

**误以为能解决（实际不能）**

- **冲突仍需策略**：两台设备都 `set(priority)`，最终必须选一个。op-log 只把「整行二选一」变成「字段二选一」，**没有消除冲突**。
- **顺序与因果**：客户端时钟不可信（F-07 就是同毫秒令牌的后果）；必须引入 `(deviceId, seq)` 或服务端单调序，否则「先删后建」「先加标签后删标签」会重放出错误状态。**这是 op-log 的最大隐藏成本**。
- **离线长尾**：离线一周的 op 链要在服务端按序应用，且要与「期间他端 200 次修改」交错 ⇒ 日志增长、压缩、快照基线、幂等窗口全部要设计。
- **存量迁移**：历史数据没有 op，只能为每行生成一条 `bootstrap(snapshot)` 事件；**无法重建真实历史** ⇒ S2/S3 只能对「上线之后」成立（必须向用户说清）。
- **删除语义**：墓碑仍然需要；「删除」在事件模型里是 `deleted` 事件，仍要定义「删除 vs 编辑」的裁决（与 F-04 同一个问题）。
- **安全/隐私反向恶化**：事件保留全部内容历史 ⇒ 静态暴露面、保留期、被遗忘权、跨境合规都要重做（F-13 已显示当前 journal 是**明文**）。

### 4.5 若要做，最小可行版本（B / B′）与**不可逆点**

**B（字段级合并，推荐的最小形态）**

1. **服务端**：高频表加**可空 JSON 列** `field_versions`（`{field: serverVersion|seq}`），写入时按字段更新；`/sync/push` 条目新增 **additive** `fieldBases: {field: version}`；合并规则 = 字段 base 匹配 ⇒ 写该字段；不匹配 ⇒ 该字段进 `fieldConflicts[]` 回执（**不写**）。整行 `baseUpdatedAt` 语义保留：**无 `fieldBases` ⇒ 逐字回落现在的整行 LWW**（老客户端零变化）。
2. **客户端**：本地行维护同一份 `fieldBases`（非索引字段，同 `syncedServerUpdatedAt` 先例，不 bump Dexie version）；写路径记录「脏字段集合」；pull 时按字段合并，冲突字段入 journal（`kind='field-conflict'`，带字段名 + 两侧值）。
3. **UI**：冲突面板从「整行 A/B」升级为「逐字段选择」（这是 `S1` 真正兑现的地方）。
4. **工作量**：`tasks` 单实体 **14–20 人天**（服务端 6–9：列 + 合并 + 回执 + 单测；客户端 6–9：字段脏集 + 合并 + journal + 面板；灰度/回滚 2）。

**B′（意图 op，仅任务域）**：op 表（`deviceId, seq, entityId, field, op, value, at`）+ 服务端投影 + 客户端未确认队列；**20–30 人天**；比 B 多的收益是审计与撤销，多出的成本是因果序、压缩、投影校验。

**不可逆点（必须在派单前写明）**

| 项                   | 为什么不可逆                                                                               | 提前规避                                                                |
| :------------------- | :----------------------------------------------------------------------------------------- | :---------------------------------------------------------------------- |
| B 的字段级合并       | 一旦写入「多源拼合行」，关闭开关只能停止**继续**合并，**无法还原**为某一端的整行快照       | 保留字段级 journal（谁赢了哪个字段）≥ 90 天；提供「回滚到某端整行」工具 |

## 5. 推荐与分阶段

### 5.1 一句话结论

> **不要改成 op-log + 重放。** 先用 **9–14 人天**把 5 条「会静默丢」的窗口（F-01/F-02/F-03/F-04/F-06）补上（A），同时补 1 个 F-01 的观测点；3 周后用真实数字决定是否对 `tasks` 上 **B**（字段级合并）。C 只在「多用户协作清单」或「合规审计」成为产品需求时才值得。

理由：

1. 现架构的**致命问题不是「没有事件日志」，而是「有一条覆盖路径完全没有记账」**（F-01）。op-log 不会自动修好它——把快照换成 op，仍然要在「同字段冲突」上做同一个决策；而 F-01 的根因是**客户端在拉取时把远端版本当成了自己的 base**，与日志形态无关。
2. 用户诉求里 **S4（断网不丢）现状已基本满足**（队列 + 墓碑 + 退避 + 启动补拉 + 首拉只读闸门），op-log 在这方面**不带来增量**，反而引入压缩/长尾风险。
3. B 的收益集中在 **S1/S5**；C 的额外收益集中在 **S2/S3**（审计/撤销）。当前是**单用户多端**形态，S2/S3 的边际价值低于其 3–6 个月成本；而 B 的 14–20 人天可以买到「改不同字段不再互相踩」。
