## 4. 判定

**测试隔离缺陷**（跨用例异步残留），不是审计功能的实现缺陷；`≤400/次`、`200/块`、收敛到 `≤1000` 的语义在生产上均成立。
附带一条**真实但轻微**的实现侧观察：缺少 in-flight 单飞 ⇒ 两个裁切可交叠，**一次窗口内的物理删除量可达 600–800（超出「单次 ≤400」的直觉口径）**，且被重复计入的键会让 `audit.entry.evicted.count` **多报**（日志里 `400` 但实际只删了 200）。业务终态仍收敛到 ≤1000/≤90 天，**不影响正确性**，只影响「限幅」这一可观测口径与日志可信度。生产端另有同类残留：`preference-sync.ts:579` 的模块级 `pushTimer`。

1. **B（首选，~10 行）**：`audit-log.ts` 导出**仅供测试/重置**的 `flushAuditPrune(userId?)`：清掉 `pruneTimers` 中的定时器并 **await 在飞裁切**；测试 `resetState` 在**清表之前**调用它。代价：新增一个半公开 API（须加注释「⛔ 生产不用」），要引入一个 `Map<string, Promise<void>>` 记录在飞裁切。
2. **C（同一次改动里做，是真生产改进点）**：调度器加 **in-flight 单飞**（同一 `userId` 在上一次裁切未结束前不再排新的一次；结束后若期间有新写入再补一次）。收益 = 「单次窗口内删除量 ≤400」与 `evicted.count` 不再多报；风险 = 若实现成「丢弃期间的写入触发」会导致淘汰延后（必须在结束后补排，否则极端写入下会滞后）；改动面小、无 schema 影响。
