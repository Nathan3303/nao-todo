## 1. 缺陷机制（两处叠加，症状为"静默漏拉且永不重拉"）

**缺陷 1 — 游标推进用字典序（客户端）**

- 原实现 `applyPullBatch()` 以 `records.reduce((max, res) => ts > max ? ts : max, existing?.lastPullAt ?? '')` 推进 `lastPullAt`（`sync-service.ts:508-514`，**字符串 `>`**）。
- 同一文件的 LWW 判定**早已注明**"远程时间戳可能带 `+08:00` / `Z` 等不同时区后缀，**字典序比较会误判**"（`sync-service.ts:491`）⇒ **游标推进是同一隐患的未修分支**：字面量更大**但瞬时更早**的值会被当成"更晚"，游标错位（既可能跳过未应用行，也可能整段重放）。

**缺陷 2 — 服务端 keyset 为严格 `>`（服务端语义，非缺陷但构成边界风险）**

- `nao-todo-server/infrastructure/utils/query/sync.go:26-36`：`updated_at > ? OR (updated_at = ? AND id > ?)`。
- 当某行 bump 后的 `updated_at` **≤** 客户端已存游标（同秒毫秒级差 / 秒级截断 / 同 ms 且 id 更小），该行被**静默跳过**；而游标"只前进不后退"⇒ 在它再次被更新前**永不重拉**。

**合成症状**：外部 API 直写后触发「立即同步」→ 本地两 store 与行文案仍为旧值、**无任何失败态**（idle / 0 pending），**重载/重启后自愈**（自愈走的是非 pull 路径：`RefreshData` 全量重读）。DB 层裁决（QA，2026-09-11）：外部写 `updated_at` **bump=TRUE**、`PUT 40020` 正常更新 API ⇒ **排除**服务端写路径缺陷（非 DEF-SYNC-04）与"副本刷新覆盖"（非 DEF-STORE-01）⇒ 定位在**立即同步路径的 pull cursor**。

## 2. 决策：**A — 请求游标按瞬时回拉 Δ=1s**

| 要素              | 取值                                                                                                                                                       | 依据                                                                                                                         |
| :---------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------- |
| 回拉量            | `PULL_BACKTRACK_MS = 1000`（`sync-service.ts:231`）                                                                                                        | 覆盖同秒 / ms 级边界与秒级截断                                                                                               |
| 回拉实现          | `rewindIsoCursor(at, deltaMs)`（`:255-264`）：`Date.parse` 取瞬时 → 减 Δ → **按原时区后缀与精度形态**重排字符串（有 ms 保留到 `.sss`，否则截到秒）         | **不得**把 `+08:00` 改写成 `Z`，否则改变服务端解析口径；不可解析 / 无时区后缀 ⇒ **原样返回**（退化＝修复前行为，不冒险改写） |
| 回拉时 `cursorId` | `cursorId: windowAt === cursorAt ? (cursor?.lastPullId ?? '') : ''`（`:415`）——**仅当确实回拉时清空**                                                      | 时间点变了，边界时刻必须**从最小 id 起**；否则同一时刻较低 id 的行仍被跳过                                                   |
| 存储游标          | 仍**只前进不后退**：本批按**瞬时**取 max（`:516-524`），采用服务端 `nextCursor` 仅当 `nextCursorTs >= lastPullTs`（`:530-537`），并同步对齐 `nextCursorId` | 避免边界行每轮重放；防止修复引入新抖动                                                                                       |

**为什么 A 是最小充分修复**：服务端语义**不动**，只在**请求侧**把窗口放宽 Δ，靠 LWW 幂等重放把严格 `>` 漏掉的行补齐；存储游标保持单调。

## 3. 被否方案

| 方案                                                                                          | 否决理由                                                                                                                                                                                                                                                                                                  |
| :-------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B：本地补偿**（拉完后用 `nextCursor` 瞬时与本地各表 `max(updatedAt)` 比对，落后则再拉一轮） | ① **A 是 B 的必要子机制** —— B 的"再拉一轮"仍必须发**更早的游标**，否则同样的严格 `>` 边界仍会漏；② 本地 `max(updatedAt)` 受**客户端时钟**、**未推送写入**、**服务端秒级截断**三重干扰 ⇒ **假阳性**（明明没落后却判定落后）⇒ 违反"Δ 窗口内无重复拉取风暴"回归线；③ 多一轮往返与状态机分支，收益不再优于 A |
| **服务端改 `>=`**                                                                             | **破坏 keyset 分页契约**：同时间戳多行会**每页重复返回**，翻页可能不终止（客户端必须以 `(updatedAt, id)` 二元组前进，`>=` 使其失去严格前进性）                                                                                                                                                            |

## 7. 已知后果与后续观察（**本单不改，留档防误判**）

- 回拉 Δ 窗口会使**窗口内已应用的行被再次 `put()` 并计入 `writtenCount`**（`applyPullBatch` 未入队分支为无条件 `put` + `written += 1`，`sync-service.ts:502-505`）⇒ 理论上**每轮同步可能多触发一次 `notifyDataChanged()`**（视图重拉）。
    - 影响面：**幂等无数据风险**（同 id upsert），仅可能带来**多余刷新**；若实测出现刷新抖动或重拉风暴，可在 `applyPullBatch` 增加"内容未变则跳过写入"或将窗口内已应用行按 `(updatedAt, id)` 过滤 —— **列为后续观察项，不在本单再改**。
- 服务端**秒级截断**场景（若 `updated_at` 精度为秒）仍依赖 Δ 覆盖：Δ=1s 与"同秒边界"等宽，属**恰好覆盖**；若未来出现更宽的模糊窗口，再评估提高 Δ（需同时复核重放成本）。
