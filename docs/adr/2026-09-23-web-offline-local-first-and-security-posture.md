## 3. 约束（C-46…C-66）

> 编号接续 SHELL-06 的 C-45；**C-46…C-66 为本 ADR 新增**（未占用任何既有编号；C-64/C-65/C-66 为 r2 新增）。

### 3.1 明文落盘与姿态

- [ ] **C-46 明文落盘（两端同一姿态）**：业务数据（`tasks`/`taskComments`/`taskCheckItems`/`projects`/`tags`/偏好/番茄）**明文**存 IndexedDB；`cryptoService` **保留为 passthrough 接缝**（`encrypt/decrypt` 直通、`isUnlocked` 语义**必须显式定义**——见 C-62）。**禁止**整体移除 `cryptoService`（迁移窗口内必须保留真解密能力）。**禁止**「半明文」（部分字段加密/部分明文）——与"弱化 KEK"同源，制造虚假安全感。
- [ ] **C-47 `meta` 迁移完成标记**：迁移**全库成功后**才写 `meta` 完成标记；标记存在时**不再走迁移路径**（幂等短路）。**禁止**在部分成功时写标记。

### 3.2 迁移红线（四条，**P0**）

- [ ] **C-48 迁移禁走 `repo.update()`**：迁移**必须直写表**（照 `applyPullBatch` 的 `entityToRecord` + `table.put` 写法），**不得**经仓储写路径 ⇒ 否则整库 `markDirty` ⇒ **推送风暴 + 服务端 LWW 被本地伪修改覆盖**。
- [ ] **C-49 迁移期禁同步**：迁移期间**必须**阻止 `syncService` 的 pull/push（否则 pull 把明文覆盖回密文 ⇒ **永不收敛**）。实现方式与解锁顺序一并设计，**不得**依赖"迁移很快"的时序假设。
- [ ] **C-50 幂等可续跑**：迁移必须可在任意中断点续跑（逐表/逐批进度可判定）；**不得**依赖"一次跑完"。中断后重启**不得**出现混合格式读失败。
- [ ] **C-51 双格式双向读取兜底（P0）**：读取侧必须**同时接受** `plain:<原文>` 与历史密文；`cryptoService.decrypt` **对明文输入不得抛错**（现状 `cipher.split(':')` 会抛"密文格式无效" ⇒ **必须修**）。**`key-bundle` 的删除是唯一不可逆开关**：仅在 C-47 标记写入后允许，**且必须长期保留密码入口**（本仓无遥测）。

### 3.3 登出清库

- [ ] **C-52 按键删除黑白名单（P0）**：登出清库**禁止** `localStorage.clear()`，必须按**键白名单/黑名单**逐键 `removeItem`。**白名单（必留）**：`nao.deviceId`（P2-Z7 实测：误清 ⇒ 设备漂移 + 服务端"同设备覆盖旧会话"失效 ⇒ 会话行膨胀）。**建议保留**（设备级偏好）：`THEME_MODE_KEY` / `LANGUAGE_KEY` / `CALENDAR_WEEK_START_KEY`。**黑名单（必清）**：`USER_JWT_LOCALSTORAGE_KEY`、`USER_PROFILE_CACHE_KEY`、`POMODORO_TIMER_SNAPSHOT_KEY` / `POMODORO_FOCUS_SNAPSHOT_KEY` / `POMODORO_SETTINGS_KEY`、`'USER_CONFIRM_UNRESTORE'`、`getStorageKey(tableId)`/`storageKey` 类（键名完备性见探针 **Z13**）。IndexedDB 侧清 11 业务表 + `meta` + `syncQueue` + `syncCursor`（复用 `deletionService` 既有事务原语）。**⚠️ r5 修订 —— `deletionSchedules` 不在清库范围**：`deletionSchedules` = 「**注销宽限期**」状态 ⇒ **登出 / 切换账号清库必须保留目标用户自己的**（丢了会让用户回来后误以为没申请过注销，从而触发恢复同步）；**仅「注销到期」路径**（`checkAndCleanExpired`）在 `wipeUserData` 返回后**删自己的**调度；**禁清任何其它用户的记录**（含 `deletionSchedules`）。与 PRD **AC5b** 对齐（AC5b 已同批收紧；矛盾源头在 PM 分别采纳 ⇒ **非笔误**）。读码核实 `a8480151`（T106）：`wipeUserData` 事务表集 = `[...BUSINESS_TABLES, 'meta', 'syncQueue', 'syncCursor']`，**不含** `deletionSchedules`。**⚠️ r2 补强**：必须抽出 **`wipeUserData(userId)`** 作**单一真源**，供 **登出 / 注销到期 / 切换账号** 三处共用（依据：`checkAndCleanExpired` 带前置条件——须存在 `deletionSchedules` 且已到期 ⇒ 登出与切换账号**无法直接调用它**）。清库**必须按 `userId` 过滤**（11 业务表 + `meta` + `syncQueue` + `syncCursor`；`deletionSchedules` **不在清库范围**，见上）⇒ **禁**整库清、**禁**清他人记录。
- [ ] **C-53 清库可重入（P0）**：清库前置 `meta.pendingWipe = <userId>`（**单事务**内与清库同提交），启动时若存在该标记则**补清**；清库完成后删除标记。⇒ 崩溃/强杀/掉电后重启**必然收敛**（"登出"是唯一清理触发点 ⇒ **登出的可靠性即安全边界**）。
- [ ] **C-54 脏队列阻塞确认（P0）**：登出前判定"是否有未回传写入"**必须直接调 `syncTracker.countDirty(userId)`**；**禁止**读 `syncStatus.pendingCount`（**DEF-13**：仅在 `endRun()` 刷新 ⇒ 滞后）。`>0` ⇒ **阻塞确认**（显示 N + 「先同步」）；离线且 `>0` ⇒ 二次确认并明示不可恢复。**绝不静默清**。

### 3.4 身份与隔离

- [ ] **C-55 `userId` 硬失败（P0，DEF-9）**：`getCurrentUserId() ?? ''` 兜底**必须移除**；`userId` 为 `null`/空时**拒绝一切库操作**（硬失败 + 可见错误），**不得**退化为"空用户"读写。明文姿态下这是**准入条件**（否则跨用户读到明文）。启动时须从 JWT 重建 `localSession`（web 现无重建点）。
- [ ] **C-62 离线进入判据替换（P0，DEF-16 / K9）**：删除 C-23 条件④；新判据 = **`offlineEntryGranted && JWT 可解析 && localSession.getCurrentUserId() === jwtUserId && 本地镜像存在`**（**两处实现同步改**：`routes.ts` 真守卫 + `offline-prerequisites.ts`）。**必须补正向单测**（现有测试只覆盖 `isUnlocked === false` 的**拒绝**路径 ⇒ 删除后无守护）。若改走"passthrough 仍置位 `isUnlocked`"的备选方案 ⇒ **必须在本 ADR 变更记录中显式声明**，否则离线进入静默失效。

## 4. 威胁模型 + 残余风险接受

### 4.1 安全边界搬迁（一句话）

**从「设备上的本地密码」搬到「浏览器/系统账号 + 设备持有本身」= 「设备即凭据」。**

### 4.2 暴露窗口（量化）

| 端          | 窗口 = 从 → 到                        | 实际长度                                                                                                                                                                                                         |
| :---------- | :------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **desktop** | 登录（建库/落明文）→ **用户主动登出** | **无上界**：应用常驻、**当前未启用单实例锁**；JWT 失效（10041）时 `clearAuthData()` **只清 localStorage、不清 Dexie** ⇒ **明文在 JWT 失效后仍留磁盘**，直到用户登出 ⇒ 以 **C-53（可重入清库）** 作为唯一收敛保证 |
| **web**     | 同上 + 浏览器驱逐                     | 有**随机上界**（**不申请 `persist()`**，作为事实上的过期机制）                                                                                                                                                   |

**关键推论**：**明文数据的存在时间 > JWT 有效期（48h）** ⇒ **真正的边界是「登出」这个动作的可靠性**（崩溃/强杀/掉电未执行完 = 明文长期残留）。⇒ C-53 为**承重约束**。

### 4.3 「无密码」的硬上限（不可绕过）

| 闸                  | 值                                | 说明                                                                          |
| :------------------ | :-------------------------------- | :---------------------------------------------------------------------------- |
| 单次 JWT            | **48h**                           | `ExpOffset` 全仓无赋值点 ⇒ 默认值；**客户端完全不校验 `exp`**，仅响应 10041   |
| 会话（`ExpiredAt`） | **7 天，绝对，不滚动**            | `sessionRepoImpl.go:47` 仅创建时写入；`UpdateToken` 换发**不动** `expired_at` |
| 触发点              | **仅冷启动**（`check-in.vue:37`） | 无周期性 ⇒ **常驻 >48h 必被踢回登录页**（DEF-15）                             |

⇒ **「不弹密码框」的现状硬上限 = 连续 7 天**（前提：每 48h 内至少一次联网冷启动）；**7 天后连 checkin 都失败 ⇒ 只能 `signIn`（需密码）**。⇒ **读法乙（永不弹密码框）在现状服务端语义下不可能达成**；要达成必须改服务端会话模型（滚动续期 / refresh token / 长期会话）⇒ **D-6 明确不做**（K8 已确认）。

| #   | 承载面                                                                            | 依据                                                      |
| :-- | :-------------------------------------------------------------------------------- | :-------------------------------------------------------- |
| ①   | 「待升级」标注 + **一次性迁移入口**（含 C-51 **长期保留的密码入口**）             | AC4 / C-51 / C-56；`unlock-gate.test.ts`（AC2/AC4 例）    |

**保留的硬约束（DEF-16 的真实守护点，写死）**：

- **进入前提不得依赖密码**：三条放行路径（**无 JWT** / **无 `key-bundle`** / **有 `key-bundle` 且迁移完成**）**直接放行**；**不得**出现密码输入闪帧（AC1/AC1b 的「不出现任何密码输入」以此为准）。已读码 + 单测核实。
- **密码仅用于迁移窗口**：`doUnlock` / `onUnlockAndMigrate` 的去向**仅**为未迁移存量用户的迁移路径；**不得**成为通用进入条件。全仓 `isUnlocked` **已无生产门控用途**（仅 `crypto-service.ts:65` 保留 getter）⇒ **DEF-16 已闭合**。
- **`checkAndCleanExpired` 调用点不得回填**：已收敛到 `bootstrapLocalData`（C-61；`AppRoot` 渲染任一门前 await），组件内已加注（读码核实）。
- **C-62 走的是一号方案**（判据替换：web `routes.ts` 真守卫 + `offline-prerequisites.ts` 去条件④）⇒ **未**改 `isUnlocked` 置位 ⇒ C-62「备选方案须在变更记录显式声明」**不触发**。

**若改为真删除（否决，理由留档）**：需 (a) 为迁移门另立宿主（等价搬进 `AppRoot` 或新组件）· (b) 迁移登出接线 · (c) 重建失败终态结构 + 改既有单测 + 改 QA smoke 选择器（`scripts/electron-smoke/**` **10 文件 37 处**依赖 `.nue-container--unlock-gate` / `input[type=password]`）⇒ **净收益为零、回归面为正**，且与 **C-51「长期保留密码入口」互斥**。

### 10.7 护栏 A 裁定（r4）：**保留 wall-clock 语义**

**裁定（2026-09-23）**：**保留 wall-clock（不采用"纯网络耗时预算"）**；默认总预算 **3000ms → 5000ms**；轮数保持 ≤10（读法修正为「**单次运行总轮数**」）。

**理由**：

1. 预算的目的是**用户可见启动阻塞时延** —— `syncService.start()` 跑在**阻塞门**内（`InitialSyncGate` 未通过前不挂载主界面）⇒ **wall-clock 才是该语义的正确度量**。
2. 纯网络预算会让"慢本地处理"**无界**：每表上限 2000 行 × 慢设备（T103 实测 fake-indexeddb + WebCrypto ≈ **10–15ms/行**）≈ **20–30s** 的启动阻塞（单表即如此）⇒ **违背护栏 A 初衷**。
3. 慢环境的真正解法不在预算语义，而在：**(a) 参数化**（`SyncServiceOptions`，T103 已做）**(b) 门后补拉**（T103 已实现：`pullIncomplete` → `scheduleBackfillTick` 不再因 `countDirty===0` 早退 → `resumeBackfill()` 会跑 `pullAllInner()`）⇒ **慢设备在同次会话内补齐**，不再依赖下次启动。

**若仍要网络耗时预算（条件回答，不推荐）**：测点必须**只包** `await this.requester.post('/sync/pull', …)`（`sync-service.ts:519-523`），**不得包含** `applyPullBatch`（本地写入），且必须**跳轮累加**（因预算是总预算）；且需**双闸**（网络预算决定"是否开始下一轮" + wall-clock 硬上限兜底防挂死）⇒ 复杂度上升且**不改善"启动阻塞"目标**。

**实现读法澄清（防后人误判）**：实现为**全局** `rounds`（每轮循环 +1，`rounds >= pullMaxRounds` 即截断，`sync-service.ts:505-513`）；因每轮每表最多前进一页，故与「每表 ≤2000 行」**等价** —— 文档口径统一为「**单次运行总轮数 ≤10（等价于每表 ≤2000 行）**」。

**生产禁放宽**：`SyncServiceOptions` 的注入面**仅限测试**；生产调用点必须使用默认值，否则"启动阻塞上界"失效。

**AC13a 环境限定（必须）**：建议措辞为「**在基准环境**（真实浏览器/Electron IndexedDB，或测试中以**注入的充足预算**运行）下，>200 行（无墓碑压力）账号**启动 1 次** ⇒ 本地拉满且含最新」；**慢环境**允许落 **AC13b** 分支，但**必须在门后补齐窗口内最终拉满**（建议将"最终拉满"写进 AC13b 的 Then）。

**待实测校准（新增 Z20）**：真实设备（Electron + 真 IndexedDB）**620 行账号首启动**的耗时分解（网络 RTT vs 本地落库）⇒ 用于定稿默认预算值。

**否决 PM 倾向中的 desktop 半**（PM ①「离线路径只读（**两端**）」）：desktop **离线写保留**。理由：

1. **零新风险原则**（PM 自己的理由 #1，须同样适用于离线半）：desktop 离线写 = 本地入队 + SHELL-06 回传，**既有且实测可用**（探针 §3.2-A：写本地成功并入队，判定「**不构成误判已保存**」）；阶段一**未改变**该路径（不碰仓储、不碰队列、不碰推送语义）⇒ 禁写 = **纯回归**，换不到任何新收益。
2. **阶段二会再翻回来**：非范围①「写路径切本地 + 回传队列 + 多标签协调 + LWW」正是**把 web 提升到 desktop 现状** ⇒ 阶段一禁掉 desktop 离线写、阶段二再启用 = 无谓开关往返，并放大阶段二回归面。
3. **LWW 豁免换不到**：desktop **在线**写同样产生 `markDirty`（写本地 + 入队 + push）⇒ 「`syncQueue` 恒空」**在任何读法下都不成立**（recon §7-10 / §T3 的豁免前提有误）⇒ 禁 desktop **离线**写并不能使豁免成立；豁免只能重新表述为「**不新增写路径**」（已入 C-59 r5）。
4. **两端不可类比**：拦 web 离线写 = 用户可见但**无能力损失**（本来也会失败/丢）；拦 desktop 离线写 = **真实能力损失**。
5. **与本 ADR 其它条款一致**：D-4 已写「**写路径切换属阶段二**」（= desktop 写路径本就无需切换）；§10.1 人天行亦只列「**禁写开关覆盖 web**」。

**因此 C-59 原文两处措辞被判定为「作用域过宽」并已修订**：①「阶段一为**只读**」⇒「阶段一**新增的离线数据面**为只读」；②「**任何**写路径都不得入队 + desktop 必须在 UI 层统一禁写」⇒「**不得新增**本地写路径；**web 恒 0**」。

**待 PM 拍板（U-7，不阻塞开工）**：若 PM 仍要 **uniform**（desktop 离线也临时禁写，换取单一可验证不变量），则 ① **须用户显式知情**（用户可见能力收缩：桌面端离线将不能编辑任务）；② 本 ADR 追加一行修订（仅改 C-59 的 desktop 半句 + AC10 分端口径）。arch 推荐 = **保持本裁定（desktop 写路径不变）**。

**r5.1 补记（PM 补定 + arch 技术约束）**：web「离线进入」flag 的**解除条件**（**本会话真实成功同步后清除**）与 4 条技术约束见 **C-59 末条**；关键点 = **不得**用 `runResult.ok` / `lastSyncAt` 反推「会话已确认」—— 注销宽限期与 `!userId` 的**空运行也报 `ok=true`**（已读码确认）。
