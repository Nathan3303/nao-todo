# ADR：数据库故障不是凭证失效（`DEF-143` 修法形态）

- 状态：已接受（待落地）
- 更新：2026-11-10
- Owner：arch-designer（`T673`）
- 指针：`docs/reports/T673-def143-fix-verdict.md` · `docs/reports/667-def143-repro-and-criteria.md`（AC-1…AC-13）· `docs/reports/defect-pool.md`（`DEF-143` / `DEF-152`）

## 背景

- 2026-11-06 生产 MySQL 被手动重启、不可用约 4.5 分钟 ⇒ 会话查询的 DB/连接错误被仓库层吞成「零值会话实体」⇒ 域层判「会话无效」⇒ 鉴权中间件统一回 `10041`（HTTP 200）⇒ 客户端按凭证失效清认证并跳登录页：**所有在线用户被踢**，同期 **0×5xx、访问日志全 200、无告警**。
- 本机复现已成立：停库 58s 内 6/6 请求 = `200 + 10041`，服务端仅一行 `warning`，与真实凭证失效**响应体逐字节相同** ⇒ 客户端无从区分。
- 同场景伴生安全缺陷 `DEF-152`：gorm 默认语句日志把 `user_sessions.token` 的**完整 JWT 明文**写入日志。
- AC-2（码型）与 AC-11（是否加客户端二次确认）待架构定稿，是本次决策范围。

## 决策

1. **DB/连接等依赖类错误一律映射 HTTP `503`**，响应体保留项目信封 `{"code":50300,"message":"服务暂时不可用，请稍后重试"}`；**不得**再映射为 `10041`。
2. **凭证语义只由显式哨兵触发**：仅「JWT 解析失败 / JWT 过期 / 会话不存在或无效」回 `200 + 10041`；**其余一切错误（含未知）回 503**（fail-safe：宁可少登出，不误登出）。
3. **不加客户端二次确认**（AC-11 判为不适用）：防线放在服务端语义，而非客户端计数。
4. 可观测性以「结构化事件 + 访问日志 5xx」落地：`auth.session_lookup_failed`（error）、`auth.credential_rejected`（warn）；**`DEF-152` 同批修**（gorm 参数化，日志不含 token 明文）。

## 理由

1. 业务匹配：用户可感知的失败模式是「被强制重登」，而它对用户没有任何可解释性 ⇒ 破坏性动作（清凭证/跳登录/撤离线授权）必须只由**显式证据**触发。
2. 技术成熟度：`503` 是 HTTP 既有语义（RFC 9110 §15.6.4）；客户端三端**现有分类学已经按状态码分流**（推送失败三分类把 `>=500` 判为 `network` ⇒ 服务级暂停、不消耗队列重试额度、不丢 pending），无需发明新码。
3. 团队能力/可观测性：访问日志对 `>=500` 本就记 `error` 级并带 `status`，5xx 面板是现成设施；`200 + 业务码` 会让故障继续不可见——正是本次事故的根因形态。
4. 成本：映射点全仓只有一处（鉴权中间件），改动集中在「上抛 + 分类」而非重写链路；**移动端零改动**（其请求器不看状态码、只对凭证码触发登出），无 DB 迁移，无新依赖；故障期重试放大风险可用既有退避约束。

## 对照过的备选模式

1. **维持现状（DB 错折叠成 `10041`）** —— 适用：无（基线）；代价：全员强制重登 + 静默无告警，且触发源反而更常见（人工/计划性重启必然触发）；不采纳。
2. **HTTP 503 + `code=50300`（采纳）** —— 适用：多客户端族、依赖抖动频繁、监控只认状态码；代价：axios 系会把 5xx 抛成错误（身份域个别页面观感，列为 P3 硬化）；采纳。
3. **HTTP 200 + 专用业务码 `9002x`（不采纳）** —— 适用：单客户端、无告警诉求、要求零抛错；代价：`9002x` 已是 `/sync` 业务码族（语义撞车）；**新增业务码在客户端检入路径属 fail-closed ⇒ 会清认证**（正是要消灭的后果）；监控仍为 200 静默；需教三端新码且移动端不可改；不采纳。
4. **鉴权缓存 fail-open（DB 不可用时用 Redis 会话缓存放行）** —— 适用：可用性优先级高于撤销时效；代价：现有缓存只缓存「有效」且仅服务于 SSE 校验，启用它等于**变更认证安全姿态**（被撤销/被顶号会话可在窗口内继续可用），且缓存与本缺陷同源故障时退化不可控；本批不采纳，如需另立 ADR。
5. **客户端二次确认（连续 2 次 `10041` 才清认证）** —— 适用：服务端无法区分故障与真失效；代价：客户端**没有可用的区分证据**（响应体逐字节相同），计数只是代理指标；与「真失效零回归」的既有用例直接冲突；须落三端共用的请求器层并牵动移动端验证面；不采纳，未来若做应为「被动 10041 ⇒ 主动取证一次」，而非本地阈值。
6. **把 `10041` 从客户端凭证集合移除** —— 适用：无；代价：真失效后永不登出、待推送数据永久堆积；不采纳。

## 后果与风险

- 正面：基础设施抖动不再清认证；故障首次具备「可数、可告警、可区分」的信号（状态码 + 结构化事件）；`DEF-152` 的凭证经日志泄漏一并关闭。
- 负面（明示）：① 故障窗口内客户端会持续重试（推送 5s→120s 服务级暂停、拉取 5s tick），`/sync` 限流桶按 IP 计（24/min，挂在鉴权之前）⇒ 同 IP 多端并发可能先撞 `10051`（非凭证类、不清认证），属既有口径被新重试行为暴露；② gorm 参数化后慢查询日志不再含绑定值，排障需靠 `request_id` 关联；③ 未知错误改判 503 意味着「未被列入哨兵的凭证失败」会表现为可重试错误，需靠告警（`auth.credential_rejected` 峰值）兜住。
- 控制措施：`10041` 分支新增 warn 事件（使「被折叠成凭证失败」的问句可被直接计数）；本文与报告同批更新缺陷池与发版说明。

## 限制与已知边界

- 仅覆盖「鉴权依赖失败」路径；`CheckIn` 的 `10022`（检入冲突）语义不在本决策范围（如需一致，另加「依赖失败 ⇒ 503」两行）。
- SSE 侧的会话校验同样吞 DB 错误（返回无效），当前 SSE 无客户端消费者，不在本批。
- 不含客户端身份域「抛出型 5xx 的观感硬化」（P3，另卡）。
- 不含故障期退避下限调整；若 `10051` 干扰验收，另卡评估。
- 移动端（红线）与 `packages/presentation-react`、`apps/mobile` 零改动，本决策不改变其任何行为预期。
