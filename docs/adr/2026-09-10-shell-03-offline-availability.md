## 2. 裁决记录

### D-1 / Q1：离线终态设计 = **"门/壳必须是总函数"+ 就绪判据与展示数据解耦**

**统一原则（4 条，写入约束）**

1. **终态完备性**：任何阻塞式门/壳（首屏、路由级、应用级）必须在**有限时间内进入且仅进入一个显式终态** ∈ {loading, ready, empty, error}；模板链必须**显式穷尽**（`v-else` 兜底），**禁止"无匹配分支 ⇒ 渲染空"**。
2. **兜底可前进**：error/empty 终态必须至少含一个前进动作；**任何失败态都必须同时提供"重试"与"登出/重新登录"**（消除"无逃生入口"整类问题）。
3. **就绪判据分层**：
    - **本地判据**（权威放行依据）= `resolveUserIdFromStoredJwt()` + `cryptoService.hasKeyBundle()` + 本地库可用性 → **亚秒级**，决定"能否进入下一步"；
    - **网络装饰数据**（`profile`/`config`/主题远端值）→ **永不作为门/壳的就绪或渲染条件**，异步加载、失败静默、缺失用占位。
4. **失败分类**：门必须区分"网络不可用/后端不可达"与"业务错误（401/403/10041、数据非法）"——前者出路是**重试 / 离线进入**，后者出路是**重新登录 / 重试**。

**profile 缺失策略（PM 直问）**：**允许无 profile 进入解锁界面**。理由：解锁所需全部要素在本地（JWT + 密钥包 + 用户密码），当前把 profile 当就绪条件属**把装饰数据升格为阻塞条件**的错误耦合。解锁界面头部改为"profile 有则渲染真值、无则渲染占位（默认头像 + 账号/邮箱占位）"。

**离线进入主界面**：**裁决为允许（并属本单最小范围）**，因为桌面端本就是"本地加密存储 + 增量同步"的离线优先架构（§1.2）。落地口径：

- 解锁门：本地判据通过即可解锁（离线可解锁，`cryptoService.unlock` 为本地运算）；
- 初始同步门：失败终态提供 **重试 / 离线进入**（离线进入 = 以本地数据继续） ；
- 壳：无论 profile 有无**始终渲染**（见 F-6 修复），身份区域降级为占位；
- **不在本轮**：离线专属提示 UI、"离线可写"的边界口径（冲突/上限/回传可见性）→ §8 遗留登记。

**约束 + 同类扫描**：新增约束"门/壳兜底分支必须有（且可前进）"；扫描结果见 §7（4 类组件 + 1 处潜在空渲染）。

### D-2 / Q2：`lastError` 语义 = **运行级聚合 + 运行边界不可变契约**

**裁决**：`SyncStatus` 引入显式**运行（run）生命周期**，阶段只"上报"，只有运行边界能"落定"：

| 规则                         | 定义                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| :--------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **R1（聚合）**               | 一次运行内任一阶段失败 → 运行结束时失败仍可见（阶段中途不得清空）                                                                                                                                                                                                                                                                                                                                                                                    |
| **R2（清空时机）**           | 全局失败信息**仅在一次新运行开始时**清空（`beginRun`）；阶段方法不得清空                                                                                                                                                                                                                                                                                                                                                                             |
| **R4（初始门不依赖全局态）** | 门以**运行返回值**判成败；全局态仅供展示                                                                                                                                                                                                                                                                                                                                                                                                             |
| **R3（聚合口径，本轮拍定）** | ① `lastError` = 本次运行**按执行序首个**阶段错误（pull 先于 push；两阶段皆失败时取"拉取失败…"，因其更接近离线根因）；② 同时保留**保序去重**的 `errors: string[]` 与 `errorCount`（多阶段失败可计数）；③ 本轮 UI 仍只展示单条 `lastError`，**"等 N 项"文案与 i18n 化一并遗留**（避免半吊子 i18n，见 Q4）；④ 无错误 ⇒ `lastError=null`；⑤ `lastSyncAt` **仅在运行无错误时推进**（修正 DEF-SYNC-03）；⑥ `pendingCount/failedCount` 在运行结束时刷新一次 |

**接口契约（字段级，供 RD 直接落地）**

```ts
type SyncPhase = 'pull' | 'push'
interface SyncRunResult { ok: boolean; errors: string[]; lastError: string | null; phase: SyncPhase | null }

// SyncStatus 新增/调整（内存态，不改同步协议/表结构）
beginRun(phase: SyncPhase): void          // syncing=true；运行序号 +1；**仅此处**清空累积错误
noteRunError(phase: SyncPhase, msg: string): void   // 阶段上报（保序去重）
endRun(): SyncRunResult                   // syncing=false；落定 lastError/errors/errorCount；
                                          // ok 时推进 lastSyncAt；顺带刷新 pending/failed 计数
get(): SyncStatusState                    // 新增字段：errors、errorCount、runningPhase（**当前执行阶段**，非入口阶段；无运行=null）
```

**实现约束（消缺陷）**

- **C-08**：所有入口（`start()`、`manualSync()`、公开的 `pullAll()/pushAll()`、`schedulePush()`）统一形态 `beginRun → try { 阶段… } finally { endRun }`；**禁止任何 return 路径绕过结束**（消除 DEF-SYNC-02）；`markSyncing()` 视为废弃（保留为 `beginRun` 的兼容别名或直接删除，二选一并留痕）。
- **C-09**：阶段内部**不得**直接调 `markSynced`/写 `lastError`（改为 `noteRunError` + 由 `endRun` 落定）。
- **C-10**：`start()`/`manualSync()` 返回 `SyncRunResult`；`initial-sync-gate` 以返回值判成败（R4），并**删除**其 `syncStatus.markSyncing()` 调用。
- **C-11**：`lastSyncAt` 语义修正后，`sync-status-bar` 文案"同步 HH:mm"含义变为"上次**成功**同步"（与其字段文档一致），属**修正**而非改版。

**兼容性**：字段类型不改（`syncing: boolean`、`lastError: string|null`）；新增字段为只增；`markSynced` 若保留需明确"仅 endRun 调用"。现有 `sync.test.ts` 三处 `syncStatus.get()` 断言均为**阶段级直接调用**（`service.pullAll()` / `service.pushAll()`），在"隐式运行"语义下仍应通过（阶段级失败仍写 `lastError`、结束时 `syncing=false`）——**RD 必须在实现后确认这三处不回归**。

### D-3 / Q3：失败可见性 vs 用户体验（两个门的终态规范）

| 门                                | 终态矩阵                                                                                                                                   | 前进动作                                                                               |
| :-------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **UnlockGate**                    | ① `checking`（本地检查，≤2s）② `ready`（可解锁；profile 有则真值、无则占位）③ `error`（**本地**失败：本地库/密钥包读取异常、JWT 解析异常） | ready：解锁 + 登出（**恒在**）；error：**重试** + **登出/重新登录**（清 JWT 回登录页） |

- 失败信息展示：沿用 `LoadingError` 的 error 分支；文案用 `lastError`（本轮硬编码中文，见 Q4）；**禁止**把原始异常/URL 直接渲染（`String(err)` 泄漏面，与 SHELL-02「lastError 禁 v-html/摘要播报」同源纪律）。
- `AppRoot` 的 `initialSynced` 语义应理解为"**门已通过**"（成功或用户选择离线进入），建议实现时更名或加注释，避免"synced"字样误导后续维护者。

### D-6 / D2（r2 补正）：离线身份呈现 = **有条件可行（采纳用户改选的 B'）**

**用户拍板（2026-09-10，改选）**：D2 = **B'**——**本地缓存昵称**；离线时用**昵称首字母头像（色块 + 字母）**而非通用小人图标，并同时提供「离线」小字兜底。用户理由：通用图标会让人疑惑"这是谁/是不是坏了"。

**架构裁决：与 r1 D2 条目下的"隐私面变更"顾虑相容（有条件可行）**，理由（逐条对照）：

| 顾虑         | 评估                                                                                                                           | 结论                   |
| :----------- | :----------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| 新增持久化面 | 仅新增**一个**白名单记录 `{ userId, nickname, cachedAt }`（C-15），**不含** email、不含头像 URL/字节、不含整对象               | 增量可度量、可审计     |
| 明文存储     | 该介质本就是明文（`USER_JWT_LOCALSTORAGE_KEY='USER_JWT'` 亦是明文，`domain-identity/src/domain/constants.ts:2`）；缓存与之间级 | 同级风险，不构成新等级 |
| 身份可辨识性 | 缓存**不得**作为鉴权/登录依据（C-19），仅作呈现降级；解锁仍必经密钥包 + 密码                                                   | 不削弱安全边界         |
| 可清除性     | 登出 / 切换用户 / 注销清理（`deletionService.checkAndCleanExpired` 路径）/ 解析失败均可清除（C-16）；userId 不匹配即无效       | 不会残留脏身份         |

> 若后续把白名单扩到 email / 头像字节 / 任何可鉴权信息，本裁决**自动失效**，需重新评审（写入 §8 变更管理）。

**落地形态（已核实的复用点，零新盒子组件）**：`NueAvatar` 在**两版**（1.11.0 / 1.10.58）均实现了 `default` slot 分支（`src && !imgError ? <img> : $slots.default ? 渲染插槽 : icon`）——1.11：`avatar-a9VhoLN8.js`；1.10.58：`avatar.DE9RQfmG.js`。⇒

- 有昵称（缓存或在线 profile）→ 提供 `default` slot 渲染**首字母 + 主题色块**；
- **无头像 URL 或图片加载失败**（离线时头像请求必然失败）→ 自动落到 `default` slot ⇒ **天然得到离线首字母**，不需额外分支；
- 无昵称且无缓存 → **不提供** `default` slot → `NueAvatar` 自行回落 `icon="user"`（符合 C-16 末条）；
- 该复用仍在 SHELL-02 的「两版行为等价子集」内（`NueAvatar` 两版同 API、同分支）。

**呈现落位（避免两套首字母规则漂移）**：首字母规则/色块推导作为**单一来源**放在 `@nao-todo/presentation-identity`（解锁门与 webapp 轨道均已依赖该包，无需新增跨包边）；UI 需要独立组件时落 `packages/presentation-identity/src/components/`（与既有 `avatar-updater/avatar-cropper/avatar-viewer` 同层）。

**「离线」小字的位置裁决（按面裁量，不强制一致）**：

- **解锁门**（有横向空间）→ 显式「离线」小字（i18n 键）；
- **轨道 70px 宽**（`aside-v2.css:11-13`）→ **不放可见小字**（会把轨道撑破/压迫图标），改用 `title` + `aria-label`（i18n）承载"昵称（离线）"语义；
- 两面的**身份图形呈现（首字母/色块）必须一致**，差异仅在文案承载方式。

## 附录 A（r3）：T0 语义确认（RD 提报，架构背书/否决）

**A-1 / Q2：`SyncRunResult.phase` = 首个错误的阶段；`runningPhase` 不用“入口阶段”语义**

- `SyncRunResult.phase`：**背书**——取首个错误的阶段（与 R3 “执行序首错”一致）；无错误 = `null`。
- `runningPhase`：**否决“入口阶段”语义**（名实不符：`start()` 运行中阶段会由 pull→push 切换，“入口阶段”会让面板永远显示“正在拉取”）。改为**当前执行阶段**（每次阶段开始时更新，无运行 = `null`）；**不新增 `entryPhase`**（无消费者）。若 RD 认为无人消费，**直接删除该字段**亦可（不反对）。

**A-2 / Q3：“未确认实体”计入运行错误 ⇒ `ok=false`：确认**

- 理由采纳（部分推送失败不得 `ok=true`，否则初始门假成功，与 R4/BC-6 冲突；`failedCount` 仅影响面板计数，不参与门判据）。文案 `推送失败：部分数据未确认` **属 C-12 family（`推送失败：` 前缀，无异常/URL）**，无需新口径。
- 补两条实现约束：① **同一阶段同类错误只 `noteRunError` 一次**（不得在逐实体循环里上报，防 `errors[]` 膨胀）；② 该分支**不得**改变“已确认项已清理、未确认项 `markFailed`”的现有队列语义（仅新增错误上报）。

**A-3 / Q4：超限早退（`pushBody`/`deletions` 皆空）必须 `noteRunError` 以满 BC-6：确认**

- 文案 `推送失败：重试次数已达上限` **采纳**（可诊断性优先；family 前缀合规）——**不**复用“网络错误”（归因不准，会误导排查）。
- 补充：早退的第二类原因 `!config`（`SYNC_TABLES` 查不到）属**不可达防御分支**（与写队列同常量源）→ 仅 `console.error` 诊断，**并入同阶段同一错误上报**（不新造文案、不重复计数）。
- **接受的副作用**（登记遗留）：`retryCount` 无重置路径 ⇒ 永久超限项的设备将在**每次冷启动**均停在 `failed`（可选择“离线进入”）；“超限后的恢复/提示口径”属 §6-2 离线写入边界遗留项，本单不做。

**A-4 / Q5：否决在 `persistence-go`（远端适配器）写本地缓存；改装配层单点**

- **否决理由**：① 适配器→适配器（跨端口）依赖，破坏 ports-adapters；② 在**读路径**（`getProfile`）产生**写副作用**；③ 远端适配器承担“离线呈现”这一非其职责的关注点；④ 实测 `persistence-go/` 当前**零** `persistence-local` 引用——属**新引入**的反模式，无先例；⑤ `scripts/guard-domain-isolation.mjs` 只查 domain-* 的 `@nao-todo/shared` 根桶导入与 `ResponseDataPagination` 命名，**不会拦此类跳边依赖** ⇒ 不能依赖守卫。

    - **存储适配器**落 `packages/infrastructure/src/persistence-local/`（localStorage 实现 + 经 infrastructure 桶导出）——它本就是本地持久化适配器；**读取**由 presentation 调用（既有先例：`unlock-gate.vue` 直接 import infrastructure）；

## 附录 B（r4）：离线进入的路由语义与 auth 守卫判据（BC-5 缺口裁定）

**缺口确认**：r1–r3 只写了“允许离线进入主界面”，但**未定义其路由语义与守卫判据**；而轨道活在 **index 路由的视图内**——路由不在 index，壳永不挂载。QA 实测（离线冷启动 → 解锁门 ✓ → 同步失败态 ✓（BC-3/BC-4）→ 点「离线进入」→ 1s 内跳 `#/auth/signin` 并持 8s+，`railSlot/gear/railBtn` 全 false ⇒ **BC-5 三条 FAIL**）证实该缺口。

**根因链（三处，已复核）**

1. `apps/web/src/views/auth/routes.ts:31-43` `beforeEnter`（**仅**挂在 index 路由：`router.ts:14`）在 `jwt!==null && !isAuthenticated` 时重定向 `auth-checkin`；离线时 profile 拿不到 ⇒ `isAuthenticated` 恒 false ⇒ boot 即被推入 checkin。
2. `apps/desktop/.../initial-sync-gate.vue:52-54` `onEnterOffline()` 只 `emit('synced')`，**不改路由** ⇒ `<App/>` 挂载到“当前路由 = /auth/checkin”。
3. `packages/presentation-identity/src/components/check-in.vue:20-21`：checkIn 失败 ⇒ `NueMessage.error` + `router.replace('/auth/signin')` ⇒ 登录页死路（且为**异步竞态**：其失败 promise 可在用户已离开 checkin 后才回弹）。

### B-1 / Q1 路由语义与归属

- **归属裁定：路由跳转唯一点 = AppRoot**（shell 路由决策唯一归属；先例：`AppRoot` 已有 session-expiry → `router.replace('/auth/signin')`）。**`InitialSyncGate` 只呈现意图**（拆 emit：`synced` 成功 / `offline` 离线进入），**不得 import router**，避免“两处都改”。
- **顺序（硬）**：`grantOfflineEntry()` → `await router.replace(LAST_VISITED_ROUTE_KEY || '/tasks')` → `initialSynced = true`。**必须等 replace 完成再挂 `<App/>`**，否则会短暂挂载 checkin 并触发其失败分支。
- **目标路由**：`LAST_VISITED_ROUTE_KEY || '/tasks'`（与 `index-view.ts` 的 check-in 成功路径一致；`router.afterEach` 只在非 `/auth` 路由写入 ⇒ 该值不可能是 `/auth/*`）。
- **同源修正（同缺陷类）**：`onSignOut` 现也仅 `emit('synced')`，靠“checkin 失败顺带跳转”落地 ⇒ 改为 AppRoot 显式 `router.replace('/auth/signin')`。

### B-2 / Q2 auth 守卫判据（可实现、不放宽）

```
allowOfflineEntry =
     offlineEntryGranted                                    // ① 用户显式动作（会话内）
  && resolveUserIdFromStoredJwt() !== null                  // ② JWT 存在且可解析出 userId
  && localSession.getCurrentUserId() === jwtUserId           // ③ 内存会话与 JWT 同一用户（解锁门已置位）
  && cryptoService.isUnlocked === true                       // ④ 本地保险库已解锁（= 用户已输入密码）
```

- **放置**：`views/auth/routes.ts` 的 `beforeEnter` **最前面**（该守卫仅挂 index 路由，已核）；四条件任一不满足 ⇒ 落回现有三分支 ⇒ **在线且 token 无效仍必须走 signin/checkin**。
- **禁用项（防“看情况放行”）**：**不得**用 `navigator.onLine`（Electron 在“网通但服务端不可达”时仍为 true，不可靠）；**不得**用昵称缓存（C-19 明文：缓存不得参予鉴权/守卫）。
- **安全论证（为何不算放宽）**：① 门槛 = “凭证存在 + 用户掌握本地保险库密码 + 用户显式选择降级”，**无任何自动放行**；② 服务器资源**从不信任**该 flag：任何带凭证请求仍由服务端裁决，且 `10041` 三处兜底（`main.ts onAuthExpired`、`AppRoot` session-expired 监听、`sync-service` 10041 分支）在**下一个请求**即清认证并跳 signin；③ 可达范围仅**本地已加密数据**（其门槛本就是本地密码）；④ **凭证类失败不得授予**（C-23）。
- **flag 生命周期（硬）**：登录/检入成功、`clearAuthData()`、10041 会话失效、登出 → **必须清**。
- **残留（登记遗留，不扩范围）**：离线进入后同一会话内不再做在线校验（依赖 10041 兜底 + 下次同步）；“网络恢复后自动重新校验（re-checkin）”另立单。

### B-3 / Q3 check-in 失败分支

- **不需要**区分“自动重定向进入 / 用户主动进入”，**不引入** query 标记；两条判据足够：
    1. **路由判据（硬）**：失败处理前先判 `router.currentRoute.value.name !== 'auth-checkin'` ⇒ **静默 return**（不弹错、不跳转）——消除“离线进入后被旧 promise 拖回 signin”的竞态。
    2. **失败分类（硬）**：**网络类**（`ERR_NETWORK`/超时/5xx）⇒ **不得** `replace('/auth/signin')`（离线必败 = 死路），改为**可重试失败态**（现仅 loading，需补最小重试 UI——符合 C-02）；**凭证类**（401/403/10041/invalid）⇒ `replace('/auth/signin')` **保持**。
- 结果：check-in 作为阻塞式门，自此也纳入 C-01/C-02 的终态完备性（此前它只有 loading + 失败跳转）。

**(b) 启动期请求来源分类**（供 QA/后人判读，均为 INFO）：
