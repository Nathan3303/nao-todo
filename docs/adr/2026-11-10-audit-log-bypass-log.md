# ADR：变更审计日志（旁路追加 / 本机有界 / 不参与裁决）

- 状态：已接受（待落地，目标 `v1.20.0`）
- 更新：2026-11-10
- Owner：arch-designer（`T696`）
- 指针：`docs/prds/2026-11-10-audit-log.md`（Issue #346）· `docs/reports/T696-audit-log-arch-review.md`（11 问 11 答 / 文件级落点 / 工期 / 建议 AC 增补）· `docs/adr/2026-11-03-sync-conflict-journal-crypto.md`（`R-H` 快照最小化）· `docs/adr/2026-11-10-field-level-merge.md`（`fieldBase` 形状教训）· `docs/reports/671-diff-field-conflict-verdict.md`（四条改写链路）

## 背景

- 任务表只存当前值，`conflict-journal` 只记**冲突败方**且上限 200 环形淘汰 ⇒ 「非冲突的正常修改」「被挤掉的冲突」「删除/归档前的原样」全部无痕；用户报障只能靠临时探针重建现场。
- 同一任务可由 `local-edit` / `pull` / `push-merge` / `conflict-retry` 四条链路改写（`T671` 实测），今天无法回溯是**哪条链路**改的。
- 硬约束：旁路（不参与裁决）、零网络往返、失败不阻断业务写、本机有界（≤1000 条 / 90 天 / ≤2 MB）、移动端零改动。
- 本档是「Agent 接入层（写权限）」的前置：没有可追溯的写入，Agent 写入不可信。

## 决策

1. **形态 = 同库新表 `auditLogs`（Dexie `version(5)`，只增表、不改既有表）**，主键 `++seq`（自增插入序），索引 `userId` / `[userId+entity+entityId]` / `[userId+at]`。
2. **判据 = 「落库前后本地行是否真的变了」**：`pickChangedFields(写前实体, 写后实体)` 非空才记 1 条；⛔ 不按「调用了一次 `put`」判定（这就是 `DEF-147` 陷阱）。实体层取值（同步边界明文），⛔ 不落记录层 `plain:` 形状。
3. **写入 = 业务事务提交后的旁路 `add`**（不参与业务事务、失败只 `logStructured`），一次业务写 ⇒ 1 条；批量写按**实体**计数（N 个实体 = N 条，每条只出现在自己实体的历史里）。
4. **来源四值固定**（`local-edit` / `pull` / `push-merge` / `conflict-retry`），**首版不引入 `deviceId`**：审计日志纯本机旁路，写者恒为本机 ⇒ 设备标识同义反复。
5. **有界 = 条数 1000 / 保留 90 天 / 单条字节预算**，裁切走「追加后单飞（single-flight）异步裁切 + 启动裁切」，不阻塞保存路径。

## 理由

1. 业务匹配：用户的编辑单元是「字段」，可追溯的最小单元也应是「字段级 diff + 来源」，而不是整行快照；来源二元（本机 / 云端）已覆盖 PRD 场景 1–3 的全部可回答面。
2. 技术成熟度：append-only 事件表 + 保留策略是有审计需求的系统的成熟解法（写侧只追加、读侧按键序分页、保留靠后台裁切），不需要事件溯源的重型机制。
3. 兼容性：`version(5)` 只增表 ⇒ 老库升级是 Dexie 的空升级（建表、无数据搬迁），既有 4 个版本的表结构零改动；Dexie 4.4.x 对「旧代码打开新版本库」会静默适配（见参考来源 1）⇒ 回滚不再是「库打不开」的硬故障。
4. 成本：无服务端改动、无网络、无新依赖；主要成本在**写入点接线**（4 类来源）与**防假刷屏的判据**，不在存储。

## 对照过的备选模式

1. **维持现状（不记 / 只靠 `conflict-journal`）** —— 适用：单端使用、不追求可追溯；代价：非冲突修改永久无痕、冲突条目还会被挤掉（200 上限），Agent 写入不可信；**不采纳**（PRD 指标 1 直接不满足）。
2. **同库新表 + Dexie `version(5)`（采纳）** —— 适用：需要索引支撑「按实体取最近 N 条」与「按 `userId+at` 淘汰」、写侧只追加；代价：IDB 原生版本 +1（**回滚不再等于「清表」**，见后果与风险）、`BUSINESS_TABLES` 不得改动（另有语义）；**采纳**。
3. **独立第二库（`nao-todo-audit`，零版本变更）** —— 适用：把「回滚即整库删除」当硬需求、可接受第二连接与清库链路 +1 处；代价：跨库无事务（审计与业务写天然非原子，但 PRD 允许「紧随其后」）、`wipeUserData` / 离线门 / 冷启动都要多一处、桌面与 Web 的配额各自分账、测试要维护两个 DB 句柄；**不采纳**（为守住「回滚只是清表」而引入长期双库成本，收益不对称；Dexie 4.4.x 已消除降级硬故障）。
4. **`meta` 单记录数组（`conflictJournal` 同型，零版本变更）** —— 适用：条目少（≤数百）、可接受每次写 RMW 整块；代价：每次写都要读-改-写整块（1000 条量级 ≈ 数百 KB）、需要仿 `withJournalRmw` 的跨路径锁、**无法走索引**取「按实体最近 N 条」（只能全量反序列化后内存过滤）；**不采纳**（`journal` 的 200 条上限正是这套形态的容量天花板）。
5. **服务端审计表 / 上报** —— 适用：需要跨端 actor 归属、合规留存；代价：契约变更 + 新表 + 隐私面扩大 + 跨仓发布耦合；**不采纳**（PRD 明确非范围；重评触发点见 PRD §九）。
6. **复用 `conflict-journal` 表** —— 适用：想省一张表；代价：两者**用途与淘汰策略互斥**（journal = 待处理的冲突败方、优先级淘汰；审计 = 已发生的变更、时间淘汰）⇒ 混表必然出现「审计被冲突挤掉」或「冲突被时间清走」；**不采纳**（PRD 已列非范围）。

## 后果与风险

- 正面：任一 `tasks` 变更（本机或云端）1 条可查；字段级 diff + 来源 + 时间可直接回答 PRD 场景 1–4；冲突面板不必扩面即可解释「这条不是我改的」。
- 风险与处置：
    1. **假刷屏（最大陷阱）** —— `DEF-147` 每轮 pull 会重写回拉窗口内的未变化行；若按调用计数记账，30s 一次的自刷新会持续产出空审计。处置 = 判据只看「落库前后本地行是否真的变了」，且**记录层预筛 + 实体层精筛**两级（见评审 Q3）；另有一个**现成假阳性源**：`tasks.projectId` 的收集箱桶映射（本地 `'inbox'` ↔ 服务端隐式桶 `userId`），必须归一后再比。两者都要有用例锁死。
    2. **回滚语义被 PRD 写错** —— PRD「回滚 = 整表清除即可」在本决策下**不完整**：清表可清数据，但 IDB 原生版本已 +1；旧代码重开需依赖 Dexie 4.x 的降级适配（本项目 `dexie@4.4.5`）。处置 = 发布说明写两段式回滚（① 关闭写入开关/清表 ② 必要时降级到带 `version(5)` 声明的构建），并把「降级可开库」写成自动化用例（伪 IndexedDB）。
    3. **写入放大** —— 批量路径（清单归档级联、批量删除、批量编辑）是 N 实体 × 1 条；单次批量 200 条会一次写 200 条审计。处置 = 审计写不参与业务事务、单飞裁切；并在 PRD 观测项里记「审计条数 / 天」。
- 负面：体积随使用增长（有界）；明文值在本地多一份副本（与业务表同姿态，见限制与已知边界）。

## 限制与已知边界

- **仅 `tasks`**（`R-8`）；其余实体按同一 helper 逐个接入，`projects` 接入时须同时处理 `DEF-155`（记录层 `plain:` 捕获陷阱）。
- **不做撤销 / 重做**（B 档）、**不做跨端 actor 归属**（协议无 `actor`，需服务端契约）、**不做服务端审计 / 上报**、**不做移动端**。
- **不参与裁决**：审计不改变 OCC / `fieldBase` / 合并 / 冲突语义；`conflict-journal` 的 200 上限与优先级淘汰**不变**。
- **来源四值不含「用云端的 / 保留我的」两个恢复动作的独立值**：两者按内容来源映射（前者 `pull`、后者 `conflict-retry`），映射口径写入评审报告并在用例中锁死（新增第 5 值属 PRD 变更）。
- **隐私姿态 = 与业务表同等明文**（当前落库是 `plain:<明文>`，审计不构成「弱于业务库」的副本）；⛔ 不存 token / JWT / 口令；⛔ 不上报；随登出/清库同事务清除（`wipeUserData` 清表名单 +1，`BUSINESS_TABLES` 不动）。
- **不承诺**「每条变更都一定留痕」：审计是旁路，进程在业务提交与审计追加之间崩溃会丢该条（有 `logStructured` 失败事件可观测），这是 R-1「不阻断业务写」的必然代价。
- **首版不引入设备标识**：`nao.deviceId` 是登录会话绑定用的随机 ID（`X-Device-Id`），既非用户可读设备名、也不参与数据归属；审计纯本机 ⇒ 记录它不增加信息量，反而制造「能区分哪台设备」的假精度。将来做服务端侧审计时须新增字段（历史行无法回填）。

**重评触发点（任一成立即重开本篇）**：① 需要「撤销/重做」⇒ 升 B 档（同时复核本档 `fields` 是否需补 `before` 全量）；② 需要「对方是谁」（跨端 actor）或服务端侧审计 ⇒ 需服务端契约变更，单独立项；③ `DEF-147` 若被修成「内容等价则不写」⇒ 必须复核本档判据与「行写次数 vs 审计条数」断言（`written` 计数 / `data-changed` 广播语义也会变）；④ `projects` 等第二个实体接入 ⇒ 先解 `DEF-155`（记录层 `plain:` 捕获陷阱）并复核动作派生表；⑤ 观测到审计条目被淘汰（`audit.entry.evicted` > 0）成为常态 ⇒ 复核 1000 条上限与字段集；⑥ 2027-05-10。
