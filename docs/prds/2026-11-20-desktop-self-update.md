# PRD：桌面端应用内自我更新（检查更新 / 立即更新）

- 状态：待确认（待用户终签范围 + 待 QA 确认验证接缝） · Owner：PM
- 更新：2026-11-20
- 指针：来源 = 用户 2026-11-20 对话需求（5 项澄清已答）；关联 ADR 待 `arch-designer` 出具；台账 `docs/tasks-state.md`
- 优先级：Must（战略筛子通过，RICE 见附录）

## TL;DR（≤5 行）

- **做什么**：桌面端内置「检查更新 + 立即更新」，更新包在应用内下载、重启后生效。
- **给谁**：桌面端用户（Linux AppImage / Windows 安装版为主），Web 与移动端不受影响。
- **成功标准**：设置页可见当前版本与检查结果；Linux / Windows 能在应用内完成下载并重启生效；macOS / deb 一键打开正确下载页。
- **不做什么**：不做差分更新、不做后台静默强更、不新增第三方分发渠道、不解决 macOS 签名。

## 一、问题证据

- **现状（已核）**：`apps/desktop` 无 updater 依赖，`preload` 暴露的 `desktopAPI` 只有 8 个键、无更新通道 ⇒ 用户升级只能来仓库手动下载安装包重装。
- **可用基建（已核）**`v1.20.2` Release 已挂 8 产物 + `latest.yml` / `latest-mac.yml` / `latest-linux.yml` ⇒ 更新源无需新建服务器。
- **5 Whys 摘要**：用户不知道有新版本 → 应用内没有检查入口 → 没有更新通道 → 分发靠手工下载 → 升级只能靠用户自觉关注发布页 ⇒ 修复长期触达不到多数用户。
- **证据缺口（诚实登记）**：本仓无遥测，拿不到版本分布与升级率；§二 目标指标因此不设升级率。

## 二、目标指标

- **北极星关联**：留存与持续使用（旧版本长期不升 ⇒ 已修复缺陷被反复感知）。
- **主指标**：应用内升级链路可达（检查 → 下载 → 重启生效 三段全通），以 AC 覆盖替代比例指标。
- **次指标**：手动检查成功率 ≥95%（网络正常前提下，抽测计数，PM 自证一条命令）。
- **反指标**：启动静默检查不得阻塞首屏（见 §六）。
- **缺口**：无遥测 ⇒ 不设「升级率 / DAU 提升」类目标。

## 三、范围 / 非范围

- **范围**：设置页新增「关于 / 更新」信息块（仅桌面端渲染）：当前版本 + 检查更新按钮 + 状态与结果。
- **范围**：启动时静默检查（延迟执行、失败静默、不弹窗），结果只在设置页可见。
- **范围**：手动检查（结果必达：有新版本 / 已是最新 / 失败原因），手动检查忽略缓存。
- **范围**：点「立即更新」下载更新包，完成后提示「立即重启更新 / 稍后」。
- **范围**：平台差异 —— Linux AppImage 与 Windows 安装版原地更新；macOS、Linux deb 降级为「打开下载页」并说明原因。
- **范围**：数据护栏 —— 存在未同步改动时，重启前提示并二次确认。
- **范围**：失败兜底 —— 检查 / 下载 / 校验失败给可读原因 + 重试 + 打开下载页。
- **非范围**：差分 / 增量更新 —— 当前产物无 `.blockmap`，改造面与收益不匹配（全量约 100MB 级）。
- **非范围**：后台静默强制更新（不告知用户）—— C 端体验与数据安全不可接受。
- **非范围**：macOS 代码签名与公证 —— 需 Apple 开发者证书，成本另立需求。
- **非范围**：Linux 仓库式更新（apt 源 / deb 自更新）—— 超出本期，deb 走下载页。
- **非范围**：应用商店分发（MS Store / Flathub / Snap）—— 本仓无此渠道。

## 四、用户场景

- **画像**：长期用桌面端、不关注仓库发布页的普通用户；不知道「有没有新版」是核心痛点。
- **场景 A（被动发现）**：打开设置改主题时看到「当前版本 1.20.3 · 有新版本 1.21.0」。
- **场景 B（主动检查）**：点「检查更新」→ 检查中 → 结果（新版本 / 已是最新 / 失败）。
- **场景 C（更新）**：点「立即更新」→ 下载进度 → 就绪 → 「立即重启更新」或「稍后」。
- **场景 D（平台降级）**：macOS 用户检查到新版本 → 看到「打开下载页」+ 一行原因说明。
- **关键路径**：设置 → 关于/更新 → 检查 → 立即更新 → 下载 → 重启 → 新版本号可见。
- **页面状态清单**：加载 = 检查中 / 下载中（含进度与按钮禁用）；空 = 从未检查（仅当前版本 + 按钮）；错误 = 网络失败 / 源不可达 / 校验失败；成功 = 已是最新 / 有新版本 / 待重启 / 本次启动已完成更新。

## 五、业务规则

- **版本比较**：按 SemVer 三段比较；仅当远端版本大于当前版本才提示有更新；相等不得出现「立即更新」。
- **版本号来源**：当前版本取自应用自身版本（与发版一致），不得硬编码、不得取 Web 端版本。
- **检查频率**：启动静默检查 24h 内最多一次（结果按版本缓存）；手动检查忽略缓存，必发一次请求。
- **静默不打扰**：静默检查结果不弹窗、不打断、不抢焦点；仅在设置页显示，桌面侧栏可有「可更新」弱提示。
- **安装时机**：下载完成后不自动重启；只有用户点「立即重启更新」才安装并重启；点「稍后」保留已下载包。
- **完整性**：更新包须按更新源提供的哈希校验；校验失败不得安装，按失败处理并允许重试。
- **数据护栏**：存在未同步本地改动时，重启前必须提示；「仍要更新」需二次确认并明确告知风险；取消后不重启且保留已下载状态。
- **平台降级**：macOS / deb 安装形态下，不提供原地更新按钮，替换为「打开下载页」+ 一行原因。
- **零外溢**：非桌面环境整块不渲染（无空容器、无占位）；Web 端 / 移动端行为零变化（红线）。
- **不打断**：下载过程不得阻塞任务、番茄、同步等正常操作。
- **文案口径**：面向用户一律说人话，禁止裸露内部术语（`updater` / `autoUpdater` / `sha512` / 内部编号）。

## 六、NFRs

- **性能**：启动静默检查延后 ≥10s 且不阻塞首屏；单次检查请求超时 ≤10s。
- **安全**：更新包只从项目 Release 源获取并校验完整性；不引入额外第三方更新服务；错误文案不暴露本机路径与内部编号。
- **兼容**：Windows 10+ / 主流 Linux 发行版（AppImage）；macOS 走下载页；Web 与移动端零影响。
- **可观测**：失败必须界面可见（不静默吞错）；本地保留最近若干次检查 / 下载结果供报障。
- **i18n**：`zh-CN` / `en-US` 两套文案同步，禁止硬编码中文。
- **缺口**：更新包体积是否在界面上提示（约 100MB 级）待 uiux-designer 定稿，不在本 PRD 硬定。

## 七、AC

- 验证接缝：候选 ① 主进程更新服务模块（注入假 updater / 假源）② `desktopAPI` 更新通道 + 设置面板组件（真实组件挂载断言状态机）③ 构建产物 + 本地假源端到端 —— 待 `qa` 确认（2026-11-20 尚未确认）。

### 主路径

- AC1：Given 桌面端且远端版本高于当前版本，When 打开设置页并完成检查，Then 显示当前版本与「有新版本 vX.Y.Z」，且「立即更新」可点。
- AC2：Given 已发现新版本，When 点「立即更新」并下载完成，Then 出现「立即重启更新 / 稍后」，点「立即重启更新」后应用重启且显示新版本号。
- AC3：Given Linux AppImage 或 Windows 安装版，When 完成下载与重启，Then 更新在该平台原地生效（无需用户手动下载安装包）。

### 异常

- AC4：Given 网络不可用或更新源返错，When 点「检查更新」，Then 显示可读失败原因 + 「重试」+「打开下载页」，且不得显示「已是最新」。
- AC5：Given 下载中断或哈希校验失败，When 下载结束，Then 不进入「待重启」状态，显示失败原因并可重试。

### 边界

- AC6：Given 远端版本等于当前版本，When 检查更新，Then 显示「已是最新 vX.Y.Z」，不出现「立即更新」。
- AC7：Given macOS 或 Linux deb 安装形态，When 检查到新版本，Then 不展示原地「立即更新」，改为「打开下载页」并给一行原因。
- AC8：Given 24h 内已完成一次静默检查，When 再次启动应用，Then 不再发第二次请求，且设置页仍显示上次结果。

### 负向闭环

- AC9：Given 本地存在未同步改动，When 点「立即重启更新」，Then 先提示同步风险；点取消后应用不重启、已下载状态保留。
- AC10：Given Web 端或移动端，When 打开设置页，Then 更新信息块完全不渲染（无空容器、无占位、无新增请求）。
- AC11：Given 检查或下载失败，When 用户关闭提示，Then 后续手动检查仍可触发（按钮不永久禁用、无卡死状态）。

### 设计一致性

- AC12：Given 更新信息块，Then 状态三态可辨（颜色 + 符号 + 文字标签三重冗余），文本对比度 ≥4.5:1、图形/边框 ≥3:1，内容区 loading/error/empty 统一用 `LoadingError`。
- AC13：Given 非中文界面，Then 全部文案走 i18n（`zh-CN` / `en-US`），无硬编码中文。

## 八、上线闭环

- **灰度**：无分渠道灰度能力 ⇒ 首个含本功能的版本按常规发布，观察用户反馈；后续可用「Release 先不公开、验证资产后再公开」控制风险（做法待 arch 确认）。
- **监控**：无遥测，以用户报障 + 本地日志为准；发版说明须写明「应用内可检查更新」。
- **回滚**：坏包 ⇒ 撤回 Release 资产并发新 PATCH；已发 tag 不删（除非用户明确要求）；更新失败不得导致旧版本无法启动。
- **发布检查项（PM 清单增一条）**：Release 的 `latest*.yml` 与产物版本、`version` 字段三者一致，否则自动更新会拉错包。

## 九、变更治理

- **正式流程**：GitHub flow —— Issue + `feat/<issue-id>-desktop-self-update` 分支 + 单 PR squash 合并；文档随本任务 PR。
- **版本记录**：`feat` ⇒ MINOR；发版说明按 C 端「说人话」规范写「本次更新」段。
- **范围变更**：平台范围、更新源或安装时机任一变更 ⇒ 更新本 PRD 并重新评审（涉及分发策略）。
- **实现决策外置**：`electron-updater` 与自研取舍、签名策略、源地址形态一律进 `docs/adr/`，不在本 PRD 正文。
