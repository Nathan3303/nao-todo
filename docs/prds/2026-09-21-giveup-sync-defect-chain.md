## 1. 现象与 5 Whys

**现象**：桌面端将任务标记「放弃」后，状态无法同步到后端（表现为「标记后当下正确、刷新后回退」）。

| 层  | 追问                                                                                   |
| :-- | :------------------------------------------------------------------------------------- |
| ①   | 放弃状态刷新后回退                                                                     |
| ②   | 服务端从未落库该状态                                                                   |
| ③   | 服务端 `POST /sync/push` 反序列化时静默丢弃该字段                                      |
| ④   | push 载荷结构体 `CreateTaskReq` **不含** `givenUpAt`（亦无 `starMarkAt`/`archivedAt`） |
| ⑤   | **批量同步契约与单条更新契约（`UpdateTaskReq`）能力不对等**，且无契约一致性测试守护    |

**次生放大**：push 仍返回成功（**假成功**）→ 客户端清队列、不进重试/退避 → 下次 pull 服务端 NULL 覆盖本地 → 回退。

| ⑩ 服务端契约                                                             | ❌      | `interfaces/types/task.go:29-51` `CreateTaskReq` 无三字段；app `dto/task.go:38` 同                                                                           |
| ⑪ 转换/落库                                                              | ❌      | `application/task/converters.go:54`；`infrastructure/persistence/task/converters.go:63` 注释明示「不触碰 archived_at/star_mark_at/given_up_at/completed_at」 |

## 4. 衍生发现（rd-be 只读核对）

### 存量脏数据（修复前 Web 端关闭提醒导致的 `remind_at` 残留）

- **扫描口径确实过窄**（`GetDueReminders` 仅 `remind_at IS NOT NULL AND <= NOW()`）；存量残留行**会各误触发一次提醒**，触发后由 `ClearRemindRepeat` **自愈清空**；过去时刻的残留早已自愈，**真正还脏的是 `remind_at` 在未来的残留行**。
- **服务端不能安全批量清洗**：残留形态（`remind_at` 非空 + `repeat=none` + `weekdays=[]`）与**合法一次性提醒完全同形**；`remind_repeat='none'` 不等价于「无提醒」。
- **处置**：用户在生产库执行只读统计 SQL（5 条，重点看「未来待触发」上界）评估规模；规模小则**接受自愈**。**严禁** `UPDATE ... WHERE remind_repeat='none'`。
- 精确清理路径：在修复后的客户端上对该任务重新开关一次提醒（触发一次写即清空）。

### 其它隐患（记录，不修）

- **H2**：cron 为进程内定时器 → 多副本部署会重复推送（当前单实例不触发，扩容时需 CAS 抢占/分布式锁）。
- **H3**：`ProcessReminders` 返回扫描全集，CAS 失败仍推送旧事件（相邻小瑕疵）。

## 5. 决策留痕

- **修复范围**：整类补齐（`givenUpAt` + `starMarkAt` + `archivedAt`），而非单字段 —— 三者同源缺席。
- **方案 A vs B（服务端）**：选 **A**（`CreateTaskReq` 补字段，局部、向后兼容）；否决 B（push 改派 `UpdateTask`，回归面大、需对齐 LWW/乐观锁）。
- **接受 A 的取舍**：Create/push 路径不做读改写 → 绕过实体状态机（如「放弃时间须晚于开始时间」校验不生效）。
- **`CompletedAt` 不纳入**：列存在，但 `UpdateTaskReq` 刻意不暴露、由服务端状态机派生；客户端也不推送。
- **H1 方案 A vs B**：选 **A（仅扫描过滤）**；**否决 B（状态变更时清 remind）** —— B 会**永久丢失**用户原设提醒，且需为「取消归档/放弃/回到未完成」定义恢复语义；A 天然保留 `remind_at`，**恢复即恢复提醒**。
- **客户端清空语义统一**：`null` 表达「清空」在 Web PUT 路径失效（服务端视为「缺省」）→ 统一改为 `''`（A-1、②）。
- **类型收紧**：`TaskRemindSetterUpdateVO.remindAt/remindTime` 收紧为 `string`（两分支均必然产出具体值；「不触碰」由载荷形状表达）。
- **移动端**：`presentation-react` 未动（红线）；rd-fe 复核其无「更新路径用 null 表达清空」实例。
- **A-2 技术债**（读取边界 `''→null` 归一不对称，`givenUpAt` 未归一）：**仅记录，不修**（当前无实际缺陷）。
