# 2026-11-03 数据同步止血批（A 批：让「被覆盖的那一方」可见、可恢复）PRD

> **状态**：立项草案（2026-11-03，用户口头「推进 A 批立项建档」）→ 待架构评审 → 待开工确认（PM 不自行派发实现）。
> **依据**：只读审计 `docs/reports/2026-10-27-T562-data-sync-audit.md`（`T562`，13 条窗口：P0×1 / P1×6 / P2×6）+ 用户 2026-11-03「数据同步是什么？」答疑后的口头批准。
> **批次形态**：需求型（Issue + `feat/<issue>-data-sync-a-batch`）· **目标版本**：`v1.17.0`（MINOR，新增用户可见能力）· **预算**：**9–14 人天**（需用户批）。
> **跨仓**：本仓 + `nao-todo-server`（服务端改动必须**先于**客户端发布且向后兼容）。

## TL;DR

- **做什么**：把现有「整行后写覆盖」机制里**静默丢失**的部分，改成**可见、可对比、可恢复**；并补齐三处契约缺口（删除也要裁决、会丢的字段要么同步要么明确标注「仅本机」）。
- **给谁**：**多端并行使用**的用户（手机 + 桌面 + 网页）；单端使用者无感。
- **成功标准**：审计列出的 `F-01` / `F-02` / `F-03` / `F-04` / `F-06` 五个窗口**在可复现场景下不再静默**；每一次覆盖都能在冲突面板里看到「谁赢了、你的哪一项没进去」；3 周后能用真实数据回答「到底多久发生一次」。
- **不做什么**：**不改冲突策略**（仍是最新时间戳赢）· 不做字段级自动合并（B 批）· 不做事件溯源（C 批）· 不动偏好/设置面的同步（`F-05`，另批）· 不做服务端单调版本列（`A5`）。
- **为什么现在做**：① 这五个窗口属「用户做过的事悄悄消失」，是数据类最坏的一类缺陷；② 它是「Agent 能替你写数据」的**硬前置**（没有可追溯的写入与冲突记账，Agent 写入无法被信任）。

## 一、问题证据

- **机制现状（读码确证，`T562` §1）**：本地优先 —— 写本地 Dexie 入队 → 2s 防抖整行推送 → 服务端按 `baseUpdatedAt` 做 OCC，冲突则 LWW；拉取按 `(updated_at, id)` 游标，**含墓碑**。裁决粒度 = **整行快照**。
- **五个窗口（本次范围）**
    1. **`F-01`（P0）**：拉取时「本地更新」这一支**只把 base 收敛到远端版本**，既不合并也不记账；随后整行推送把他端的异字段覆盖掉 —— **冲突面板里什么都看不到**（`sync-service.ts:967-981` + `:1148-1158`）。这是唯一一个「连证据都没有」的窗口。
    2. **`F-02`（P1）**：冲突面板点「保留服务端版本」对 `stale` / `noop` **并不真的把服务端行写回本地**，只删了 journal 条目 ⇒ 用户以为听服务端的，接着一编辑又把它覆盖了（`conflict-journal.ts:317-338`）。
    3. **`F-03`（P1）**：`conflict` / `skipped` 两类**不留败方快照**，且当场出队 ⇒ 用户「看不到自己改的到底是什么」，也没法恢复。
    4. **`F-04`（P1）**：**删除没有 LWW/OCC** —— 客户端 `deletions` 不带 base；服务端删除无条件覆盖，且「覆盖即清 `deleted_at`」⇒ 离线删除永远赢他端编辑，反向会**复活墓碑**并吃掉删除意图。
    5. **`F-06`（P1）**：契约不承载的字段被**白名单静默丢弃**（`projects/tags` 的 `sortId`/`icon`、`taskComments` 的 `attachments`/`isTopUp`、`taskCheckItems` 的 `description`），告警还被抑制（`dropped-fields.ts:20-32`）⇒ 直接对应台账里的 `DEF-107`（清单/标签自定义图标跨端不生效）。
- **为什么用户现在才发现**：这些窗口**全部静默** —— 没有冲突条目、没有提示、没有日志上报；审计明确写「真实发生频率**不可估计**」（无遥测面）。这也正是本批要补的第二件事（可观测）。
- **5 Whys**：① 为什么数据会丢 —— 整行快照裁决；② 为什么整行裁决会丢 —— 两端改的是不同字段，却只能整行分胜负；③ 为什么没发现 —— 只有 `noop`/`stale` 留快照，最严重的「本地胜」支不留；④ 为什么只在这些分支留 —— 当时的冲突面板是为「推送被拒」设计的，没把「拉取收敛」也算成一次可能丢数据的裁决；⑤ 根因 —— **把「同步」当成了传输问题，没有当成"用户数据的最终归属问题"**。
- **设计输入**：这不是一次体验优化，而是**数据安全**问题；验收重点是「不再静默」与「可恢复」，不是观感。

## 二、目标指标

- **北极星（可核）**：审计的五个窗口在**构造场景**下从「静默」变为「可见」—— 每次覆盖都产生**一条含败方内容的记录**，且用户能据此恢复或明确选择放弃。判据：场景用例逐条通过（见 §七）。
- **过程指标 1（可观测性）**：覆盖类事件的**记账率 100%**（构造 N 种覆盖场景，全部出现在冲突面板/日志里，无遗漏）。
- **过程指标 2（可回答频率）**：上线后 3 周能给出「按类型 / 表 / 实体」的发生次数与竞态窗口（`winnerUpdatedAt − loserUpdatedAt`）分布 —— 之前是「不可估计」。
- **反指标**：① 为让场景通过而**放宽既有同步用例**（视为失败）；② 单端使用路径的**同步请求量/耗时**出现可测上升（>5% 需说明）；③ 老客户端行为发生任何变化（必须以「不带 base 的请求行为逐字不变」为红线）。
- **口径缺口**：频率仍取决于部署形态与用户习惯；本批只交付「能测」，不承诺具体次数。

## 三、范围 / 非范围

- **范围（A 止血批 = `A1`–`A4` + `A6`，合计 8–11.5 人天，含门禁与走查记 9–14 人天）**
    1. **`A1`（对应 `F-01`）**：拉取「本地胜」分支**落冲突记录**（远端行快照 + 逐字段 diff），使「被收敛掉的那次裁决」可见。
    2. **`A2`（`F-02`）**：修正「保留服务端版本」的动作语义 —— **真的把服务端行写回本地并保留新 base**，再清 journal。
    3. **`A3`（`F-03`）**：`withSnapshot` 覆盖 `conflict` / `skipped` 两类；面板对「无法自动恢复」的条目（如同 ID 冲突）给**重新生成 ID** 的引导。
    4. **`A4`（`F-04`）**：契约给 `deletions` 增加 `baseUpdatedAt`；服务端删除加 OCC 守卫，**缺省（老客户端不带 base）保持现有「删除优先」行为**。
    5. **`A6`（`F-06`）**：`sortId` / `icon` / `description` / `attachments` 等逐项收口 —— 要么进同步契约，要么在 UI 明确标注「仅本机」，**不允许静默丢弃**；`SYNC_PUSH_DROPPED_FIELDS` 白名单收敛为「已确认仅本机」项。
- **非范围**
    - **`A5`（`F-07` / `F-08`：服务端单调版本列 + 游标改版本）** —— 理由：需 DDL + 存量回填，3–5 人天，且属「同一毫秒」与「时钟回拨」两条例外窗口；**待 A 批观测结果再定**。
    - **`F-05`（偏好/设置面 push 无版本校验）** —— 理由：另一条同步链路（偏好队列），改动面独立，避免批次蔓延；单独立项。
    - **`F-09`–`F-13`（P2：伪 stale 挤占日志、无 `navigator.locks` 环境、拉取截断、日志有界/清库、日志明文加密姿态）** —— 理由：`F-12`/`F-13` 与本批的 `A1`/`A3` **强相关**，故**不在本批改实现、但必须由架构评审给出结论**（见 §六 R-H）。
    - **B 批（字段级合并，tasks 单实体 14–20 人天）/ C 批（事件溯源 45–80 人天）** —— 理由：待 A 批观测后按真实频率决策。
    - **移动端（`apps/mobile` / `packages/presentation-react`）** —— 理由：项目红线且本次同步审计未覆盖移动端；如需一并纳入须用户授权。
    - **改冲突策略 / 改整行快照模型** —— 理由：A 批的定位是「让结果可见可恢复」，不是换机制。

## 四、用户场景

- **场景 1（`F-01`，多端同时改不同字段）**：手机上把任务名改成「买牛奶」，桌面同时把优先级调成「紧急」。两边都在线。**今天**：桌面最后一次推送覆盖整行，手机那边改的名字在两端都变成旧值，且**没有任何提示**。**本批后**：冲突面板出现一条「云端版本覆盖了你的修改」的记录，能对比「我的名字 / 云端的优先级」，并且可以一键恢复被覆盖的字段。
- **场景 2（`F-02`，点错「保留服务端」之后的连带覆盖）**：冲突面板点「保留服务端版本」，回到列表继续编辑同一任务 —— **今天**：下一次推送又把服务端覆盖回去（因为服务端行其实没写回本地）。**本批后**：点完即把服务端内容落本地、后续编辑基于它进行。
- **场景 3（`F-03`，ID 冲突）**：两台设备都离线新建了同 ID 的任务，同步时服务端拒一条。**今天**：那条被静默出队，用户看不到内容、也没法找回。**本批后**：条目带完整内容，面板引导「重新生成 ID 后保留」。
- **场景 4（`F-04`，删除 vs 编辑）**：手机离线删了一个任务，桌面在线把它改了名并加了标签。**今天**：要么删除永远赢（桌面的编辑白做），要么反向把任务"复活"（删除意图丢失），**都没有提示**。**本批后**：按 base 判定，两种情况都能在面板里说清并让用户选。
- **场景 5（`F-06`，图标/排序跨端不同步）**：桌面给清单设了自定义图标、拖了排序，手机上看不到。**今天**：静默丢弃，反复推反复丢。**本批后**：要么真的同步过去，要么在 UI 上明确写「仅本机」（用户不再困惑）。
- **关键路径**：构造双端数据 → 触发同步 → 观察冲突面板记录 → 恢复动作 → 校验两端最终一致。

## 五、业务规则

- **R-A（策略不变）**：冲突裁决仍为「最新时间戳赢」；本批**不引入**自动字段合并、不引入人为选择弹窗（除既有的冲突面板）。
- **R-B（不许再静默）**：任何一次「一方的修改没进最终结果」都必须留下**含内容**的记录；**没有内容的记录 = 没做**。
- **R-C（说人话）**：冲突面板与提示**禁止暴露内部术语**（`stale` / `noop` / `OCC` / `base` / `derivedUpdates` / 字段键名等），一律映射为用户可读标签（如「云端最新」「我的修改」「被覆盖的字段」）；沿用 `AGENTS.md` C 端原则与三态冗余（颜色 + 符号 + 文字）。
- **R-D（老客户端向后兼容，红线）**：服务端新增守卫/字段必须**缺省保持旧行为** —— 老客户端不带 base 的推送与删除，结果必须与今天**逐字一致**（以回归用例锁死）。
- **R-E（「保留服务端」必须真生效）**：该动作 = 用服务端内容覆盖本地 + 保留新 base + 清记录；不允许只删记录。
- **R-F（删除也要裁决）**：`deletions` 携带 `baseUpdatedAt`；服务端按同一 OCC 语义判定；不做「删除永远赢」也不做「编辑永远赢」。
- **R-G（字段收口二选一）**：每个会被丢弃的字段，要么进同步契约（服务端加列/加 DTO 字段，需 DDL 的单独评估），要么在 UI 明确标注「仅本机」。**不得**保留"丢弃但不告知"。
- **R-H（密文姿态）**：`A1` / `A3` 会给冲突记录写入更多业务内容（此前 `loser` 已属明文风险，`F-13`）。**架构评审必须给出结论**：同批加密 / 沿用现状并登记风险 / 只存摘要。**在评审结论出来前不得实现快照落库**。

## 六、NFRs

- **兼容性**：客户端与服务端**双向兼容**（新客户端 + 旧服务端 / 旧客户端 + 新服务端都不得崩、不得行为突变）；服务端先发布。
- **性能**：整行推送路径不增加往返次数；冲突记录写入为本地事务内附加操作，**不得**阻塞推送队列；单次同步耗时增幅 <5%。
- **数据安全**：冲突记录不得成为「明文业务库」的越权副本（见 `R-H`）；登出/清库必须一并清理（沿用现有清理链路）。
- **可观测**：冲突记录必须**可按类型 / 表 / 时段统计**且能被导出（用于 3 周观测）；上报口径若涉及隐私须先过 PM（默认只在本机统计，不做网络上报）。
- **不适用**：视觉设计体系（沿用 `nue-*` token）· 移动端（红线）。

## 七、AC（验收标准）

- **AC1（`F-01`）** 构造「两端改不同字段 + 本地胜」场景 ⇒ 冲突记录出现，含**远端快照**与**逐字段 diff**；用户可据此恢复被覆盖字段；**不得**只留一句文案。
- **AC2（`F-02`）** 点「保留服务端版本」后本地行 = 服务端行（逐字段比对）、base 已更新、记录已清；随后编辑并推送**不再覆盖**服务端其它字段。
- **AC3（`F-03`）** `conflict` / `skipped` 两类记录均含败方内容；面板对不可自动恢复的条目给出「重新生成 ID」引导且可用。
- **AC4（`F-04`）** 新客户端：删除 vs 编辑两种顺序都能裁决且结果可见；**旧客户端**（不带 `baseUpdatedAt` 的 `deletions`）行为与今天逐字一致（回归用例）。
- **AC5（`F-06`）** 会丢字段清单逐项有结论（进契约 或 标「仅本机」）；`SYNC_PUSH_DROPPED_FIELDS` 只剩「已确认仅本机」项；用户界面无「设了但不同步且没说」的项。
- **AC6（兼容）** 旧客户端 + 新服务端、新客户端 + 旧服务端两组组合的同步用例全绿（可用桩/契约测试模拟）。
- **AC7（文案与三态）** 冲突面板内 `stale|noop|OCC|base|derivedUpdates` 等内部词 **0 命中**（源码级断言）；三态（谁赢/我的改动/可恢复性）颜色 + 符号 + 文字三重冗余。
- **AC8（门禁）** 九项全绿 + **跨仓**服务端 CI 全绿；给出精确数字与差值解释。
- **AC9（可观测）** 冲突记录可按「类型 / 表 / 时段」统计并可导出；3 周观测方法写进报告（含要采集的字段）。
- **AC10（零回归）** 单端使用路径（上传下载 / 冲突面板既有操作）行为与耗时无退化（对比数据入报告）。
- **AC11（清理）** 冲突记录随登出/清库清理；不残留跨账号数据。

## 八、上线闭环

- **版本**：`v1.17.0`（MINOR，用户可见能力）。
- **发布顺序**：服务端（`nao-todo-server`，向后兼容 + 缺省旧行为）→ 客户端 → 发版说明（说人话：讲清「以后数据被覆盖会告诉你」）。
- **观测**：上线后 **3 周**复盘「冲突/覆盖事件」频率与类型，据此决定是否上 B 批；数据只在本机统计，不外传。
- **回滚**：服务端守卫可关（配置/缺省路径）；客户端按 `A1`–`A4`、`A6` 分提交，可单独回退。
- **走查**：PM 出可勾选清单（多端冲突面板观感、恢复动作手感、文案可读性），由用户本人执行。
