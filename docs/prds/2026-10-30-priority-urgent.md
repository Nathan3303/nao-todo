# PRD：客户端识别「紧急」优先级（`DEF-84`）

> 状态：**待开工确认**（PM 2026-10-30）· 缺陷：`DEF-84`（P3）· 场景：web + desktop（移动端红线，不动）
> 来源：`docs/reports/defect-pool.md` `DEF-84` · qa 重核报告 `docs/reports/2026-10-30-T580-pool-status-recheck.md`

## 一、问题证据

- 服务端与其它端可把任务优先级设为 `urgent`；客户端转换层把**非白名单值**（含 `urgent`）统一映射为 `DEFAULT_TASK_PRIORITY = 'low'`（登记位置：`packages/domain-task` 的 `converters.ts:48-50`）。
- 后果：这类任务在 web / 桌面**显示为「低」**；`T538` 起排序与显示同源（`prioritySNMap`）⇒ 也落在**低档**，与服务端排序在 `urgent` 行上不一致。
- 用户目前**无法在客户端创建** `urgent`（选择器只有三档），因此这是「外部数据被降级展示」的静默错误，不产生数据丢失。
- 触发器：2026-10-25 `T538` 排序语义修复的副产品登记；2026-10-30 `T580` 池重核复核仍成立。

## 二、目标指标

- `urgent` 任务在本端**显示为「紧急」且不可被降级成「低」**（错误映射命中数 = 0）。
- 排序位置 = 优先级最高档（与 `prioritySNMap` 单一来源一致），跨端排序对 `urgent` 行**不再不一致**。
- 既有三档（`low` / `medium` / `high`）显示、排序、i18n 与用例**零回归**。

## 三、范围 / 非范围

**范围**

- 转换层：`urgent` 从「未知值 ⇒ low」中摘出，成为合法档位。
- 展示层：优先级选择器 / 标签 / 排序 rank 增加第四档「紧急」。
- **看板视图（`T582` 裁定 A 纳入）**：看板按优先级分组的分组名单仅三档 ⇒ `urgent` 任务**无列可落**；本单须给它一个落点，语义与列表/表格的「紧急」一致。
- **详情导出文案（`T582` 裁定 B 纳入）**：导出文本的优先级标签硬编码三档 ⇒ `urgent` 会被写成「低优先级」（对外文档错误），本单一并纠正。
- i18n：zh / en 各一处文案。
- 用例：转换映射 + 排序 + 选择器渲染（含「未知值仍回落 low」的负向断言）。

**非范围**

- 服务端任何改动（服务端已支持 `urgent`）。
- `packages/presentation-react` / `apps/mobile`（**移动端红线**，除非用户另行授权）。
- 优先级视觉体系重设计（沿用既有 `nue-*` token；若现有色板无「紧急」语义色，沿用既有 `error` 语义映射，不新造 token）。
- 与优先级无关的其它缺陷（`DEF-13` / `DEF-83` 等另立单）。

## 四、用户场景

- **S1 打开外部来源的紧急任务**：其它端（或服务端直写）把任务设为 `urgent` ⇒ 用户在本端任务详情 / 列表看到「紧急」，不是「低」。
- **S2 自己创建紧急任务**：优先级选择器出现四档，选「紧急」后保存、刷新、跨端拉取后仍为「紧急」。
- **S3 排序**：列表按优先级排序时，`urgent` 任务在 `high` 之前。
- **S4 未知值兜底**（负向）：遇到既非四档也非空的脏值仍回落 `low`，不崩、不显示空白标签。

## 五、业务规则

- **R1 单一来源**：优先级枚举与 rank 只允许一处定义（沿用 `prioritySNMap` 所在处），选择器与排序都引用它，不得各自写字符串/数字字面量。
- **R2 未知值口径不变**：除四档与空值外的一切输入仍归 `low`（保持现状语义，防脏数据）。
- **R3 空值不变**：`null`/空串仍按既有 `DEFAULT_TASK_PRIORITY` 处理，既有排序末位规则不变。
- **R4 配色**：不得仅靠颜色区分四档（项目红线：颜色 + 符号/文字三重冗余），对比度沿用 `DESIGN.md` 下限。

## 六、NFRs（业务视角基线）

- 不新增运行时依赖；不改同步载荷字段（`priority` 值语义由服务端既有定义决定）。
- 列表渲染性能不回退（纯映射表变更）。
- 离线 / 弱网行为不变（本地优先路径不动）。

## 七、AC

- **AC1（主路径）** 给定一条 `priority = 'urgent'` 的任务（本地库直写或跨端拉取），当渲染列表与详情时，Then 显示「紧急」，且**不显示**「低」。
- **AC2（主路径）** 给定优先级选择器，Then 提供四档（低 / 中 / 高 / 紧急）；选「紧急」保存后重新读取仍为 `urgent`（不回落）。
- **AC3（排序）** 给定同一列表内 `urgent` / `high` / `medium` / `low` 各一条，当按优先级排序时，Then 顺序为 紧急 → 高 → 中 → 低。
- **AC4（异常/负向）** 给定脏值（如 `'unknown-x'`）与 `null`，Then 分别按 R2 / R3 处理（`low` / 默认值），无异常抛出、无空白标签。
- **AC5（边界/跨端）** 给定服务端返回 `priority = 'urgent'` 的 pull 结果，Then 本地落库保留 `urgent`（不被转换层写成 `low`），再次 push 时不产生优先级变更。
- **AC6（设计一致性）** 四档标签在浅色 / 暗色下均满足对比度下限，且**不只靠颜色**区分（有文字标签）；不新增 `nue-*` 之外的 token。
- **AC7（移动端红线）** `git status --porcelain -- packages/presentation-react apps/mobile` = **0 行**。
- **AC8（看板视图，`T582` 裁定 A）** 给定已有三档分组的看板，当存在 `urgent` 任务时，Then 该任务在**某个可见列**渲染且列语义正确（**不得凭空消失**）；搬迁后优先级读写不回退。
- **AC9（导出文案，`T582` 裁定 B）** 给定含 `urgent` 任务的导出（详情导出 / 任务说明文本），Then 优先级显示为「紧急」而非「低优先级」。
