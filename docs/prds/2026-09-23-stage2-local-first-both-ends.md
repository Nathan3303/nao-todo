## 1. 问题证据（5 Whys）

| 层       | 内容                                                                                     |
| :------- | :--------------------------------------------------------------------------------------- |
| 现象     | **两端架构分裂**：desktop 读写本地 + 回传；**web 只读镜像 + 写路径远端直连**（离线禁写） |
| Why1     | 阶段一为「最小风险」选了 web 只读（C-59），desktop 保持既有 local-first                  |
| Why2     | 分裂导致**同一产品两端行为不同**（web 离线不能写、desktop 能写）                         |
| Why3     | **web 的 IndexedDB 只用于读镜像**，未用于写 ⇒ 架构能力浪费                               |
| Why4     | 两端各维护一套写路径语义 ⇒ **同步/冲突逻辑无法统一**                                     |
| **根因** | **缺少「两端同构 local-first + 统一同步 + 服务端冲突解决」的终态架构**                   |

## 5. 业务规则

1. **本地优先**：两端**所有写**先落本地，再回传 ✓
2. **离线可写**：两端离线均可写 ✓（撤销 C-59 的 web 离线禁写）
3. **冲突由服务端解决**：客户端不做合并决策（或仅做无损提示）✓
4. **不丢功能**：阶段一的「离线可读镜像 / 迁移门 / 清库 / 明文姿态」等**全部保留** ✓
5. **可观测**：冲突、回传失败、重试均有计数与可见提示 ✓

1. **冲突 = LWW（服务端权威、per-row）**；不做版本向量/字段级。⚠️ **关键更正**：**per-row LWW 服务端已实现**（`DecideUpsert` / `task/repoImpl.go`）⇒ **业务面无需新增 per-row 版本标记**；真缺口 = ① **时间基准**（本地写用裸 `new Date()`；`getServerTimeOffset` **只写不读**）② **覆盖不可观测**（`sync-service.ts:742-757` 静默移除队列）⇒ **2A = 时间校准（PS-15）+ 冲突 journal（含败方快照，`meta` 纯追加，PS-14）**；**2B = OCC** ⇒ **`T141` 非阶段二业务面前置**

## 19. 2B 定向设计裁定（`T161` / ADR r3，2026-09-24）

> 设计真源 = `docs/adr/2026-09-24-stage2-both-ends-local-first.md` **§9**（本 PRD 只记口径与裁定，不复制设计）。

| 项                               | 裁定                                                                                                                                                                                                                                                                                                                                                                                                     |
| :------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AC3 口径补充（OCC）**          | 冲突判据由「服务端 `updated_at` 权威 + 客户端时钟」升级为 **OCC**：版本令牌 = 服务端 `updated_at`（**不新增 `version` 列**）· push **逐条**回传 `baseUpdatedAt`（**缺失 ⇒ 现行 LWW 回退**，向后兼容）· `base` 不等 ⇒ **不写** + 回库中版本 + outcome **`stale`**（**additive**，与 `conflict`=ID 碰撞区分）· HTTP 200 + 逐条 outcome、**不新增错误码** ⇒ AC3「服务端给出确定结论」不变，**判据改为 OCC** |
| **AC4 口径补充（冲突 UX 边界）** | **自动解** = `remote-wins` / `push-noop` / `stale`（服务端权威 + journal + 可见）；**不自动解** = 需用户选本地版本者；恢复只给两种显式动作（「保留服务端版本」/「以我的版本重试」）。**字段级冲突（改不同字段）亦判 `stale`、不自动合并**（推论自「客户端不做合并决策」）                                                                                                                                |
| **AC6 口径补充（契约）**         | additive 协议面经 **C-44 评审**：sync 专用条目类型（嵌 `CreateXxxReq` + `baseUpdatedAt,omitempty`）· **不改共享 create DTO** · 不新增错误码；偏好侧 `POST /projects/:projectId/preference` 与 `PUT /user/config` **同批补回 `updatedAt`**（与 `GET` 同 `RFC3339Milli` 格式）                                                                                                                             |
| **DP-2B-1…5**                    | ① base 存储 = **(i) 业务行非索引字段 `syncedServerUpdatedAt`**（不 bump Dexie version）② **全局启用 OCC**（接受 R-16 行为变更 ⇒ W3 同批 + 发布说明登记）③ **新增 `stale`** ④ **R-2 同批消费 `error`**（闭合 2A 窄窗）⑤ **journal 上限 50 → 200 + 折叠提示**                                                                                                                                              |
