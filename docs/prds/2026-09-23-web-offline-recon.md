## 3. arch 三轮核验的关键结论

### 3.1 A1：安全姿态选项

| #   | 结论                                                                                                                                                                                                                 |
| :-- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 加密面**全收敛在 `cryptoService` 单一入口**（24 个调用点，无绕过）⇒ 姿态改造可收敛在 **1 个文件**                                                                                                                    |
| 2   | 现状形态本就是「**结构化字段明文 + 文本字段加密**」⇒ 真正要选的只有「文本明文/密文」+「解钥材料来源」                                                                                                                |
| 3   | **「弱化 KEK」= 最差档位**：持久化解钥材料与密文同处一个 origin ⇒ 复杂度换 **0 保护**，且制造「本地已加密」的**虚假安全感**，比诚实明文更危险                                                                        |
| 4   | **威胁模型重构（关键）**：web **已**明文存 bearer JWT 于 localStorage 且**全仓零 CSP** ⇒ XSS / 恶意扩展 / 同源页面**在 token 有效期内已可读全量**；故明文 IndexedDB 的增量是「**读取的持久性**」而非「读取的可行性」 |
| 5   | **真正的增量只有两处**：共享/借用设备、物理取盘；**最严重新增暴露 = 登出后残留**（现状 web 无业务数据 + `clearAuthData` 不碰 Dexie）                                                                                 |
| 6   | 迁移：跨端无冲突（origin 隔离）；同 origin 内模式切换需**自描述格式**（`plain:<原文>`）+ 持久化模式标记 + 双向读取，否则 `cryptoService.decrypt` 对明文**硬报错**                                                    |

### 3.2 A2：迁移方案与解锁门退役

| #   | 结论                                                                                                                                                                                                                                                                                                                                  |
| :-- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **「从此不输密码」与「启动解包老数据」的冲突被低成本解掉**：解锁门密码提示的**唯一**条件是 `hasKeyBundle(userId)`（无 bundle 直接放行），而**登录路径已自带明文密码**（`use-auth-usecase.ts:41` `ensureUnlocked(userId, password)`）⇒ **多数用户升级后首次登录即静默完成迁移、无需弹窗**；仅「有 JWT 的冷启动且不走登录」才见一次提示 |

| 6   | 14 项既有条款三分：**删除 2** / 修订 7 / 保留 6 —— 见 §5.3                                                                                                                                                                                                                                                                            |

### 3.3 A3：离线边界（本轮新增最关键）

| #       | 结论                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| :------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **0.1** | **「不弹密码框」≠「离线可进入」——存在两个独立的门**：门 A（保险库密码 `UnlockGate.checkLocal()`，**仅 desktop**）；门 B（网络检入 `routes.ts` `beforeEnter` + `check-in-page.vue`，**两端共用**）。⇒ 甲能拆门 A、**拆不掉门 B**；**web 没有任何离线旁路**（`grantOfflineEntry` 唯一生产调用点 = desktop `AppRoot.vue:83`）                                                                                                                                                                                                                                                                                   |
| **0.2** | ⚠️⚠️ **现状缺陷（本轮新发现）：离线检入会把 JWT 删掉** —— `AuthUseCase.checkIn` **任何错误（含网络类）**都执行 `authStore.clearAuthData()` → `clearUserData()` → **`localStorage.clear()`**。⇒ web 离线刷新 = 门 B 拦下 → checkin 网络失败 → **JWT 被销毁** → 落登录页（离线无法登录）= **彻底进不去**。**这条直接否掉「进应用永不弹密码框」的激进读法**，也说明 SHELL-05 C-24「网络类不跳 signin」的意图在 usecase 层被 `clearAuthData()` 反噬                                                                                                                                                              |
| **0.3** | 客户端**完全不校验 JWT `exp`**（`resolveUserIdFromStoredJwt` 只正则提 Id；`onAuthExpired` 仅响应 10041）⇒ 「JWT 已过期」与「有效」在客户端视角**无差别**                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **0.4** | 实测**服务端 JWT 默认有效期 = 48 小时**（`infrastructure/auth/jwt.go:70-71`，`ExpOffset` 全仓无人设置 ⇒ 走默认）⇒ 「设备即凭据」自然窗口 ≈ 48h；**但明文数据活得比 JWT 久**（只有登出才清）                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 1       | JWT 缺失/过期 + 离线：**「仅移除本地解锁密码」读法下 desktop 成立、web 不成立**（受 §0.2 阻断）；**「永不弹密码框」读法不成立**（§0.2 使其更难）。建议形态：**把 desktop 的「离线进入」模式搬到 web 的 checkin 失败页** —— 网络类失败且本地镜像存在 ⇒ 提供「**离线进入（只读）**」**显式按钮**，不自动放行                                                                                                                                                                                                                                                                                                   |
| 2       | 登出后离线：**两种读法下都是死路**（登出正是废除 JWT 的动作，与「JWT 长期有效」语义互斥）。**现状已存在**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 3       | 首次安装/新设备 + 离线：**正确终态，不是缺陷**（需文案「需联网登录一次」）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 4       | 空库或 C5 未修 + 离线：**C5 是「离线能看」的硬前置**；⚠️ **空库进入会被误读为「数据丢失」** ⇒ 必须用 `syncStatus.lastSyncAt === null` 区分「空库」与「未同步完成」                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 5       | 脏队列 + 离线 + 登出：desktop 现状登出不清 Dexie ⇒ **不丢**；**新姿态「登出即清」会永久丢**。口径：**`syncTracker.countDirty(userId)` 是权威**；`syncStatus.pendingCount` **会滞后**（只在一次同步的 `endRun()` 刷新）⇒ 护栏**必须直接调 `countDirty`，不得读缓存**                                                                                                                                                                                                                                                                                                                                          |

| 9       | 多标签/多实例（`requestSingleInstanceLock` **实测未启用**）竞态 6 条：①pull 游标 RMW ②重复 push ③暂停/退避态互相覆盖 ④迁移并发 ⑤**⚠️ 新增：登出竞态**（标签 A 登出清库、标签 B 内存 store 仍有数据并可能随后写回 ⇒ **明文「复活」**）⑥双实例双倍首同步                                                                                                                                                                                                                                                                                                                                                       |
| 10      | 跨端不一致 / LWW：阶段一只读**可豁免**（无本地写 ⇒ `syncQueue` 恒空 ⇒ LWW 的 queued 分支永不触发）；但**必须有「阶段一不产生任何 `markDirty`」的纪律**                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 11      | `deletionSchedules` 与「注销即清」**无冲突**（注销**本身需网络** ⇒ 离线无法注销）；真实问题是宽限期内离线启动会看到注销前数据（合理）                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 12      | 另发现：① **desktop 生产走 `file://`**（`win.loadFile`）⇒ 无响应头 ⇒ **CSP 只能靠 `<meta>`**；且 Chromium 下 `file://` 的 localStorage/IndexedDB 归属「file 协议」大类 ⇒ 同 profile 下其它本地 HTML 也可能触及同源存储；② **SPA 不由 `nao-todo-server` 托管** ⇒ CSP 需落**静态托管侧**；API 是**另一个 origin** + `withCredentials`（带 cookie）；③ 被顶号/10041 **离线不可知**，联网第一请求即清认证 ⇒ 用户感到「离线改的突然全没了」；④ `localSession` / `isAuthenticated` 均**内存态、web 无重建点**；⑤ `X-Device-Id`（`getDeviceId()`）与「登出只清业务键」需明确保留；⑥ 时钟偏移 ⇒ 表现为「莫名被登出」 |

## 5. 与 WEB-OFFLINE 解耦、但顺带发现的独立缺陷

### 5.1 独立缺陷（无论 web 离线是否做，都建议单独立单）
