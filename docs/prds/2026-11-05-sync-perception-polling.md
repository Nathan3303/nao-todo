# 2026-11-05 同步感知 A′：可见窗口自动刷新（自适应轮询）PRD

- 状态：待开工确认 · 更新：2026-11-05 · Owner：PM
- 技术底稿：`docs/reports/T653-realtime-feasibility.md`（arch 只读评估，PM 已抽查 4 处关键结论）
- 关联：`docs/prds/2026-11-03-data-sync-a-batch.md`（OCC / 冲突落账语义，本单**零改动**）· `docs/adr/2026-09-13-shell-06-offline-backfill.md`（退避范式）· `docs/adr/2026-10-23-reminder-local-judgment.md`

## 一、问题证据

- **现状的拉取触发源只有四个**：启动/解锁 · `online` · 回到前台（节流）· 手动「立即同步」（`shell-05` / `shell-06` ADR 记载）。**没有任何周期性刷新**。
- **后果不是"慢"，是"永久"**：窗口停在列表上不操作，他端改动在本端**永远不会出现**，直到用户切走再回来或手动点同步（`T653` §5 基线行原文：「他端改动最长**永久**不可见」）。用户主观结论是「数据没同步 / 是不是丢了」。
- **A 批放大了这个缺口**：`v1.17.0` 把冲突做成可见、可恢复，前提是拉取及时。拉取不触发时，用户看到的是「另一台改了这边没反应」，反过来削弱了刚建立的「冲突看得见」的可信度。
- **多标签还有一个既有缺陷**（arch 读码，`sync-service.ts:828-848`）：`withPullLock` 用 `navigator.locks` 的 `ifAvailable`，**未取到锁即整轮跳过**，没有任何补偿通知 ⇒ **非主标签的界面永久陈旧**。这不是本单引入的，但本单把「自动刷新」做成常态后，这个缺陷会从「偶尔」变成「每次」。
- **限流预算不足（既有隐患，与本单无关但会被本单踩到）**：`/sync/pull` 与 `/sync/push` **共享** `24 次/分/IP` 的桶（`syncRouter.go:19` + `rateLimit.go:50`，key = `ClientIP()+":"+tag`）。push 在 2s 防抖下连续编辑**理论峰值 30 次/分 ⇒ 今天就可能触顶**；A′ 再加 2 次/分/端，同一 NAT 下多端会更快打满。
- **用户诉求**：2026-11-05 提出「同步实时性」并倾向服务端推送（B）。经 arch 可行性评估 + 决策问询后，用户拍板：**A′ 先落地（目标时延 ≤30s 够）、B 挂账待观测**。

## 二、目标指标

- **指标 1（主指标·他端可见时延）**：两端在线、本端窗口可见且无未推改动时，他端改动到本端出现 **≤30s**（p95 ≤35s），无需刷新页面或手动同步。
- **指标 2（请求预算）**：单端可见空闲态 **≤2 次/分**（30s 周期）；隐藏态 **0 次/分**；脏队列态周期拉取 **0 次**。
- **指标 3（多标签陈旧）**：非主标签收到广播到界面更新 **≤2s**；主标签关闭后 **≤30s** 选出新主。
- **指标 4（零新增裁决路径）**：OCC / `baseUpdatedAt` / 冲突落账 / `pull-local-wins` 相关代码与用例**零改动**（用反断言证明：删掉定时器 ⇒ 指标 1 红，其余语义用例仍全绿）。
- **指标 5（不新增静默失败面）**：任何周期拉取失败都不得改变数据状态，只退避并留结构化日志；不得出现「拉取在跑但界面说已是最新」的判据（新鲜度只看 `syncStatus.mirrorPulledAt`）。

## 三、范围 / 非范围

**做（客户端，本单）**

- 可见窗口 30s 周期拉取（复用既有 `syncService` 串行入口）。
- 可见性门控：隐藏即停、回到可见立即补拉一次后恢复周期。
- 失败退避：复用 `computeBackfillDelayMs` 范式（5s→10s→30s→60s→120s 封顶，成功清零），不引入第二套退避实现。
- 脏队列门控：`syncQueue` 非空时**降频或暂停**周期拉取（避免把用户刚输入的内容判成 `remote-wins` 回滚），队列清空后 ≤1 周期恢复；`online` / 回到可见 / 手动仍可拉（不得永久饿死）。
- 多标签：`navigator.locks` **单主拉取** + `BroadcastChannel` 广播「已拉取」通知 **成对落地**（只做单主 ⇒ 非主标签永久陈旧，T653 §6.4 明确列为已知坑）。
- 定时器与监听的生命周期清理（卸载/登出/离线）。

**做（跨仓维护单 `M20261105-sync-ratelimit`，独立 PR / 独立部署）**

- `/sync` 限流 key 由 **IP** 改为**已鉴权 `userId`**（未鉴权请求回落 IP），并把 `pull` 与 `push` **拆成两个桶**，避免互相挤占。
- 该单**先于或并行于**本单落地（服务端独立，客户端零依赖），并对老客户端逐字兼容。

**不做**

- **B（SSE 事件推送）**：挂账。决策口径见本单 §九。
- **`WriteTimeout=15s` 的生产改动**：当前**无 SSE 消费者**（客户端 SSE 已在 `v1.12.15` 删除），改它没有收益 ⇒ 归入 B 的立项前置条件。
- SSE 一次性 ticket（`?token=` 隐患）· `pull-local-wins` 降噪 · Web Push · binlog CDC · 多实例 Redis fanout。
- **移动端**（`apps/mobile` / `packages/presentation-react`）零改动（红线）。
- 任何 OCC / 冲突裁决语义调整。

## 四、用户场景

- **场景 1（桌面 + web 同时开着，主场景）**：桌面端把任务名改成「买牛奶」，web 端窗口就停在列表页。**今天**：web 端永远不会变，用户以为改了没生效，可能再改一次 ⇒ 制造真实冲突。**本单后**：≤30s web 端标题自己变成「买牛奶」。
- **场景 2（两台机器，一台在另一个网络）**：笔记本在公司网、台式机在家。**今天**：回家看台式机还是旧数据。**本单后**：可见后 ≤30s 收敛；切换网络（`online`）立即收敛。
- **场景 3（多标签误用）**：用户开了 3 个标签，在标签 A 编辑、回头在标签 B 看。**今天**：B 永久陈旧（`ifAvailable` 整轮跳过）。**本单后**：A 拉取后广播，B ≤2s 更新；A 关闭后 B 在 30s 内接管。
- **场景 4（正在输入时另一端也改了）**：本端输入到一半、还有未推改动。**今天**：可能被 `remote-wins` 回滚。**本单后**：脏队列态不周期拉取，等推完再拉，用户输入不被抢走。
- **场景 5（离线/后台）**：断网、或标签被切到后台。**本单后**：零周期请求，不刷屏；恢复可见/联网后立即拉一次。

## 五、业务规则

- **R-1（单一入口）**：周期拉取与事件驱动拉取（`online` / 可见 / 手动 / 广播）**一律经既有串行队列**；禁止直接调内部 `pullAllInner` 或绕过锁。
- **R-2（写事务原子性不放宽）**：本地写必须「业务行 + 队列」同事务（现状 `putWithSyncBaseAndEnqueue`）；本单**不得**为拉取频率改动写路径。
- **R-3（墓碑不改语义）**：墓碑强制远端胜的特判**不得**因拉取变频繁而放宽（放宽 = 复活血亏墓碑）。
- **R-4（门控优先级）**：`隐藏 > 离线 > 脏队列 > 周期`。命中任一前项即不发周期请求；但 `online` / 回到可见 / 手动 属用户可感知动作，**不受脏队列门控限制**。
- **R-5（退避单一实现）**：复用既有退避函数与上限（120s 封顶），不新建第二套。
- **R-6（单主 + 广播成对）**：单主不取锁即跳过是允许的，但**必须**广播「我已拉取（`pulledAt`）」，非主标签收到后自行刷新本地视图状态（数据来自同一 IndexedDB，不需要二次网络）。
- **R-7（新鲜度判据单一）**：界面「是否最新」只读 `syncStatus.mirrorPulledAt` / `lastSyncAt`，**不得**用定时器状态或「刚跑过」推断。
- **R-8（文案说人话）**：新增/变更文案不得出现内部术语（`pull` / `cursor` / `stale` / `mirror`），一律用户可读（`C 端原则`，`AGENTS.md`）。

## 六、NFRs

- **请求预算**：单端可见空闲 ≤2 次/分；同 NAT 3 端并发 + 连续编辑场景不得触发限流拒绝（依赖 `M20261105-sync-ratelimit` 落地）。
- **性能**：空响应拉取不得造成可感卡顿；不得阻塞本地 CRUD（沿用本地优先，写不等网络）。
- **后台与电量**：隐藏态零请求、零定时器空转；不引入无界定时器。
- **可观测性**：记录周期拉取次数/耗时/失败率/退避次数/广播命中（结构化日志，不进用户可见面）；**不新增**「同步中」以外的界面状态。
- **兼容性**：web 与 desktop 同代码同行为；桌面隐藏到托盘时 `visibilityState` 恒为 `visible` ⇒ **明确按可见处理**（持续刷新，符合用户「托盘里也是活的」预期，登记为有意行为）。
- **红线**：移动端 0 改动；服务端零改动（本单）。

## 七、AC（五覆盖）

**主路径**

- **AC1**：给定两端登录同一账号、本端窗口可见且 `syncQueue` 为空，当他端修改任务标题，则本端 **≤30s** 内显示新标题，无需刷新页面或手动同步。
- **AC2**：每次周期拉取成功后 `syncStatus.lastSyncAt` / `mirrorPulledAt` 前进；同步面板显示的时间随之更新，且不出现「同步中」抖动（沿用 `DEF-138` 的展示层约束）。

**异常**

- **AC3**：给定连续拉取失败，则退避按 5s→10s→30s→60s→120s 递增并**封顶 120s**，期间不产生请求风暴；恢复成功后间隔回到 30s（成功清零）。
- **AC4**：给定离线或凭证失效（401/`10041`），则不周期重试（离线不建定时器）、走既有鉴权过期路径；**不得**清本地库、不得新增导航行为。

**边界**

- **AC5**：给定标签隐藏/窗口最小化（web），则周期请求数为 **0**；回到可见后**立即拉取一次**再恢复 30s 周期。桌面最小化到托盘按**可见**处理（持续刷新）。
- **AC6**：给定 `syncQueue` 非空（用户刚编辑未推），则周期拉取**不发生**；队列清空后 ≤1 周期恢复；期间 `online` / 回到可见 / 手动 仍可正常触发拉取（不被门控饿死）。
- **AC7**：给定同浏览器 3 个标签，则只有主标签发起网络拉取；非主标签在 **≤2s** 更新界面（广播驱动）；主标签关闭后 **≤30s** 内选出新主并继续刷新。

**负向闭环**

- **AC8**（零新增裁决路径）：OCC / `baseUpdatedAt` / 冲突落账 / `pull-local-wins` 的源码与用例**零改动**；变异验证 = 移除周期定时器 ⇒ **AC1 红**，而冲突语义用例**仍全绿**。
- **AC9**（限流不自伤）：单端 30s 周期 ⇒ ≤2 次/分；配合 `M20261105-sync-ratelimit` 后，同一 NAT 3 端并发 + 连续编辑 **60 分钟**不出现限流拒绝（响应码非限流类）。
- **AC10**（资源清理）：组件卸载 / 登出 / 进入离线时，定时器与广播监听全部释放（测试断言无残留）；不引入无界定时器。

**设计一致性**

- **AC11**：新增文案中英双语、无内部术语（列举禁用词）；沿用 `nue-*` token，不新增 token / 不自绘状态；移动端 `git status --porcelain -- packages/presentation-react apps/mobile` = **0**。

## 八、上线闭环

- **落地顺序**：`M20261105-sync-ratelimit`（服务端，独立 Issue + 独立 PR + 部署）**先或并行** ⇒ 本单客户端发版。两端互不阻塞（客户端在旧限流下 30s 单端仍可用），但**多端同 NAT 场景要靠服务端那单**才算达标。
- **验证**：客户端受影响面用例 + 全仓门禁（按批末口径）；服务端单跑其仓门禁 + 部署后 `POST /api/sync/pull` 非破坏探测。
- **用户验收（视觉/真机由用户执行）**：① 两端同开，改一条任务，看另一端 ≤30s 自己变；② 切走标签 1 分钟，回来立即是新数据；③ 3 个标签同时开，改一个看另外两个；④ 输入到一半时另一端改动，本端输入不被抢走；⑤ 离线 1 分钟再恢复，不刷错误、恢复后自动收敛。
- **回滚**：客户端回退到上一版本即可（无数据迁移、无服务端契约变更）；服务端限流单回滚 = revert + 重启容器。

## 九、变更治理

- **重评触发点 1（B 的生死判据）**：A′ 上线 **1 周**后回看 —— 用户「几乎每天两端同时开」已确认（2026-11-05），但目标时延选的是「≤30s 够」。若用户在多端同开场景下**从未感到 30s 慢**，则 **B 销案**（不是继续挂账）；若出现「30s 明显不够」的具体实例，凭实例重新立项。
- **重评触发点 2（冲突噪声）**：A′ 上线后一周内，若冲突面板因拉取频率上升出现 **>3 条/天** 的 `pull-local-wins` 记账，则立「降噪」小单（同实体合并 / 仅在随后 push `applied` 时保留），本单不做。
- **重评触发点 3（限流）**：`M20261105-sync-ratelimit` 涉及按 `userId` 限流，**属安全面改动**，落地前需 arch / qa 各一次评审（防「换维度即绕过」）。
- **B 的前置清单（保持挂账，不遗忘）**：`WriteTimeout` 仅对 SSE 放宽 · 事件源 2 处冒烟点 · 心跳 + 看门狗 + 常开兜底轮询 · 一次性 ticket · 反代/CDN 拓扑确认 · 老客户端零影响 4 条件。
- **本单不生成 ADR**；A′ 落地时按 `docs/adr/2026-11-XX-realtime-sync-polling.md` 归档一次（记录门控优先级与单主广播决策）。

## 十、优先级与决策留痕

- **战略筛子**：① 服务 C 端核心价值（数据可信）→ **是**；② 现有能力可覆盖 → **否**（现状永久不更新）；③ 引入第二真源 → **否**（周期拉取只触发既有 pull）；④ 触碰移动端红线 → **否**；⑤ 跨仓 → **A′ 否 / 限流单是**。⇒ **通过**。
- **MoSCoW**：**Must** = 可见 30s + 可见性门控 + 脏队列门控 + 单主/广播成对；**Should** = 限流改 `userId` 维度（跨仓）；**Could** = 聚焦补拉；**Won't（本期）** = B / SSE / 降噪 / Web Push / CDC。
- **RICE**（触达 = 每周受影响的跨端会话数，主观赋值）：**A′** R=4 · I=2 · C=0.8 · E=3 ⇒ **2.13**；**限流单** R=4 · I=1 · C=0.9 · E=0.5 ⇒ **7.2**（分高但因"看不见"排在 A′ 之后并行）；**B′** R=4 · I=2 · C=0.5 · E=9 ⇒ **0.44**（⇒ 挂账，不排期）。
- **Kano**：A′ = **基本型向期望型过渡**（"数据会自己变新"正在成为基线预期）；B = 期望型（有则更好，无则不投诉）。
- **决策留痕**：2026-11-05 用户拍板 D1–D7（见 `docs/tasks-state.md` §二）—— 方向 A′ 先落地 · 时延 ≤30s 够 · 接受事件可丢（B 语境）· 授权仅对 SSE 放宽 `WriteTimeout`（**因无消费者改挂 B 前置**）· 限流改 `userId` · 降噪暂不做。
