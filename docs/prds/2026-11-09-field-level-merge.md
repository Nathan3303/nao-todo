# 2026-11-09 B 批：字段级合并（两端改不同字段不再互相覆盖）

- 状态：待评审（arch ADR 并行中）· 更新：2026-11-09 · Owner：PM
- 上游依据：`docs/prds/2026-11-03-data-sync-a-batch.md`（A 批把「覆盖」变可见，B 批把「不必要覆盖」消掉）· 审计 `docs/reports/2026-10-27-T562-data-sync-audit.md`
- 直接证据：`docs/reports/671-diff-field-conflict-verdict.md`（qa 三时序实测）· 用户 2026-11-09 走查反馈「不同字段的更改无法合并，依旧冲突」
- 相关：`DEF-146`（保存侧覆盖记账，`v1.18.2` 已交付）· `DEF-147`（回拉幂等挂账）· `DEF-153`（非文本字段基准挂账）· `A5` 服务端单调版本列（挂账）

## 一、问题证据

- **机制现状**：本地先写 Dexie 并入队 → 2s 防抖**整行**推送 → 服务端按 `baseUpdatedAt` 做行级 OCC，冲突即 **LWW 整行分胜负**；拉取按 `(updated_at, id)` 游标回放。**裁决粒度 = 整行快照**（`T562` 读码确证，A 批 PRD §问题证据）。
- **三时序实测（`T671`，真实本地仓储 + 真实 journal + 假服务端只模拟 OCC/base/keyset）**：
    - **X（另一端保存前本端已拉取过）**：0 条记录，最终两端均为 `name:B / description:A` —— **两边都保住**；
    - **Y（本端保存后先 push、尚未拉取）**：产生 `stale`（既有行级 OCC），条目为「我的整行 vs 云端整行」，只能**整行二选一**；随后 push 把服务端描述覆盖为我的旧值 ⇒ **远端改的描述被吃掉**；
    - **Z（本端保存后先 pull）**：产生 `pull-local-wins`（A1 既有记账），同样**整行覆盖**、同样吃掉远端描述。
- **用户可见后果**：两端各改各的字段（最常见场景：一台改标题、一台调优先级/写描述），只要不在"对方改完之后、我保存之前"恰好拉取过一次，就**必然**出现冲突记录，且只能二选一 —— 选哪边都丢另一边的字段。**自动刷新把窗口从"偶发"变成每 30 秒一次**（`v1.18.0`）。
- **为什么现在必须做**：`DEF-146` 只解决了「覆盖要看得见」，用户看到的第一反应就是「为什么不合并」。A 批累计的冲突记录数与「不同字段占比」是最直接的立项依据（qa 可从现有 journal 统计，若线上样本不足以三时序实测为准）。
- **5 Whys**：① 为什么两端各改一个字段也会丢数据 —— 裁决粒度是整行；② 为什么整行 —— 服务端 OCC 以行 `updated_at`/`baseUpdatedAt` 为唯一版本；③ 为什么没有字段级 —— 初版同步以"整行 Last-Write-Wins"为最简实现；④ 为什么会频繁发生 —— 多端常开 + 30s 自动刷新；⑤ 根因 = **版本粒度与"用户实际编辑单元"不匹配**（用户编辑的是字段，系统裁决的是整行）。

## 二、目标指标

- **指标 1（不同字段零冲突）**：两端改**不同**字段（含 X / Y / Z 三种时序、含 300ms 内并发）⇒ 冲突记录 **0 条**，且两端 `name` 与 `description` **都等于各自最后一次写入值**（字段级逐条断言，不是"整行相等"）。
- **指标 2（同字段仍可见可恢复）**：两端改**同一**字段 ⇒ 仍按既有 LWW/OCC 裁决，产生既有 kind 的冲突记录（`stale` / `remote-wins` / `pull-local-wins` 之一），可查看、可复制；**⛔ 不新增第二条裁决路径**。
- **指标 3（零丢失）**：任一场景结束后 `local == server == 期望值`（按字段比对），且 **墓碑/删除语义不被合并逻辑破坏**（删除不被"字段合并"复活）。
- **指标 4（契约与成本）**：网络往返**不增加**（若不增加需要改变推送粒度，需 ADR 论证并在验收时给前后对照数字）；服务端契约变更须在 ADR 中显式列出并评估老客户端/移动端影响。
- **指标 5（红线）**：`packages/presentation-react` / `apps/mobile` diff = **0 行**。

## 三、范围 / 非范围

**做**

- **三方字段级合并**（`tasks` 单实体先行）：以「合并基准 `B`（上次同步成功的服务端版本）× 云端当前 `R` × 本地当前 `L`」逐字段判定，等价于 `DEF-146` 的三值判据，但结论是**合并**而不是"记账后保留我的"。
- **合并结果的落库与推送**：合并后本地行 = 合并值；推送只带**本端真正改动过**的字段（是否改推送粒度由 ADR 定，PM 要求：要么证明"整行推但不覆盖异字段"足够，要么给出字段级推送方案与契约影响）。
- **冲突记账按字段**：仅当**同一字段**三方冲突（`R≠B 且 L≠B 且 R≠L`）才记一条，快照只含该字段；与 `DEF-146` 的保存侧记账口径统一（同一 helper / 同一 kind 家族）。
- **派生与关联字段规则**：`state`/`priority`/`starMarkAt` 等枚举与布尔、`startAt`/`endAt` 时间、`tags` 集合、`parentTaskId` 父子引用、`archivedAt`/`deletedAt` 墓碑 —— 每类给出明确合并规则（枚举/时间/标量按三方；集合按"并集不丢"除非 ADR 反对；墓碑**删除优先**）。
- **面板呈现**：冲突记录按**字段**展示（而非整行两版对照）；文案去掉"整条二选一"之外的误导，明确"已自动合并的字段不会出现在这里"。
- **用例先行 + 变异**：合并矩阵（不同字段 × 3 时序 × 并发）× 墓碑 × 集合，红基线先出。

**不做**

- 事件溯源 / 操作历史（C 批）。
- 偏好与设置面同步（`F-05`）。
- 移动端任何改动（红线）。
- 放宽 OCC 或改动 `pull-local-wins` 既有语义（`DEF-146`/`DEF-139` 已定口径）。
- `D1(b)`「把我的修改一键写回云端」—— 与本批无耦合，继续挂账。
- 删除后自动复活、跨字段语义推导（例如"状态改完成 ⇒ 自动补完成时间"）。

## 四、用户场景

- **场景 1（最常见，主路径）**：桌面改标题、web 改描述，各自保存（任意先后、任意是否刷新过）→ **两边都保住**，冲突面板**无新增**。
- **场景 2（同字段）**：两端都改描述 → 按既有规则出一条冲突记录，能看两版、能复制、能二选一。
- **场景 3（编辑期远端改同字段）**：`DEF-146` 已覆盖（保存侧记账）；本批**不得回归**该行为。
- **场景 4（集合）**：手机加标签 `#紧急`、桌面加 `#工作` → 合并后两个标签都在（不丢）。
- **场景 5（墓碑）**：A 端删除任务、B 端同时改描述 → **删除优先**（不因字段合并不删），B 端看到"已被删除"的既有提示，且**不产生"我的修改已覆盖云端"类假账**。
- **场景 6（父子）**：A 端把子任务移到别的父任务、B 端改该子任务标题 → 两边都生效（引用字段与文本字段互不覆盖）。
- **场景 7（并发靠近）**：两端 300ms 内先后保存不同字段 → 仍零冲突（keyset/时间戳同毫秒也成立）。

## 五、业务规则

- **R-1（判据唯一）**：字段级三方判定统一走一个 helper（`valuesEqual` 作比较、空哨兵归一），**⛔ 不新增第二套比较语义、⛔ 不加第五套忽略字段表**。
- **R-2（何时合并 / 何时冲突）**：`R==B` ⇒ 取 `L`（我改的）；`L==B` ⇒ 取 `R`（对方改的）；`R==L` ⇒ 取其一；三者两两不等 ⇒ **冲突**（记账，按既有裁决保一方）。
- **R-3（kind 不扩张）**：合并成功的字段**不记账**；冲突沿用既有 kind；如 ADR 论证必须新增 kind，须显式列在开工确认卡上并由 PM 决定（默认**不加**）。
- **R-4（墓碑优先）**：`deletedAt`/`archivedAt` 非空一方胜出时不参与字段合并；墓碑冲突按既有墓碑语义处理，⛔ 不得新增"复活"路径。
- **R-5（幂等）**：合并必须可重放（同一份输入重复应用结果不变），与 `DEF-147`（回拉窗口未变化行仍重写）的口径协同 —— 该项仍挂账，但本批的合并逻辑不得依赖"每轮都重写"。
- **R-6（基准只前进）**：合并成功后 `syncedServerUpdatedAt` 按既有规则推进；⛔ 不得回退 base（`R-20` 灾难路径守护点）。
- **R-7（文案说人话）**：面向用户不出现字段内部名、kind 名、`revision` 等；冲突类型一律映射为用户可读标签。
- **R-8（范围守卫）**：合并逻辑只作用于 `tasks`；其余实体（projects / check-items / comments / tags / pomodoros）本批**行为不变**，由后续批次按同一 helper 逐个接入。

## 六、NFRs

- **性能**：单次 pull 的合并计算 O(字段数)；不新增网络往返；合并后的推送载荷不得大于现状（若改变推送粒度需给体积对比）。
- **兼容**：老客户端（未升级）与服务端必须仍能正常工作（最坏情况退化为今天的整行 LWW，**不得**产生数据损坏）；移动端零改动、只验签名/协议兼容。
- **可观测**：合并次数 / 冲突次数（按字段）可从既有状态面读出；日志不含明文业务值（`STRUCTURED_LOG_EVENTS` 风格）。
- **数据安全**：合并只在本地库与既有推送通道内进行；不新增服务端存储的明文副本；`A` 批 `R-H` 快照约束继续有效。
- **可回滚**：合并逻辑必须可按开关降级为整行 LWW（便于线上问题快速止血），开关默认开启后给出回滚判据。

## 七、AC（五覆盖）

**主路径**

- **AC1**：场景 1 三种时序（`T671` 的 X / Y / Z）各跑一遍 ⇒ 冲突记录 **0 条**，`name` 与 `description` 两端均等于各自最后写入值。
- **AC2**：场景 4 集合合并 ⇒ 两个标签都在；重复标签不重复（幂等）。

**异常**

- **AC3**：合并中途失败（存储/加解密抛错）⇒ 不写入半成品、不丢数据、走既有错误面；日志为结构化且不含业务值。
- **AC4**：服务端返回 `stale` 且云端字段与该字段无重叠 ⇒ 客户端**不记冲突**、按合并结果重推一次并成功。

**边界**

- **AC5**（零误报 / 零漏报矩阵，逐条可断言）：仅我改 / 仅对方改 / 我改回原值 / 格式化差异 / 空哨兵（`''`/`null`/`[]`/`'none'`）/ 同毫秒并发 / 字段集不相交 / 字段集部分相交（一半合并、一半冲突）。
- **AC6**：墓碑优先 —— 删除 + 改字段并发 ⇒ 删除胜、无假账；归档与改字段并发 ⇒ 按 ADR 结论（默认归档胜）。

**负向闭环**

- **AC7**（变异证明）：① 去掉三方判定退化为"整行 LWW"⇒ AC1 必红；② 合并只取本地 ⇒ 对方字段丢失用例红；③ 集合改成覆盖 ⇒ AC2 红；④ 墓碑参与合并 ⇒ AC6 红；⑤ 去掉幂等（重复应用产生不同结果）⇒ AC5 的重复应用用例红。
- **AC8**（不新增第二裁决路径）：既有 kind 集合与 `conflict-journal` 对外语义零变化；`DEF-146` 保存侧记账用例、`DEF-139` 重试口径、`t659` 广播收敛全部零回归（用例零修改）。

**设计一致性**

- **AC9**：面板按字段呈现、无内部术语、无新增自绘状态；零新 i18n 键（如需新增须在开工确认卡列出并说明）；移动端 diff 0；`DESIGN.md` 若有新交互需同批更新。

## 八、上线闭环

- **落地**：单 PR（客户端 + 可能需要服务端配套，ADR 定）· 用例先行 · 批末全量门禁 9 项。
- **验证**：qa 独立复验（三时序 + 并发 + 墓碑 + 集合 + 变异）；用户走查（两端不同字段、同字段、集合、删除并发）。
- **观测（上线后 2 周）**：冲突记录数按 kind/字段统计应显著下降；「不同字段仍冲突」类报障应为 0；`local==server` 对账不得出现新的不一致。
- **发版**：`v1.19.0`（MINOR，行为变更）。
- **回滚开关**：置为整行 LWW 即恢复本版行为（需在验收时实测该开关）。

## 九、变更治理

- **重评触发点 1**：若合并后 `local==server` 对账出现新不一致 ⇒ 立即关闭开关、回滚到整行 LWW 并复盘。
- **重评触发点 2**：若服务端必须改契约（字段级 OCC / 单调版本列 `A5`），须单独 ADR + 部署计划，**不得**与客户端 PR 混发。
- **重评触发点 3**：`DEF-153`（非文本字段基准）与本批字段规则强相关 —— 若本批引入字段级基准，需重评 `DEF-153` 是否顺带闭环。
- **已知不关闭**：编辑草稿与合并的交互（`DEF-146` 已定口径，本批只保证不回归）；`pull-local-wins` 真写回（`D1(b)`）；`DEF-147` 回拉幂等。

## 十、优先级与决策

- **战略筛子**：① 服务 C 端核心价值（数据可信）→ 是；② 现有能力可覆盖 → 否（现状必然丢一侧字段）；③ 引入第二真源 / 第二裁决路径 → 否（复用既有 journal 与 OCC）；④ 触碰移动端红线 → 否；⑤ 跨仓 → 视 ADR（若需服务端改动则跨仓）。
- **MoSCoW**：**Must** = 三方字段合并 + 同字段零回归 + 墓碑优先 + 幂等 + 回滚开关；**Should** = 面板按字段呈现；**Could** = 其余实体接入；**Won't（本期）** = 事件溯源、偏好同步、删除复活。
- **RICE**（主观口径）：R=4（每天多端同时开 + 30s 自动刷新的用户几乎每天都可能踩到）· I=4（丢字段 = 丢工作内容，且用户明确要求）· C=0.7（触碰裁决粒度，风险集中在同步链）· E=17（人天，取 ADR 拆分后中位数）⇒ **RICE ≈ 0.66**；与 A 批（止血）比对：A 批解决"看不见"，本批解决"不必丢"，价值密度低于 A 批但用户体感更强。
- **Kano**：**基本型**正在向**期望型**迁移 —— 多端用户认为"各改各的字段应该自动合并"，不满足会直接怀疑同步可靠性。
- **预算**：以 `A` 批 PRD 的 14–20 人天为上限，ADR 拆分后落到开工确认卡；**超过 20 人天须重报**。
