- **关联**：`apps/web/src/components/calendar/`（monthly / weekly）；上游单 TASK-08 日历排序（`calendar-sort.ts`，v-something 冻结口径）、TASK-11 日历界面 UI 优化
- **澄清来源**：用户 2026-09-21 提出需求 + 提供复现例子（3 个整周高优 + 1 个周一至周四中优 + 1 个周一全天高优，选「优先级降序」）；PM 通读链路后**新增发现 2 处隐藏排序**，已列出并给处置建议

## 1. 问题证据与 5 Whys

**现象（用户直提，附复现例）**：日历选「优先级降序」后，同一天起始的任务从上到下仍按**跨度长度**排列，用户选择的排序几乎不生效。

| 层  | 追问                                                                                     |
| :-- | :--------------------------------------------------------------------------------------- |
| ①   | 用户选了排序，看到的结果与所选排序不符                                                   |
| ②   | 行内轨道（上下位置）由 `colStart asc → colEnd desc` 决定，用户排序只在几何完全相同时生效 |
| ③   | 该二次键是为"长条挂在低轨道、跨周不跳行"而加，但它**覆盖**了用户意图                     |
| ④   | 日内抽屉/未安排列表**各自还有独立硬编码排序**（开始时间+创建时间 / 创建时间 desc）       |
| ⑤   | **命题：展示顺序应有唯一真源（用户排序），几何排序仅保留"起始列升序"这一最小必要键**     |

## 4. 用户场景

- **画像**：用排序下拉整理日历任务优先级的用户。
- **场景卡**：选「按优先级降序」→ 期望同一格/同一行内高优在上；打开某日抽屉 → 期望列表同样按所选排序；打开未安排抽屉 → 同样。
- **关键路径**：排序下拉 → `useCalendarSort` → `sortCalendarTasks`（唯一真源）→ ①月/周网格（`buildGridModel`）②日内抽屉 ③未安排列表。
- **页面状态清单**：未选排序（默认名称升序）/ 选中字段升降序 / 加载中 / 加载失败重试 / 空态 / `+N` 折叠态。
- **边界数据**：全部任务同起始列；同起始列不同跨度；跨周任务（len > 7 天）；同日只有 1 条；同名任务。

## 5. 业务规则

### 5.1 展示顺序唯一真源（本单变更）

- 所有日历展示顺序 = `sortCalendarTasks(tasks, sort)` 的结果顺序。
- 未选排序字段 → **按名称升序**（`localeCompare` 中文自然序，同名/空名按 `id` 稳定兜底）。
- 选中字段 → 主字段比较（升降序）→ **二次键恒为名称升序**（沿用现状，已实现）。

### 5.2 行内轨道分配（月/周共用，`buildRowContent`）

- 排序键：**仅 `colStart asc`**（"起始列早的在上"这一日历语法必需）。
- **同 `colStart` 内保持传入顺序**（＝用户排序；`Array.sort` 稳定性承载，不得再引入 `colEnd` 比较）。
- 轨道分配仍为贪婪首次适配（第一个无重叠轨道），**轨道总数不变**（数学上：按左端点升序做首次适配着色即为区间图最优着色，组内顺序不影响轨道数）。
- **已接受的代价**：跨周（len > 7 天）任务在不同周的轨道号可能不同 → 视觉上"跳行"。用户已知悉并接受（2026-09-21 决策）。
- `+N` 溢出计数与"哪些任务可见"随轨道分配变化（可见者＝低轨道号那批）。

### 5.3 日内抽屉（`getDayTasks`）

- 数据源由 `tasks`（原始快照）改为 `sortedTasks`；**删除**内部 `sort(开始时间 asc → 创建时间 asc)`。
- 结果：抽屉内顺序 = 用户排序（默认名称升序）。

### 5.4 未安排列表（`unscheduledTasks`）

- **删除** `createdAt desc → id asc`；顺序 = 用户排序。
- 实现落点二选一（RD 定，倾向 B）：**A** 在 `useCalendarTaskQuery` 注入排序函数依赖；**B** 在组装点 `useCalendarMonthly` 由 `sortedTasks` 派生，query 组合式不再自带排序。

### 5.5 保留项（明确不撤销）

- `buildCalendarListQuery` 的 `sort:{field:'id',order:'asc'}`：服务端分页稳定契约，**保留**。
- 快照集合 `taskIds`（Set 插入序）：**保留**；因 5.1 起展示顺序不再依赖它。

## 6. NFRs

- `sortCalendarTasks` / `buildGridModel` / `buildRowContent` 保持**纯函数**，可单测。
- 排序键比较不得引入 `dayjs` 依赖到 `monthly-layout.ts` 之外的新位置（沿用现状）。
- 展示顺序计算为 O(n log n) 且不新增网络请求；不改数据结构。
- 门禁：`vp test` 全绿（含新增用例）、`vp check` 全绿、`guard:ddd` OK、双端 build ✓。

## 9. 决策留痕

- **D1（2026-09-21 用户拍板：方案 B）**：行内二次键由 `colEnd desc` 改为**用户排序**。PM 曾误判"会导致轨道占用率下降"，复核区间图着色后**已更正**：仅 `colStart` 为主键时组内顺序不影响轨道总数；`colEnd desc` 的真实动机是让长条挂低轨道不跳行，其代价由用户明确接受。
- **D2（方案 C 否决）**：`colStart → colEnd → 用户排序` 三键无法解决用户复现例（长度键优先），否决。
- **D3（方案 D 否决）**：完全移除 `colStart` 主键会破坏"起始早的在上"语法并可能浪费轨道，否决。
- **D4（PM 新增发现，本单扩大范围）**：`getDayTasks`（日内抽屉）与 `unscheduledTasks`（未安排）各自带硬编码排序，与"展示顺序唯一真源"直接冲突 → 纳入本单。**若用户认为抽屉/未安排的"时间序"应保留，请在开工确认时否决该条。**
- **D5**：服务端 `id asc` 保留为分页机制（非展示排序），本单不动。
- **D6（流程偏离，留痕）**：本单**未走 QA 先行**，而是 PM 在 PRD 内**固化精确期望轨道表**（AC1）→ RD 实现+单测 → QA 独立复核。理由：改动小、期望值可完全穷举；以"QA 独立复核 + PM 读码交叉验证"替代"QA 写基线"，节省一轮往返。
