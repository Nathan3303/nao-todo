# 2026-11-07 编辑期覆盖可见化（`DEF-146`）PRD

- 状态：待开工确认 · 更新：2026-11-07 · Owner：PM
- 技术底稿：`docs/reports/T668-def146-verdict.md`（arch，含文件级拆解与变异点）· ADR `docs/adr/2026-11-06-edit-vs-remote-overwrite.md`（已接受、待落地）
- 关联：`docs/prds/2026-11-03-data-sync-a-batch.md`（`A1` 记账 / `F-01` 静默覆盖止血）· `docs/prds/2026-11-05-sync-perception-polling.md`（自动刷新，本缺陷的放大器）
- 批次：**编辑期覆盖批**（单任务，客户端 + domain 签名可选入参；服务端零改动）

## 一、问题证据

- **时序**：用户在任务编辑框打字**但未保存** → 另一端改了同一条 → 本端自动刷新（`v1.18.0` 起每 30s / 广播 / 回可见）把远端版本落库并**推进 base**（`syncedServerUpdatedAt`）→ 编辑器里保留用户草稿（`v1.18.1` 的 `DEF-145` 已保证输入不被冲掉）→ 用户保存时既有 OCC 判「基于最新版本」⇒ **`applied`**。
- **后果**：远端那次变更被**静默覆盖**，冲突面板**零记录**，**不可恢复**。用户永远不知道"我这一保存，把另一台机器的修改吃掉了"。
- **与 A 批同类**：A 批把「远端在我保存之后到达」这条对角线（`A1`）的覆盖记账做出来了，本缺陷是**另一条对角线**（远端在我保存**之前**到达），当时没有落点。
- **放大器**：`v1.18.0` 的自动刷新把该窗口从"偶发"变成**每 30 秒一次机会**（`PULL_BACKTRACK_MS=1000` 回拉 + 未变化行也重写 ⇒ 每轮都可能刷新 base）。
- **arch 结论（读码）**：唯一可行落点是**保存侧**。拉取侧否决理由：数据层拿不到「编辑器未保存草稿」（无 editing/dirty 通道），且 pull 每 30s 重放会每轮记一次 ⇒ **用户 Esc / 关面板不保存会产生假账**。

## 二、目标指标

- **指标 1（同字段并发必记）**：编辑期间同字段被远端改过、且用户保存的值与云端当前值不同 ⇒ **100% 落一条记录**（可见、可查看、可复制）。
- **指标 2（零误报）**：以下场景记录数 **= 0** —— 用户连改两次 · 仅格式化差异 · 远端改的是**别的**字段 · 用户改回原值 · 远端改完用户才输入 · 用户保存值与云端当前值相同 · 普通编辑（远端未动该字段）。
- **指标 3（零行为变化）**：OCC / `/sync/pull|push` 契约 / `pull-local-wins` 既有语义 / 上限 200 / 截断 512 —— **逐字不变**；老客户端与移动端零影响。
- **指标 4（不拖慢保存）**：记账在保存事务**之后**，失败只 log 不阻断；保存路径耗时不因本改动出现可感变化。

## 三、范围 / 非范围

**做**

- **保存侧三值判定 + 记账**：对「载荷字段 ∩ 编辑基准字段」逐字段判 `R_f ≠ O_f` **且** `L_f ≠ R_f` 才记账（`R`=库中云端当前值 / `L`=我的载荷 / `O`=编辑起点值）；比较一律走既有 `valuesEqual`，⛔ 不用 `!==`。
- **复用既有记账通道**：`kind = 'pull-local-wins'` + `appendConflict`（字段子集快照、忽略字段白名单、>512 截断带 `truncated`、上限 200 环形淘汰不升、journal 锁内 RMW）；抽共享 helper 复用 `recordPullLocalWins` 的「挑 diff 字段」逻辑；忽略字段统一用 `SYNC_COMPARE_IGNORED_FIELDS`（⛔ 不加第 4 套表）。
- **编辑基准入参（可选）**：domain 端口 / 用例 / 仓储链路加**可选**「编辑基准」参数，缺省 = 今天行为逐字不变（2 实现 + 约 8 调用点 + 组合根；移动端只需签名兼容）。
- **面板按钮收口（`D2`，同批）**：冲突面板目前对所有 kind 都渲染「保留服务端版本」，而该动作对非 `stale` 只清条目 ⇒ 对 `pull-local-wins` **点它是误导**。本批按 kind 收口（与 `DEF-139` 同一精神）。
- 编辑器传基准（`use-task-view-object`）。

**不做**

- **「保留服务端」对 `pull-local-wins` 的真写回（`D1` 选项 b）**：本批不做，登记为后续候选（触发条件见 §九）。
- **还回 base 让 OCC 自判 `stale`（`D1` 选项 c）**：会触碰 base / `R-20` 守护点，且保存后需用户裁决才上云 —— 本批不做。
- **提高淘汰优先级（`D3`）**：需新增区分字段（等于引入第四套 kind 语义）⇒ 不做，观察实际量再定。
- **`DEF-147`（回拉窗口未变化行无条件重写）**：与本源**零重叠**（pull 幂等 vs 本地保存记账），**继续挂账**；唯一口径：将来「内容等价则跳过 put」**不得**跳过 `syncedServerUpdatedAt` 推进。
- 移动端改动 · 服务端改动 · `/sync` 契约改动 · OCC 放宽。

## 四、用户场景

- **场景 1（主路径）**：桌面端打开某任务详情，把描述改到一半、尚未保存；这期间 web 端把同一条任务的描述改了并保存。桌面端**继续输入并保存**。→ **今天**：web 端那次改动被静默吃掉，谁都不知道。→ **本单后**：冲突面板出现一条「我的修改已覆盖云端」，能看到「云端当时的版本 / 我的当前版本」，可复制。
- **场景 2（不同字段，不应打扰）**：同上但 web 端改的是**优先级**，桌面端改的是描述。→ **本单后**：**零记录**（各改各的字段，没有覆盖）。
- **场景 3（连改两次）**：用户在详情面板连续保存两次，期间远端没动。→ **零记录**。
- **场景 4（改回原值，远端未动该字段）**：用户改了描述又改回原值再保存，期间远端**没有**动该字段。→ **零记录**（我的值 = 编辑起点值 = 云端值）。
- **场景 4b（改回原值，但远端改过该字段，`D8`）**：用户改了描述又改回原值再保存，期间远端把同一字段改成了别的值。→ **记 1 条**：这次保存**真的**把云端那次修改写回了旧值（静默覆盖真实发生），因此必须可见（显示「云端当时的版本 / 我的当前版本」）。⛔ 不加「我确实动过这个值（`L_f ≠ O_f`）」第三条件 —— 那会把一次真实覆盖变成不可见。
- **场景 5（远端改完我才输入）**：自动刷新先把远端新值落库（此时用户还没开始输入），用户基于**新值**编辑后保存。→ **零记录**（基准已是新值）。

## 五、业务规则

- **R-1（判据唯一）**：`F = keys(载荷) ∩ keys(编辑基准)`；逐字段 `R_f ≠ O_f` **且** `L_f ≠ R_f` 才记；比较用 `valuesEqual`（⛔ 不用 `!==`、⛔ 不新写比较函数）。
- **R-2（不误报）**：「保存载荷 ≠ 库中当前值」**不是**可用判据（远端未动该字段的普通编辑会全命中）⇒ 必须以 `O`（编辑起点）为锚。
- **R-3（kind 复用）**：记录 `kind = 'pull-local-wins'`，**不新增 kind**；界面文案沿用既有「我的修改已覆盖云端」与「云端当时的版本 / 我的当前版本」（⛔ 不新增文案键）。
- **R-4（快照口径不变）**：只存 diff 涉及字段 + 身份字段；剔除 `userId` / `syncedServerUpdatedAt` / `revision`；文本 >512 截断并带 `truncated`；上限 200 **不升**；忽略字段用 `SYNC_COMPARE_IGNORED_FIELDS` 单一来源。
- **R-5（记账在事务之后）**：保存事务成功后再记账；记账失败只 log、不阻断保存、不回滚业务写入（与既有 `appendConflict` 各调用点同姿态）。
- **R-6（缺省零行为变化）**：编辑基准为**可选**入参；不传 = 今天行为逐字一致（用于非详情面板入口、移动端与既有调用点）。
- **R-7（不新增裁决路径）**：OCC / base 推进 / `pull-local-wins` 既有语义 / 墓碑特判 —— 全部不动。本单只**新增一处记账时机**。
- **R-8（按钮按 kind 收口，`D6` 收敛后口径）**：冲突面板的「保留服务端版本」**仅对 `pull-local-wins` 不渲染**（改为复制入口 / 需手动处理说明）。理由：该动作只有 `stale` 会真写回，其余 kind 只清条目 —— 但 `remote-wins` / `push-noop` 语义上服务端已是胜方，点它是「确认保留」而非误导；`conflict` / `skipped` 已由 `DEF-139` 收口。⇒ 只掩掉唯一误导的那一类，且**不改既有用例**。

## 六、NFRs

- **性能**：保存路径不新增网络往返；判定在本地同步完成；记录写入不阻塞 UI（与既有 journal 写入同事务姿态）。
- **兼容**：domain 端口新增参数为**可选** ⇒ 不传的调用方零改动；`persistence-go` 签名跟随、行为零变；**移动端只验签名兼容**（红线：`packages/presentation-react` / `apps/mobile` diff = 0）。
- **可观测**：记录数与 kind 分布沿用既有状态面计数（零新增字段）；记账失败必须有结构化 log（含实体 id 与失败原因，**不落明文业务值**）。
- **数据安全**：快照仍只存本机 `meta`、随登出/清库清除、无网络上报（沿用 A 批 `R-H`）。

## 七、AC（五覆盖）

**主路径**

- **AC1**：编辑期间同字段被远端改过、用户保存的值 ≠ 云端当前值 ⇒ 冲突面板**新增 1 条** `pull-local-wins` 记录，可查看「云端当时的版本 / 我的当前版本」，可复制。
- **AC2**：该记录不改变任何同步裁决 —— 保存仍按既有 OCC 结果落库；不产生额外网络请求。

**异常**

- **AC3**：记账失败（写 journal 抛错）⇒ 保存**仍然成功**、无回滚、无用户可见错误；有结构化 log（含实体 id 与原因）。
- **AC4**：编辑基准缺失（老调用方 / 移动端不传）⇒ 记录数 **0**，保存行为与今天逐字一致。

**边界**

- **AC5**（零误报，逐条可断言）：连改两次 / 仅格式差异 / 远端改的是别的字段 / **用户改回原值且远端未动该字段** / 远端改完才输入 / 保存值 = 云端值 ⇒ **各 0 条记录**。
- **AC1b**（正例，`D8`）：用户改回原值**但远端改过该字段** ⇒ **1 条** `pull-local-wins`，显示「云端当时的版本 / 我的当前版本」，可复制。
- **AC6**：截断与上限不回退 —— >512 文本带 `truncated`；记录数超 200 时按既有优先级淘汰、总量仍 200。

**负向闭环**

- **AC7**（变异证明）：① 去掉「`R_f ≠ O_f`」⇒ 普通编辑误报，AC5 必红；② 去掉「`L_f ≠ R_f`」⇒ 改回原值也记账，AC5 必红；③ 用 `!==` 替代 `valuesEqual` ⇒ 格式化差异用例红；④ 快照取整行 ⇒ 忽略字段/体积断言红；⑤ 记账前置抛错 ⇒ AC3 红。
- **AC8**（不新增裁决路径，`D5` 收敛后口径）：以下**零改动**——`applyPullBatch` 的 if 分支结构 · `putWithSyncBase`（base 继承语义）· OCC 裁决 · 墓碑特判 · `sync-normalize` 判等；且**既有用例文件零改动并全绿**（用 diff 断言，非自述）。
    - **允许**（`D5`）：把 `sync-service.ts` 的「diff 挑选循环」抽成共享 helper 并让 `recordPullLocalWins` 改为调用 —— 前提 ① 既有 A1 用例**零改动**全绿 + 补 1 条新旧实现同输入同产物的等价用例；② 忽略字段**只留一份**（`SYNC_COMPARE_IGNORED_FIELDS`，旧表若成孤儿可删）；③ 重构面仅限该挑选逻辑，不顺手改周围判定 / 写回。

**设计一致性**

- **AC9**：不新增 i18n 键、不新增 kind、不自绘界面；「保留服务端版本」按钮按 kind 收口后，对 `pull-local-wins` **不出现**（AC 内断言按钮数）；中文文案沿用既有；移动端 diff = 0。

## 九、变更治理

- **重评触发点 1（`D1` 选项 b）**：若用户实际遇到「想一键把云端版本合回」的需求 **≥1 次**，立单做「保留服务端」的真写回（+0.5–1 人天，按字段合回当前行）。
- **重评触发点 2（`D3` 淘汰优先级）**：若观察到 `pull-local-wins` 记录被 200 上限挤掉的实例（面板里记录无故消失），再评估新增区分字段。
- **重评触发点 3（归因边界）**：若将来出现**第二个**修改 `name`/`description` 的本机入口（当前唯一入口是详情面板），必须补「base 前进门」并重评判据。
- **已知不关闭**：保存读/写之间毫秒级 TOCTOU 属既有窗口（⛔ 不把加解密挪进 Dexie 事务）。
- **决策留痕（2026-11-07）**：`D1 = (a) 可见 + 复制/导出`（不加写回）· `D2 = 同批收口按钮` · `D3 = 不做` · `D4 = 采纳`（PRD 增补同字段/不同字段两条 AC）。
- **决策留痕（2026-11-09，开工后由 rd-fe 提问触发）**：`D5 = 允许行为等价重构 + AC8 口径收敛`（见 AC8 两项前提；本意是防第二条裁决路径，不是文件不可碰）· `D6 = 面板收口取「仅 `pull-local-wins` 不渲染」`（`remote-wins`/`push-noop` 的服务端已是胜方，不算误导；不动既有用例）· `D7 = 新增 1 个 `STRUCTURED_LOG_EVENTS` 键用于 AC3 记账失败日志`（不含业务值，不算 kind / i18n / 状态面字段）。
- **决策留痕（2026-11-09，第二条）**：`D8 = 「改回原值」拆两义` —— 远端**未**动该字段 ⇒ 0 条（AC5 零误报项）；远端**改过**该字段 ⇒ **1 条**（新增 `AC1b`）。**判据冻结不变**，⛔ 不加 `L_f ≠ O_f` 第三条件（会把真实覆盖变成不可见）。

## 十、优先级与决策

- **战略筛子**：① 服务 C 端核心价值（数据可信）→ 是；② 现有能力可覆盖 → 否（当前零记录不可恢复）；③ 引入第二真源/第二裁决路径 → 否（复用既有 journal）；④ 触碰移动端红线 → 否；⑤ 跨仓 → 否。⇒ **通过**。
- **MoSCoW**：**Must** = 三值判据 + 复用记账 + 可选入参零行为变化 + 按钮按 kind 收口；**Should** = 无；**Could** = `D1(b)` 真写回；**Won't（本期）** = `D3` 优先级、`DEF-147`。
- **RICE**（触达 = 每周可能踩到的编辑并发次数，主观）：R=3 · I=3（静默丢数据、伤可信度）· C=0.8 · E=2.5 ⇒ **2.88**（高于 B′ 的 0.44，低于限流单的 7.2）。
- **Kano**：**基本型**（"我保存时改了什么、吃了什么"应当看得见）—— 不满足会直接损伤对同步的信任。
