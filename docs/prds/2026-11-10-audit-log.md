# 2026-11-10 A 档：变更审计日志（谁、何时、把什么改成了什么）

- 状态：待评审（arch 设计评审并行中）· 更新：2026-11-10 · Owner：PM
- 定位：事件溯源的**第一档**（`A 档 = 只追加审计日志，不换真相源`）。B 档（历史 + 单步撤销，15–25 人天）/ C 档（全事件溯源，45–80 人天）**不在本期**
- 上游依据：`docs/prds/2026-11-03-data-sync-a-batch.md`（可见可恢复）· `docs/prds/2026-11-09-field-level-merge.md`（B 批合并）
- 动机之一：**Agent 接入层（写权限）没有审计就不能开放** ⇒ 本档是其前置

## 一、问题证据

- **改了什么、谁改的，现在查不到**：任务表只存当前值，改了就覆盖；冲突 journal（`pull-local-wins` / `remote-wins` / `stale`）只记**冲突败方**、上限 200 环形淘汰 ⇒ ① 非冲突的正常修改完全无痕 ② 冲突记录也会被挤掉 ③ 无法回答「这条任务上周谁改成这样的」。
- **多端后归属模糊**：`T671` 实测同一任务可由「本机编辑 / 远端拉取 / push 合并 / 冲突重试」四条链路改写，用户与我们都无法回溯是哪条链路、改的是哪些字段。
- **删除与归档不可追溯**：`deletedAt` / `archivedAt` 一旦非空，之前的内容与操作者信息不再可见。
- **用户报障时无法定位**：过去多次（`DEF-131` 任务专注恒空 / `DEF-144` 刷新抖动 / `DEF-146` 静默覆盖 / `DEF-153` 非文本字段覆盖）都要靠**临时探针**重建现场；有审计日志即可直接回答「当时发生了什么」。

## 二、目标指标

- **指标 1（有痕）**：任一实体（`tasks` 先行）经**本机编辑**或**同步落库**（pull / push 合并且实际改变了业务字段）后，**1 条**审计记录可查（字段级 diff + 来源标记 + 时间 + 设备标识），覆盖率 = 100%（有变更就必须有记录，允许失败但必须可观测失败）。
- **指标 2（可读）**：界面能回答用户问题「这条任务最近改过什么」，用**人话**呈现（字段中文名 + 旧值→新值 + 时间），⛔ 不出现 `fieldBase`/`revision`/`kind` 等内部词。
- **指标 3（零侵入）**：审计写入失败**不阻断保存/同步**（沿用 `DEF-146` 姿态：只记结构化错误日志）；不增加网络往返。
- **指标 4（有界）**：本地存储有明确上限与保留期（见 R-5），超限淘汰最旧 ⇒ 体积可控（首版目标 ≤ 2 MB / 用户）。
- **指标 5（红线）**：移动端 `packages/presentation-react` / `apps/mobile` diff = **0**。

## 三、范围 / 非范围

**做**

- **本地审计日志**（同库新表 `auditLogs` + Dexie `version(5)` **空升级**，只增表、无需 `.upgrade()`）：记录 `entity`（**首版只 `tasks`**；`projects` ⛔ 不同批 —— 须先解 `DEF-155` 的记录层 `plain:` 陷阱）/ `entityId` / `action`（`create` / `update` / `archive` / `unarchive` / `delete` / `restore`）/ `fields`（字段级 `{field, from, to}`）/ `at` / `deviceId` / `source`（`local-edit` / `pull` / `push-merge` / `conflict-retry`）。
- **来源标记**：至少能区分「我在本机改的」与「同步从云端带下来的」，这是本档最直接的价值。
- **入口 = Footer「更多」菜单项「变更历史」→ 打开对话框**（`D8`，2026-11-11 用户定，替代原「详情面板内联区块」）：⛔ 不在详情正文里占位；对话框内为 C 端形态（卡片/时间线，非表格），只显示最近 N 条 + 「更早」分页。
- **`R-10`（入口形态，`D8`）**：变更记录**不得**内联在详情正文；入口收进 Footer「更多」菜单（与「导出 / 复制任务」同级），点击后以**对话框**呈现。理由（用户）：内联块会长期占位、把详情页越堆越长；这类「查阅型」信息应「用时打开、看完关闭」。对话框必须：可 Esc / × / 底部按钮关闭、焦点归还触发项、不因自动刷新被打断。
- **保留与清除**：上限与保留期（R-5）；登出 / 清库随业务数据一并清除。

**不做**

- **不做**事件溯源（真相源仍是当前表；日志是**旁路追加**，不参与裁决、不参与同步推送）
- **不做**撤销 / 重做（B 档）
- **不做**跨端 actor 归属（协议里没有 `actor` 字段；本档只能标"远端来的"，无法标"对方是谁"——这需要服务端契约变更，另议）
- **不做**服务端审计表 / 上报（隐私面扩大且跨仓；若后续 Agent 接入需要服务端侧审计，另立）
- **不做**移动端
- **不做**与 `conflict-journal` 合并（两者用途不同：journal 是"待处理的冲突败方"，审计是"已发生的变更"，⛔ 不得复用同一套淘汰策略）

## 四、用户场景

- **场景 1（主路径）**：用户打开任务详情 → 「变更历史」→ 看到「今天 14:32 我把「描述」从 A 改成 B」+「今天 14:20 云端同步把「优先级」从高改成中」。
- **场景 2（可解释的同步）**：用户在 B 端发现优先级变了、不是自己改的 → 历史里明确写「同步自云端」，与"我自己改的"可区分。
- **场景 3（报障定位）**：用户说"我的任务莫名消失了"→ 历史显示「昨天 09:12 删除（本机）」或「同步自云端：归档」→ 直接定位，无需探针。
- **场景 4（批量）**：清理批/合并批导致的多字段变更 ⇒ **1 条记录带多个字段 diff**（不刷屏成 N 条）。

## 五、业务规则

- **R-1（旁路）**：审计写入**不得**参与任何裁决，不改变 OCC / base / 合并 / 冲突语义；⛔ 不得让审计失败影响业务写。
- **R-2（字段级 diff）**：只记**实际变化**的业务字段；比较用既有 `valuesEqual`（单一口径）；忽略集用 `SYNC_COMPARE_IGNORED_FIELDS`（⛔ 不新增第五张表）。
- **R-3（同一次写 = 1 条）**：一次业务写（含合并落库）产生**1 条**记录；`fields` 内按固定顺序（`entityToPush` 键序）稳定输出。**创建（`create`）也要记 1 条**（`action=create`，`fields` = 新建时的业务字段）—— 历史里应能看到「谁创建了这条任务」（PM 2026-11-11 裁定，先前 PRD 漏写）。
- **R-4（来源枚举固定）**：`local-edit` / `pull` / `push-merge` / `conflict-retry` 四值，**不新增**（新增须 PRD 评审）。
- **R-5（有界）**：每用户保留 **≤ 1000 条** 且 **≤ 90 天**，先到者淘汰（环形）；单条 `fields` 值 > 512 字符截断并标记 `truncated`（沿用 journal 口径）。
- **R-6（隐私）**：日志只存业务值（与业务表同等明文姿态，`plain:` 已在库内）· ⛔ 不存 token / 口令 / 完整 JWT · ⛔ 不上报服务端 · 登出/清库随业务数据删除。
- **R-7（说人话，`D2` 修正）**：**字段名**复用既有 `conflict-field-labels`（40+ 人话标签）；**面板框架文案**允许新增 **≤13 个 i18n 键**（标题 / 空态 / 来源 4 值 / 动作 5 值），须在开工确认卡逐条列出，⛔ 不得超出。
- **R-9（收集箱桶归一，`T696` C2）**：审计 diff **前**必须做 `projectId` 归一转译（`'inbox'` ↔ 服务端隐式桶 `userId`，复用 `toLocalProjectId`）；否则**每个收集箱任务每轮 pull 都会产出一条假的 `projectId` 变更**（`v1.19.0` 的字段合并已做同型归一，审计必须一致）。**这是本档最容易漏测的假刷屏源**（既有用例抓不到）。
- **R-8（范围守卫）**：首版只接 `tasks`；其它实体按同一 helper 逐个接入（`R-8` 与 B 批同型）。

## 六、NFRs

- **性能**：审计写入为一次附加 `add`（批量事务内或紧随其后），保存路径耗时不出现可感变化；读历史按 `entityId + at desc` 走索引。
- **存储**：新表 + 索引；Dexie 版本 +1 并**幂等迁移**（老库升级不丢数据）。
- **兼容**：老数据无审计 ⇒ 历史区显示"暂无记录"（⛔ 不得显示错误）；移动端零改动、只验不崩。
- **可观测**：写入失败走既有 `STRUCTURED_LOG_EVENTS` 风格事件（不含业务值）。
- **可回滚**：审计表可整表清除（提供一次性清理入口/脚本），清除后业务零影响。

## 七、AC（五覆盖）

**主路径**

- **AC1**：本机改 3 个字段 ⇒ **1 条**记录，`fields` 恰含这 3 个字段（顺序稳定）+ `source=local-edit` + `at` 合理。
- **AC2**：pull 带来远端变更（1 个字段）⇒ **1 条** `source=pull`，且**不**与本地编辑混记。
- **AC3**：界面真挂载 ⇒ 时间线可读、字段用中文标签、无内部词、无技术键名（⛔ stub 不算证据）。
- **AC12**（入口形态，`D8`）：详情正文中**不出现**变更记录区块；Footer「更多」菜单里有「变更历史」项；点击后**对话框**打开并可 Esc / × / 底部按钮关闭（焦点归还触发项）；关闭后详情页无残留占位。
- **AC13**（展示形态，`D9`）：**⛔ 不得用左侧竖线 / 左侧色条 / 时间轴轨道**表达来源或分组；改为**活动流（activity feed）**行式呈现 —— 每行 = 圆形来源徽标 + 主文案（来源中文 · 动作/字段变更）+ 右侧时间；行高 ≥44px、整行可点、hover/focus 有底色、键盘可达（Tab + Enter 展开长值）；文本对比度 ≥4.5:1、图形 ≥3:1（**按渲染后计算样式实测**）；**i18n 仍 ≤13 键**。

**异常**

- **AC4**：审计写入抛错 ⇒ **业务保存仍成功**、无回滚、有结构化错误日志（含 entity/entityId/原因，不含业务值）。
- **AC5**：老库（无审计表）升级 ⇒ 迁移成功、历史区显示"暂无记录"、业务数据零变化。

**边界**

- **AC6**：`>512` 值截断带 `truncated` · **单条记录 ≤1 KB 字节预算**（超出按字段截断；这是「≤2 MB 总体积」成立的前提）· 超 1000 条 / 90 天 ⇒ 最旧被淘汰且总量不超上限 · 同一次写只 1 条（⛔ 不刷屏）。
- **AC11**（防假刷屏，`R-9` / `T696` C2）：**收集箱任务**在内容无变化时连续 pull 多轮 ⇒ **0 条**审计记录（若未做 `projectId` 归一 ⇒ 每轮 1 条假 `projectId` 变更）。
- **AC7**：删除 / 归档 / 恢复各产生 1 条（`action` 正确）· 墓碑操作不产生"字段变更"噪声。

**负向闭环**

- **AC8**（变异证明）：① 审计接线去掉 ⇒ AC1 红 ② 用 `!==` 替 `valuesEqual` ⇒ 空哨兵用例红 ③ 记录整行快照而非 diff ⇒ 体积/最小化断言红 ④ 审计前置抛错 ⇒ AC4 红 ⑤ 去掉上限淘汰 ⇒ 边界用例红。
- **AC9**（不侵入）：OCC / base / `field-merge` / `conflict-journal` **语义与既有用例零改动**（diff 断言）；`valuesEqual` 口径未变。

**设计一致性**

- **AC10**：C 端形态（卡片/时间线，无表格式排版）· 复用既有 i18n 与字段标签（零新键）· 移动端 0 行 · 若新增交互样式须同批更新 `DESIGN.md`。

## 九、变更治理

- **重评触发点 1**：若需要「对方是谁」（跨端 actor）⇒ 必须改服务端契约（sync 载荷带 `actor`），单独立项。
- **重评触发点 2**：若用户真实需要"撤销这一步"⇒ 升 B 档（15–25 人天）。
- **重评触发点 3**：若 Agent 接入层需要**服务端侧**审计（不只本机）⇒ 另立跨仓单。
- **已知不关闭**：老数据无历史；跨端无法标 actor；审计不参与裁决（设计如此）。

## 十、优先级与决策

- **战略筛子**：① 服务 C 端核心价值（可追溯/可信）→ 是；② 现有能力可覆盖 → 否（journal 只覆盖冲突败方且上限 200）；③ 引入第二真源/第二裁决路径 → 否（旁路日志，不参与裁决）；④ 触碰移动端红线 → 否；⑤ 跨仓 → 否（首版本机）。
- **MoSCoW**：**Must** = 旁路写入 + 字段级 diff + 来源标记 + 有界 + 不阻断业务；**Should** = 详情面板时间线；**Could** = `projects` 实体接入；**Won't（本期）** = 撤销、跨端 actor、服务端审计。
- **RICE**（主观）：R=4（所有多端/报障场景都受益）· I=3（提升可信与可运维性，非直接功能）· C=0.85（新表 + 迁移，风险集中在 Dexie 版本）· E=7.5（人天，`T696` 复核）⇒ **≈ 1.36**。
- **Kano**：**期望型**（"我改了什么应该查得到"），缺失不致命但直接损伤信任。
- **预算**：**7–8 人天**（`T696` 复核：5 人天不成立，理由见评审工期表）；超过 8 人天须重报。
- **决策留痕（2026-11-10，arch `T696` 评审后 PM 拍板）**：`D1 = 同库新表 + version(5) 空升级`（否决独立第二库 / `meta` 数组）· `D2 = 复用字段标签 + 允许 ≤13 个框架 i18n 键`（「零新键」不可行）· `D3 = 来源复用四值`（用云端的→`pull`、保留我的→`conflict-retry`，⛔ 不新增第 5 值）· `D4 = 同一实体一次写 1 条`（批量按实体计数，⛔ 不按用户手势）· `D5 = 数组字段顺序噪声先接受并观测`· `D6 = 首版不接 projects`（前置 `DEF-155`）· `D7 = 面板随 desktop 一并上线`（`app.ts` 一处 provide 覆盖两端）。
- **评审带入的新发现**：`R-9` / `AC11`（收集箱桶归一是假刷屏源，`T696` C2）；同批登记 `DEF-159`（既有归一口径缺口，任何「按字段比较」的新路径都会踩）。
- **决策留痕（2026-11-11，用户提出）**：`D8 = 入口由「详情正文内联区块」改为「Footer『更多』菜单项 + 对话框」` —— 理由：内联块长期占位、详情页越堆越长，查阅型信息应「用时打开、看完关闭」。⇒ 新增 `R-10` / `AC12`；对话框三条硬要求（可 Esc/×/底部关闭 · 焦点归还 · 不被自动刷新打断）已写入 `R-10`。
- **决策留痕（2026-11-12，用户提出）**：`D9 = 对话框内的展示由「左侧色条/时间轴」改为「活动流（activity feed）」` —— 用户原话：不要选项左侧线条这种设计，参考业界历史记录类展示。**业界参照**（本档只借样式，不引入依赖）：GitHub 活动流（圆形图标 + 动作句 + 右侧相对时间，无竖线）· Linear（按天轻分组、行内 icon + 动作、极淡分隔）· Notion 页面历史（行式列表、hover 整行）· Google Drive 活动面板（icon + 「你编辑了 X」+ 右侧时间）。⇒ 具体形态：① **删除** `border-left` 四条低阶修饰与任何竖线/轨道；② 每行 flex：20px 圆形来源徽标（色 + 符号 + 文字三重冗余）· 主文案 `来源中文 · 字段名 旧 → 新`（长值单行省略 + 点击展开，复用既有 `sync.conflict.expand/collapse`）· 右侧时间（次要色 12px、`tabular-nums`，复用既有 `date.today` / `date.yesterday`）；③ 按天轻分组（今天 / 昨天 / 更早）+ 组间留白，组内用留白或极淡分隔（⛔ 表格线、⛔ 竖线）；④ 整行 hover/focus 底色（主题 token，⛔ 硬编码色值）、圆角 8px、焦点环可见。**i18n 预算不变（13 键）**：分组标题与相对时间若既有键不足 ⇒ 先报 PM，⛔ 不得擅自新增。
